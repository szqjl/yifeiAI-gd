# YiFeiAI-GD 项目开发历程总览

**整理目的**：以「人类速度」完整兜底翻看项目，梳理开发历程与现状，便于后续协作与决策。  
**整理时间**：2026-02-26  
**阅读范围**：README、docs、src 主模块、训练/分析文档、分支与版本说明。

---

## 一、项目定位与目标

- **是什么**：南京邮电大学掼蛋AI算法对抗平台的**客户端实现**，不是平台本身。
- **平台**：https://gameai.njupt.edu.cn/gameaicompetition/gameGD/index.html，当前版本 v1006。
- **核心目标**：
  - 实现 AI 自动出牌决策，符合平台协议（WebSocket + JSON）；
  - 支持自我对弈与数据收集；
  - 可扩展架构（规则引擎 / 机器学习可切换）；
  - 平台动态信息监控（可选）。
- **约束**：组队规则 1-3 一队、2-4 一队；决策响应 &lt; 1 秒；信息监控间隔 ≥ 6 小时、静默时段 0:00–6:00；**所有时间必须用系统 API**，禁止硬编码。

---

## 二、技术架构（分层）

从文档与代码可见的稳定分层：

1. **应用层**：入口脚本、配置、日志（无统一 `main.py`，按分支/版本有多套入口）。
2. **通信层**：`src/communication/` — WebSocket 连接、消息收发、对局录制（`GameRecorder`），多套客户端并存（见下）。
3. **决策层**：`src/decision/` — 规则引擎 M1、阶段路由器、牌型处理、策略引擎、配合策略；另有 RL/MoE/终极胜率等实验性引擎。
4. **知识层**：规则库、策略库、技能库（`docs/knowledge/`），部分有 YAML 与加载逻辑。
5. **游戏逻辑层**：`src/game_logic/` — 牌型识别与比较、记牌与推理（CardTracker）、状态管理（EnhancedGameStateManager）、手牌组合（HandCombiner）等。
6. **数据与训练**：`src/data/`、`src/train/` — 对局数据、回放、多种训练脚本（BC、RL、阶段 7/8、胜率导向等）。
7. **监控与运维**：`src/monitor/` 平台信息抓取；`batch_executor/` 批量对局执行与重启；根目录多套 GUI/批处理入口。

整体符合 README 与《[掼蛋AI客户端架构方案](../architecture/掼蛋AI客户端架构方案.md)》中描述的分层设计。

## 三、分支与版本线（你实际在走的路）

- **main**：主分支，合并与发布用。
- **m-dev**：当前主开发分支。**M1 = 硬编码规则引擎**，不是机器学习模型；5 阶段细分路由（开局 / 中局前 / 中局后 / 残局前 / 残局后），主动/被动出牌分离，策略引擎（队友保护、优先级、牌值系统）、手牌结构分析、残局策略类。
  - 客户端：`yf1_m1.py`、`yf2_m1.py`（Player 0 与 2）；优先尝试加载 MoE 引擎，失败则回退到 `RuleBasedDecisionEngineM1`。
- **m1-dev-clean**：轻量干净分支，无模型与游戏记录，适合远程训练/协作。
- **v6-dev**：V6 优化线，`yf1_v6` / `yf2_v6`，基于旧架构的优化版。
- **V7**：在 m-dev 上出现的新线，包含 `yf1_v7.py`、`yf2_v7.py`、`ultimate_win_rate_engine_v7.py`、`ultimate_win_rate_training.py`，以及 `start_v7_*.py`、`diagnose_v7_connection.py` 等；已修复 `actIndex` 与连接顺序问题（见 [V7_SYSTEM_FIXES.md](../fixes/V7_SYSTEM_FIXES.md)），偏「终极胜率」实验。

README 里仍有少量合并冲突标记（`<<<<<<< HEAD`），说明主分支与 m1 的文档曾有过未完全合并的修改。

## 四、训练与机器学习路线（阶段 0–8）

- **阶段 0**：基础验证与数据验证；课程学习；基线指标（如完全匹配 37.31%、卡牌级 96.73%），数据量约 796 样本/34 对局。
- **阶段 1–4**：完善信息提取、策略理解深化、动作预测精度、持续优化（见《方向评估与完整提升方案》《历次训练效果汇总》）。
- **阶段 5**：完全匹配准确率优化（曾到 59.67%）、高级策略学习；概率偏低（如 0.0063）、概率缩放与阈值等问题被反复记录。
- **阶段 6**：游戏导向训练（目标与评估更贴近对局结果）。
- **阶段 7**：策略学习重构；大量 `stage7_*` 脚本（breakthrough、lightning、optimized、evaluation、robust 等）和阶段 8 的强化学习整合，说明在反复尝试突破。
- **阶段 8**：强化学习整合；Self-Play 参数（episodes、学习率、早停）有推荐配置。

**历次训练效果汇总** 中记录：数据从极少样本到 1.3w+ 样本，完全匹配率从高到崩再调到 59.67%；RL 曾出现平均奖励负、波动大、需固定种子与学习率衰减。结论是：**方向正确（BC + Self-Play + 课程学习），但实施不完整**——信息提取不全、策略理解不足、概率与奖励设计未根本解决。

## 五、硬编码路线（YF 与 M1）

- **决策**：约 2025-12 中旬，基于「机器学习 3 周未达预期」的结论，**策略重心回归硬编码**（见《YF硬编码完整提升计划》及优化版）。
- **参考对象**：对 lalala 的决策机制做了完整分析（`lalala决策机制完整分析*.md`），学习其 rule_parse → passive/active → 牌型专法的简洁结构，但强调「学习优点不抄袭」，做 YF 自己的分层与模块化。
- **M1 设计**：RuleBasedDecisionEngineM1 = StageRouter + 各阶段 Active/Passive Handler + Tribute/Back + 可选 IntelligentStageRouter；StrategyEngine（队友保护、优先级、牌值）、HandStructureAnalyzer、残局策略集成在阶段处理器内。
- **实施与问题**：有《YF硬编码阶段1实施总结》《M1策略问题分析与修复计划》《M1开局主动出牌策略说明》《M1卡牌一致性修复说明》等，说明 M1 在持续修策略与一致性问题；另有 `analyze_m1_*` 等脚本用于分析行为与 PASS 等问题。

## 六、工具与基础设施

- **批量执行**：`batch_executor/` — 主执行器、状态持久化（`execution_state.json`）、重启管理（`restart_manager`）；根目录 `batch_executor_gui.py`、`batch_executor_gui_m1.py` 提供 GUI，可配置对局数、客户端路径等。
- **启动与诊断**：多套 `START_*.bat`、`start_v7_*.py`、`diagnose_v7_connection.py`、`test_v7_*.py`，便于本地与 V7 调试。
- **模型与仓库**：模型/检查点不入库；`check_models_before_push.py`、`verify_gitignore` 等用于推送前检查。
- **知识库与文档**：`docs/knowledge/` 下规则、策略、技能；有冲突检查报告、YAML 依赖与集成说明；`docs/development/` 下分支指南、M1 测试指南、手牌扫描器与上下文衔接等。

## 九、结论（人类视角的归纳）

- **项目已经是一个「成型的掼蛋 AI 客户端」**：能连平台、能出牌、能对局录制、有规则引擎（M1）、有批量测试和 GUI，文档和分支管理都很认真。
- **难点不在「能不能做」，而在「做到什么水平」**：大厂级、强策略、可解释、高胜率，需要数据、策略设计、奖励与概率设计、大量实验，这些在《Cursor无法解决的问题分析》里写得很清楚；单人说「你能力无法搞掼蛋 AI」更像是「以当前条件很难做到顶尖」，而不是「项目没价值」。
- **你已经在两条腿走路**：一条是硬编码 M1（可维护、可解释、持续在修）；一条是 ML/V7（数据与训练管线在，效果待验证）。两条线都有文档和代码支撑，适合按「先稳住 M1 体验，再逐步用数据与实验补 ML」的节奏推进。

若你愿意，下一步可以针对「当前最想解决的一个具体问题」（例如：M1 某类牌局表现、V7 与 M1 对比、或数据/标注 pipeline）再拆一版可执行清单。
