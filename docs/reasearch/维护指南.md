## 🎯 三个新文档的用途

### 1. [[README.md]] — 索引文档

**用途**:
- 快速了解所有调研文档的核心结论
- 查看文档的时效性状态
- 建立与项目决策（GUA/ITERATIONS）的关联

**何时使用**:
- 新 Agent 启动时，先读此索引
- 季度回顾时，检查状态表格
- 做决策前，查找相关调研依据

**核心字段**:
```markdown
| 文档 | 核心结论 | 最后更新 | 状态 | 关联 GUA | 落地情况 |
|------|---------|---------|------|---------|---------|
```

---

### 2. [[时效性检查模板.md]] — 检查清单

**用途**:
- 为每个调研文档添加 frontmatter
- 定义"活跃/待更新/已过期"状态
- 提供过时结论的标记方法

**如何使用**:
1. 复制 frontmatter 模板到每个调研文档顶部
2. 填写 `created`/`updated`/`reviewed` 日期
3. 标注 `status` 和 `related_gua`
4. 设置 `next_review` 提醒

**Frontmatter 示例**:
```yaml
---
created: 2026-01-15
updated: 2026-05-31
reviewed: 2026-06-02
status: 活跃
tags: [调研，技术选型]
related_gua: [GUA-026, GUA-029]
related_iter: [2026-05-31-M3-batch]
next_review: 2026-09-02
---
```

---

### 3. [[action_tracker.md]] — 落地追踪表

**用途**:
- 追踪调研建议是否转化为实际代码/决策
- 记录落地效果（胜率提升/性能改善）
- 避免"调研完就忘"

**核心流程**:

```
调研文档 → 发现建议 → 登记到 action_tracker
       ↓
创建 GUA/TASK → 实施代码 → 批跑验证
       ↓
更新 action_tracker 为"已落地" → 填写效果
```

**状态分类**:
- ✅ 已落地（附效果验证）
- 🧪 验证中（实验/批跑）
- 📋 待办（待评审/拆分）
- ❌ 已否决（附原因）
- ⏸️ 搁置（等待条件）

## 📋 维护工作流

### 场景 1: 创建新调研文档

```
1. 撰写调研内容
2. 在顶部添加 frontmatter（复制时效性检查模板）
3. 填写 created/updated 日期
4. 标注 related_gua（如有）
5. 在 README.md 的表格中新增一行
6. 在 action_tracker.md 登记建议
```

### 场景 2: 更新已有调研文档

```
1. 修改文档内容
2. 更新 frontmatter 的 updated 日期
3. 如有新结论，在 README.md 更新"核心结论"
4. 如有新建议，在 action_tracker.md 新增一行
5. 如标记过时，用删除线 + 注释说明
```

### 场景 3: 调研建议落地

```
1. 创建 GUA 或 TASK
2. 实施代码改动
3. 批跑验证效果
4. 在 action_tracker.md 更新状态为"已落地"
5. 填写 PR/Commit 和效果数据
6. 在 README.md 更新"已落地"表格
```

### 场景 4: 季度回顾

```
1. 检查 README.md 中所有文档的"最后更新"
2. 对超过 3 个月未更新的，标记为"待更新"
3. 检查 action_tracker 中的"待办"和"验证中"
4. 清理"搁置"超过 6 个月的项目
5. 更新 ITERATIONS.md 记录本季度成果
```

## 🚀 立即可做的事

### 第一步：为现有文档添加 frontmatter

打开每个调研文档，在顶部添加：

```yaml
---
created: [创建日期，如不知道就写 2026-06-02]
updated: [今天日期 2026-06-02]
reviewed: [今天日期 2026-06-02]
status: 待回顾  # 先标记为待回顾
tags: [调研，根据内容填写]
related_gua: []  # 如有已知关联的 GUA，填写
next_review: 2026-07-02
---
```

### 第二步：填写 README.md 的表格

打开 [[README.md]]，为每个文档填写：

| 文档 | 核心结论 | 最后更新 | 状态 | 关联 GUA | 落地情况 |
|------|---------|---------|------|---------|---------|
| 调研 - 技术研判 | [用 1 句话总结] | 2026-06-02 | 🟡 待回顾 | [] | 待追踪 |

### 第三步：在 action_tracker 登记已知建议

如果您记得某些调研建议已经落地或正在验证，直接填写：

```markdown
## ✅ 已落地

| 来源 | 建议 | 落地形式 | 效果 |
|------|------|---------|------|
| 调研 - 竞品实测 | 炸弹过滤策略 | GUA-029 | +15% |
```

## 💡 最佳实践

### ✅ 推荐

1. **创建时即标注**: 新文档创建时就加 frontmatter
2. **关联可点击**: 用 `[[文档名]]` 链接，Obsidian 会自动关联
3. **结论可追溯**: 每条建议都应有 GUA/TASK 编号
4. **定期清理**: 每季度检查一次，标记过时内容
5. **效果量化**: 已落地的建议填写具体数据（胜率/性能）

### ❌ 避免

1. **只调研不落地**: 调研完就忘，不追踪实施
2. **过时不标记**: 结论已失效但未标注
3. **孤立文档**: 不与 GUA/ITERATIONS 建立关联
4. **过度详细**: 核心结论超过 5 条，难以速读
5. **长期不回顾**: 创建后从未更新 reviewed 日期
