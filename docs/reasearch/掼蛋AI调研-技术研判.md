## T1. Danzero+ 源码架构（P0）

### 1.1 总体架构

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  Game Core  │────▶│   Actor × N  │────▶│  Learner    │
│ (掼蛋引擎)  │     │ (采样器)     │     │ (训练器)     │
└─────────────┘     └──────────────┘     └─────────────┘
                         │                    │
                         ▼                    ▼
                    ZMQ 通信            TensorFlow/PyTorch
                         模型参数同步
```

**两阶段：**
- **Phase 1**：训练 value-based teacher（Danzero 原版 DMC）
- **Phase 2**：用 teacher 筛 top-K 动作，喂 policy net（PPO）训练

### 1.2 关键技术细节

**动作空间处理（核心贡献）**

| 方案 | 方法 | 复杂度 | 问题 |
|------|------|--------|------|
| Danzero | Value-based: (s,a)→Q(s,a) | O(1) 每步 | 探索受限 |
| Danzero+ | top-K 过滤 + PPO | O(K) | K 过大效果下降 |
| PPO 原始 | softmax 全动作 | O(|A|) | 显存爆炸 |

**动作压缩策略（Danzero+）：**
```
1. Teacher 对当前状态评估所有合法动作 Q 值
2. 取 top-K（K=2 最优）作为 candidates
3. Policy net 只在 K 个候选上输出概率分布
4. 训练损失同时保留 teacher Q 值正则化
```

**实验结果：**
- K=2 时胜率 55% 击败 rule-based（远超 rule-only 30%）
- K 增大到 >4 时胜率下降（原因：探索空间过窄）

### 1.3 牌态编码（公开信息有限）

根据论文描述 + 代码结构推断：

| 特征 | 维度 | 说明 |
|------|------|------|
| 手牌编码 | ~108×N | 每张牌 one-hot 或 embedding |
| 出牌历史编码 | ~108×T | 时间步序列 |
| 出牌类型 one-hot | ~15 | 单张/对子/三张/顺子/炸弹等 |
| 玩家信息 | ~4 | 手牌数、得分、位置 |
| 当前级牌 | ~1 | 影响牌力大小 |

**联合编码方式：**
- 手牌 → CNN/MLP 提取 spatial 特征
- 历史 → LSTM/Transformer 提取时序特征
- Concatenate 后进入决策网络

### 1.4 工程实现

**Actor-Learner 分离架构：**
- Actor：做游戏交互 + 采样，'python actor_n/actor.py'
- Learner：模型更新，'python learner_n/learner.py'
- 通信：ZMQ（pyzmq）
- 框架依赖：TensorFlow 1.x + PyTorch 1.9（CPU actor / GPU learner）

**注意：** TF 1.x 已 deprecated，迁移到 TF2.x 或 PyTorch 需要大量改动。

## T2. SDMC 论文技术细节（P0）

### 2.1 南京大学方案（未开源）

**核心创新：**

| 模块 | 原理 | 增益 |
|------|------|------|
| **软启动** (Soft Init) | 用已有策略（rule-based）初始化 agent，而非随机 | 加速收敛，少走弯路 |
| **软动作采样** (Soft Action) | 训练中以一定概率混合 rule-based 动作和模型探索动作 | 提升策略稳定性 |

**架构：**
- 2 个价值网络（V-net）
- 蒙特卡洛采样估值
- 奖励设计：胜率 + 每小局净胜分

**实验结果（与 Danzero 对比）：**
| 方法 | 胜率 vs 1st Top 16 | 每小局净胜分 |
|------|-------------------|-------------|
| SDMC | **~57%** | +X |
| DMC (Danzero) | ~54% | - |
| Rule-based | ~30% | - |

### 2.2 ABL-GD 反绎学习（CCFAI 2025，未开源）

**突破性关键：动作空间压缩 ~168 伪动作**

```
原始动作空间：~10^18（108 张牌的所有排列组合）
压缩后：168 个"伪动作"

方法：
1. 知识库定义合法牌型模式
2. ABLN 推理对手隐藏手牌
3. Decision model 输出 168 维概率分布
4. Inconsistency Minimizer 保证规则合规 + 选择最高分合法动作
```

**混合训练：**
- 阶段 1：预监督学习（随机策略数据模拟）
- 阶段 2：PPO 强化学习

**实验结果：**
- 500 局胜率 **60.9%**（±0.7%）—— 接近人类专家
- 净胜分 +740（500 局）
- 数据集：专家手牌标注数据集（200 局，15,645 个动作）

**关键洞察：** ABL-GD 是目前唯一达到人类专家水平的算法。

## T4. 自对弈训练流程（P1）

### 4.1 Danzero+ 训练流程（可复现）

```
1. 初始化：rule-based policy 生成初始对局数据
2. 预训练：value net 用蒙特卡洛预测对局结果
3. 自对弈循环：
   a. Actor 用当前策略在线对局
   b. 每步采样 (state, action, reward)
   c. Learner 更新 value net + policy net
   d. 定期评估对 rule-based/旧策略
4. 模型版本：定期保存，淘汰劣质版本
```

### 4.2 ABL-GD 训练流程

```
1. 收集专家手记数据
2. 预监督：BC 学习专家行为
3. PPO：对专家策略微调
4. 自对弈迭代：对局数据 → ABL-GD 推理 → PPO 更新 → 重复
```

### 4.3 数据渠道评估

| 来源 | 成本 | 数据质量 | 合规性 | 可行性 |
|------|------|---------|--------|--------|
| ABL-GD 专家数据集 | 中等 | ⭐⭐⭐⭐⭐ | ✅ | 论文已用 |
| 自对弈生成 | 低 | ⭐⭐⭐（初始弱） | ✅ | ✅ 推荐 |
| 欢乐掼蛋爬虫 | 高 | ⭐⭐⭐⭐ | ⚠️ | 需合规审查 |
| 真人采集 | 极高 | ⭐⭐⭐⭐⭐ | ❌ | 不建议 |

## T5. 低延迟工程实现（P1）

### 5.1 现有问题

Danzero/Danzero+ 框架：
- Actor 单进程，每次出牌需完整推理
- TensorFlow 1.x 无现代推理优化
- ZMQ 通信有网络开销

### 5.2 推荐优化

| 方案 | 收益 | 工程量 | 优先级 |
|------|------|--------|--------|
| 引擎 → ONNX 导出 | 推理提速 2-4x | 低 | P0 |
| Actor 批量并发 | 4 人同时推理 | 低 | P0 |
| Redis 缓存 | 常见牌型快速返回 | 低 | P1 |
| Triton Inference Server | 多模型并发 + 动态批 | 中 | P2 |

## 综合结论与技术选型建议

### 最优技术路径

```
目标：做出一个具有拟人化、配合强、可产品化的掼蛋 AI

推荐方案 B（基于 Danzero+ 自训练）：

1. 基础框架：DanZero+ 架构（已适配掼蛋，含百搭牌/级牌/4人组队）+ top-K 改进
   - 为什么：代码完整、已验证、Apache-2.0、掼蛋规则已内置

2. 牌态编码：参考 ABL-GD 的 168 伪动作压缩
   - 为什么：168 维 vs 10^6 维，训练效率提升 10^4x

3. 协同建模：双 LSTM 共享 encoder + 独立决策头
   - 原因：最大差异化点，joy/欢乐掼蛋也做不好的地方

4. 拟人化：PPO reward 中引入"姿态打牌"惩罚
   - 原因：市场空白，差异化竞争

5. 段位分级：Elo 在线评测 + 动态难度调整
   - 原因：产品化必需，用于陪练/对战匹配

6. 低成本启动：先用 ABL-GD 论文的专家数据集预训练
   - 原因：减少自对弈冷启动时间
```

### 工程优先级（Roadmap）

| Phase | 周期 | 目标 |
|-------|------|------|
| Phase A | 2-4周 | 复现 Danzero+ 代码 + 本地 PyTorch 迁移 |
| Phase B | 4-6周 | 添加 168 伪动作压缩 + 双人协同建模 |
| Phase C | 4周 | 接入自对弈训练 pipeline + 迭代 |
| Phase D | 2周 | Elo 评估系统 + 段位分级 |
| Phase E | 2周 | 拟人化 reward 设计 + 评测 |
