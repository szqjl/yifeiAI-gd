```python
def wait_for_all_clients_game_ready(
    expected_ids: Iterable[str],
    *,
    timeout: float = 90.0,  # 默认 90s
    poll_interval: float = 1.0,
) -> bool:
    """批跑侧等待 expected_ids 全部 game_ready（首条游戏消息已被处理）。"""
    expected = set(expected_ids)
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        ready = _game_load()  # 读 batch_executor/game_ready.json
        if expected.issubset(ready.keys()):
            return True
        time.sleep(poll_interval)
    return False
```

## 3. 73s 卡顿的真因

### 3.1 双根因分解

| 根因 | 占比 | 位置 | 性质 |
|---|---|---|---|
| **根因 A**：客户端 `mark_game_ready` 写盘耗时 > 60s | 60/73 = **82%** | `src/communication/lalala_adapter.py` 的 `mark_game_ready` 调用链 + V7 引擎冷启动 | **客户端问题** |
| **根因 B**：`ServerStdoutReader.start()` 在 game_ready 超时**之后**才启动 | 13/73 = **18%** | `batch_executor/executor.py:547` | **批跑侧调度问题** |

### 3.2 因果链

```
20:59:06 服务器向 4 席推送 game_start
    ↓
20:59:07 4 席 burst 出 actIndex（首轮决策）
    ↓
20:59:08 4 席进入 "等待服务器下次推送" 状态
    ↓
[客户端异步处理 game_start 消息]
    V7 引擎: torch 模型加载 + 124 维特征提取 + 首次推理 = 冷启动 1-3s
    lalala: 规则引擎初始化 + 当前局面评估
    ↓
[handle_game_start 完成后调用 mark_game_ready(client_id)]
    mark_game_ready → 写 batch_executor/game_ready.json（单进程文件 IO）
    ↓
[等待 60 秒仍未全部写完]
    ↓
21:00:09 batch_executor WARNING 退出
    ↓
21:00:10 ServerStdoutReader.start() 启动
    ↓
21:00:10 dump 落幕（前 60s 积压的服务器 stdout 一次性写入主日志）
    ↓
21:00:10~21:00:19 14 副密集打完（每副 < 1 秒，因为客户端已经 warmed up）
    ↓
21:00:19 游戏 #15 结束 + victoryNum 落盘
    ↓
21:00:38 batch_executor 清理
```

### 3.3 关键反证

- **"dump 延迟"是表象**：yf1 / yf2 独立日志 20:59:08 之后**也**没新 act——**dump 延迟无法解释独立日志的静默**
- **Trae 修的"async for"是修对地方**：`ServerStdoutReader` 单线程 drain 解决了**启动后**的 dump 延迟，但**没修启动晚 60s 的根本问题**
- **GUA-048 closed 标错了**：trae 跑 `pytest tests/test_batch_stdout_reader.py` pass 就 closed，**没跑实际批跑验证 dump 延迟 ≤ 5s**

## 4. 修复方向

### 4.1 根因 A：客户端 `mark_game_ready` 写盘慢

**嫌疑路径**（待实测验证）：
1. **V7 引擎冷启动**：`yf1_v7.py` / `yf2_v7.py` 的 `handle_game_start` 触发 V7 引擎首次推理（torch 模型 + 124 维特征），冷启动 1-3 秒
2. **mark_game_ready 写盘**：在 `handle_game_start` 异步**完成后**才调，4 席并发冷启动撞 IO
3. **可能写盘路径有锁**：`batch_executor/client_ready.py:52` 的 `mark_game_ready` 写 `game_ready.json` 是否有文件锁

**修复**：
- 加 `time.monotonic()` 打点到 `lalala_adapter.mark_game_ready` + `yf1_v7.handle_game_start` 入口/出口
- 把 `mark_game_ready` 改成**首条消息到达就写**，不依赖 `handle_game_start` 完成
- 或**异步写盘**：`asyncio.create_task(mark_game_ready_async())` 不阻塞主流程
- 4 席分时启动，避免 4 席冷启动撞 IO

### 4.2 根因 B：ServerStdoutReader 启动晚

**修复**：
- 把 `ServerStdoutReader.start()` 调用从 `executor.py:547`（game_ready 之后）移到 `executor.py:488`（4 席 WS 连接就绪后）**立即启动**
- 加 pytest `tests/test_server_stdout_reader_startup.py`：mock executor，验证 `start()` 在 4 席 WS 就绪后 ≤ 1s 内被调用

### 4.3 关单验收标准

- [ ] **实测 1**：跑 3 局批跑，主日志 4 席 actIndex dump 延迟 ≤ 5s（与 yf1 / yf2 独立日志偏差）
- [ ] **实测 2**：`batch_executor/game_ready.json` mtime 与 `server:96 game_start` 时间偏差 ≤ 10s
- [ ] **pytest 1**：`tests/test_game_ready_timing.py`（mock 客户端，验证 `mark_game_ready` 写盘 < 10s）
- [ ] **pytest 2**：`tests/test_server_stdout_reader_startup.py`（mock executor，验证 `start()` 在 4 席 WS 就绪后 ≤ 1s 内调用）
- [ ] **回归**：M1/M3 批跑 `logs/batch_executor_*.log` 同样 ≤ 5s dump 延迟

## 5. 教训

### 5.1 Trae 的 V 系列教训 V4 复发

V4-V5-V6 时代教训："**训练有'准确率'无'队胜率'**"——只看到指标 pass 就关单，**不端到端跑实测**。  
2026-06-07 复发：**Trae 看到 pytest pass 就关 GUA-048**，**没跑实际批跑验证 dump 延迟**。

**V7 护栏**（2026-06-07 拍板）：**pytest pass ≠ 端到端 pass**。任何关单必须有**实测基线**对照（dump 延迟 / 队胜率 / 决策分布），不能只看单元测试。

### 5.2 dump 延迟 ≠ 真实卡顿

之前 GUA-048 推论"dump 延迟 73s"是错的——**dump 延迟是表象**，**真实卡顿是 4 席真在等**。  
**教训**：**主日志 vs 独立日志的时差**≠**真实事件延迟**。必须用独立日志（yf1_v7 / yf2_v7）+ 服务器时间戳三重对照才能定位真因。

### 5.3 调度时机是隐形根因

ServerStdoutReader 修对了"async for"，但**没修"启动晚 60s"**——因为 b5df0bc 改动**只在 line 547 之后**才生效。**调度顺序的隐性 bug**比代码 bug 更难发现。
