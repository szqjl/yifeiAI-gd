## 一、项目背景与技术路线

自 2026 年1 月起，我以贵平台的离线对战环境为依托，分别开发了两个系列的掼蛋 AI：

### 1.1 M 系列（硬编码决策引擎）

M 系列是**基于规则的决策系统**，不依赖神经网络。核心思路是将掼蛋领域的经验知识编码为若干「Guard」（守卫规则），每条 Guard 对应一个具体的决策场景，例如：

- 牌型保护（不拆炸弹/同花顺/三连对等核心结构出单出对）
- 队友识别与送牌（队友快赢时主动送小牌）
- 对手抑制（对手即将出尽时主动炸断）
- 残局算牌（根据已经出过的牌推算剩余威胁）
- 三带二拆牌保护、接风跟线、让道逻辑等

M 系列最新版本为 **M3**，累计实现 14+ 条 Guard 规则，决策链路为 `Guard 过滤 → 剩余合法动作 → 按优先级选择`。M3 的代码规模约 2,000 行 Python，部署于 `src/m/m3/`。

### 1.2 V 系列（神经网络决策引擎）

V 系列是**基于神经网络的决策系统**，采用行为克隆（Behavior Cloning）路线，以 M3 的胜局牌谱作为训练数据，试图学习 M3 的出牌策略并泛化到未见场景。

V 系列的技术栈包括：

- **组牌引擎**（Grouping Engine）：对手牌进行最优分组（顺子/同花顺/炸弹/三带二/三连对/对子/单张），输出 5 维评分（牌力/手数/回收/灵活/去单化），共 24 维特征
- **BC 模仿学习**：以 1938 样本训练 MLP 模型（2048 → 2048 action space），最高验证准确率 80.88%
- **Guard 壳**：从 M3 移植了 10+ 条规则作为安全护栏（队友保护/对手抑制/残局等），确保 NN 输出不会违反基本牌理
- **决策管线**：组牌引擎特征提取 → NN 输出 → Guard 过滤 → 动作选择

V 系列最新版本为 **V7**，代码规模约 3,500 行 Python，部署于 `src/v/nn/` 和 `src/v/guards/`。目前仍在迭代中，组牌引擎已冻结参数，重点攻关决策链路的实战转化率。

M3 队胜率稳定区间为 **55%–82%**，在绝大多数批跑中碾压 lalala。M3 的强项在于规则覆盖全面，尤其在三带二保护、残局算牌、队友协作方面表现稳健。

## 三、actionList 候选缺失观测

在持续的 V7 批跑和决策链路复盘中，我们发现一个与离线平台 engine 相关的异常现象，在此如实呈报。

### 3.1 问题描述

在相当比例的决策回合中，平台返回的 `actionList` 仅包含 `PASS` 一个选项，但此时玩家手牌中实际存在可压制当前 `greaterAction` 的有效牌型。

该现象我们判断为离线引擎在计算合法出牌候选集时的一个边界条件缺陷，而非主观倾向性问题——同一局内四个席位均由同一 C++ 引擎计算 actionList。

### 3.2 总体统计

在最近 3 局（共 6 副）批跑中，V7 队（yf1 + yf2）共产生 **769 次决策点**，其中：

| 指标 | 次数 | 占比 |
|------|------|------|
| actionList 仅含 PASS（即 len=1） | **205** | **26.7%** |
| 其中：手牌明确可压但平台未给出 | 44 | 21.5% |
| 其中：可能需要炸弹/同花顺压制 | 104 | 50.7% |
| 其中：确实无法压制（PASS 正常） | 57 | 27.8% |

### 3.3 手牌数分布

该异常不限于残局尾牌，在全游戏阶段均有出现：

| 剩余手牌 | 次数 | 占比 |
|----------|------|------|
| ≤ 5 张 | 55 | 26.8% |
| 6–10 张 | 27 | 13.2% |
| 11–15 张 | 71 | 34.6% |
| 16–20 张 | 32 | 15.6% |
| 21+ 张 | 20 | 9.8% |

峰值出现在中盘 11–15 张区间（34.6%），其次为残局 ≤5 张（26.8%）。

### 3.4 greaterPos 分布

当 actionList 仅含 PASS 时，greaterPos（当前最大牌出牌者）的分布表明问题均匀作用于所有对抗关系：

| greaterPos | 次数 | 占比 | 说明 |
|------------|------|------|------|
| 0（yf1·我方） | 21 | 10.2% | 我方出牌 |
| 1（opp1·对手） | 83 | 40.5% | 对手出牌 |
| 2（yf2·我方） | 21 | 10.2% | 我方出牌 |
| 3（opp2·对手） | 67 | 32.7% | 对手出牌 |

### 3.5 典型案例

以下案例均来自实际批跑记录（`game_records_v7/`），原始数据已备份至 `docs/analysis/evidence/`，便于复现校验。

**案例 1：单张（Single）**

```
文件：20260628201953141540 [yf2_v7]-[opponent_1_3]-[4]-[2].json
greaterAction: ["Single", "J", ["DJ"]]
玩家手牌(1张): ["DA"]
actionList: [["PASS"]]
```

手牌仅剩 DA（方块 A），点数 > J，应能出 DA 压制。但 actionList 仅含 PASS。

**案例 2：对子（Pair）**

```
文件：20260628201953682662 [yf1_v7]-[opponent_1_3]-[5]-[2].json
greaterAction: ["Pair", "6", ["H6", "D6"]]
玩家手牌(4张): ["H2", "H2", "D2", "D4"]
actionList: [["PASS"]]
```

持有 3 张级牌 2，可组成对子 22 压制 66，未被识别为合法 Pair。

**案例 3：三张（Trips）**

```
文件：20260628201953682662 [yf1_v7]-[opponent_1_3]-[5]-[2].json
greaterAction: ["Trips", "7", ["S7", "S7", "C7"]]
玩家手牌(4张): ["H2", "H2", "D2", "D4"]
actionList: [["PASS"]]
```

同 Hand 2，3 张 2 可组成 222 压制 777，未被识别。

**案例 4：炸弹（Bomb）**

```
文件：20260628201951214091 [yf1_v7]-[opponent_1_3]-[2]-[2].json
greaterAction: ["Bomb", "7", ["H7", "C7", "D7", "D7"]]
玩家手牌(11张): ["S2", "H2", "C2", "D2", "D6", "HT", "CT", "CK", "DK", "CA", "DA"]
actionList: [["PASS"]]
```

持有 4 张 2（S2, H2, C2, D2），即 2222 炸弹，大于 7777，未被列入候选。

**案例 5：同花顺（StraightFlush）**

```
文件：20260628201953682662 [yf1_v7]-[opponent_1_3]-[5]-[2].json
greaterAction: ["StraightFlush", "5", ["D5", "D6", "D7", "D8", "D9"]]
玩家手牌(25张): ["H2", "H2", "D2", "S3", "S3", "H3", "C3", ...]
actionList: [["PASS"]]
```

25 张手牌可能含有更大同花顺或炸弹，未提供任何除 PASS 外的候选。

### 3.6 模式特征

综合分析 44 例"明确可压但未给出"的案例，呈现以下规律：

1. **与级牌密切相关**：当前对局 curRank=2，几乎所有漏判案例都涉及点数 **2（级牌）**。玩家手中的 2 在形成对子、三张、炸弹时，未被识别为有效的同牌型压制选项。

2. **牌型覆盖广泛**：受影响牌型包括 Single、Pair、Trips、Bomb、StraightFlush，说明问题可能出在点数大小比较或级牌身份识别环节，而非特定牌型的生成逻辑。

3. **对四个席位公平作用**：平台使用同一 C++ 引擎为四个席位独立计算 actionList。但从实际 PASS 率看，不同策略遭遇此问题的频率不同（V7 队 ~61%，lalala 队 ~46%），推测与各 AI 保留的手牌结构有关。

4. **不影响 M3 对 lalala 的优势**：M3 仍能以 ~70% 队胜率碾压 lalala，因为此缺陷对双方公平约束，就像两边都绑了同样重量的沙袋——跑得快的还是快。M3 的策略优势（Guard 完整性/手牌管理/残局判断）足以覆盖这个共同负担。

## 四、数据来源与可靠性

为确保本报告数据可靠：

1. `actionList` 取自平台 WebSocket 原始消息，项目侧 `normalize_action_list()` 仅将 action[2]（牌列表）从平台内部对象转为字符串列表，**未对 actionList 做任何增删或过滤**（代码见 `src/communication/v7_game_recorder.py` L44–57）。

2. 测试时设置 `YF_DEBUG_WS=1`，决策记录器将完整 `greaterAction` 和 `actionList_sample` 写入 game record。

3. 所有案例可复现——牌局记录位于 `game_records_v7/`，`my_decisions[].context` 保存了手牌、actionList 长度及 greaterAction。

4. 典型案例原始牌谱已备份至 `docs/analysis/evidence/`，共 3 个文件（458 KB）。

## 五、影响评估

坦率而言，该问题对 AI 对战的影响程度尚难精确量化，但存在以下潜在干扰：

- **对训练/评测的公平性**：四个席位虽同受限制，但不同 AI 遭遇此问题的频率不同，可能在统计上引入系统性偏差。
- **对决策复盘的误导**：复盘时看到"AI 被迫 PASS"，可能误判为 AI 失误，实际是候选集缺失导致的被迫行为。
- **对级牌=2 场景的特殊影响**：如果缺陷与级牌识别有关，则在 curRank=2 的对局中影响最显著。

## 六、建议排查方向

基于以上观测，我们冒昧建议从以下角度排查离线引擎：

1. **级牌（curRank）的身份识别**：在计算合法出牌候选集时，级牌点数在比较逻辑中是否被正确提升为最大。例如 curRank=2 时，2 应在点数比较中大于 A。

2. **actionList 生成时的过滤条件**：检查是否存在过早过滤候选牌型的逻辑（如某些条件下跳过了对子/三张/炸弹的候选生成），导致合法选项被遗漏。

3. **边界测试覆盖**：建议对 curRank=2~A 分别编写单元测试，覆盖各牌型（Single/Pair/Trips/Bomb/StraightFlush）的压制判断，验证 actionList 的完备性。
