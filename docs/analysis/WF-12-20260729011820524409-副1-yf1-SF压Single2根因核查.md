    Map<Integer, CardInfo> result = new HashMap();

        idx++;

    return result;
}

### 3.3 规则总结：OpenGuanDan 对 Single 跟牌的枚举规则

| greater_action 类型 | 平台枚举的 Single 候选 |
|---|---|
| `Single K`（普通牌） | A + SB + HR + 级牌单张（rankIdx） |
| `Single 9`（普通牌） | T, J, Q, K, A + SB + HR + 级牌单张 |
| `Single 6`（普通牌） | 7, 8, 9, T, J, Q, K, A + SB + HR + 级牌单张 |
| **`Single 2`（级牌！）** | **仅 SB + HR**（不走普通循环，命中 `rankIdx == greaterPoint` 早退） |

**这就是 OpenGuanDan 的特殊设计**：当响应级牌单张（Single rankIdx）时，平台认为**只有 SB/HR 能压**——与掼蛋标准规则（Single 2 是最小、所有 > 2 的牌都能压）不一致。

### 3.4 md[22] 场景：手牌没 SB/HR → 0 个 Single 候选

- yf1 手牌 = `[H2,H2,D4,D6,H7,C7,D7,C7,D8,H9,HT,CT,DT,HJ,DJ,HQ,HK,CK]`

**所以 md[22] actionList=71 不是「漏枚举」，是 OpenGuanDan 平台的特殊规则触发**。

## 4. 根因（三层叠加）

### 4.1 第一层：OpenGuanDan 平台规则（与掼蛋标准不一致）

- `ActionJudgment.getSingle` 命中 `rankIdx == greaterPoint` 早退分支 → 只枚举 SB/HR
- **客户端 AI 没有「Single 4/6/7 等能压级牌单张」的合法候选**——出 D4 会被平台拒绝（不在 actionList）
- 关联 GUA-180（OpenGuandan 漏 Trips K）/ GUA-124（v1006 漏 SF）/ GUA-123 §8（步 76 `actionList_size=2` 漏 SF）

### 4.2 第二层：4 张 7 炸被 core-filter 拦截

代码（`src/v/nn/ultimate_win_rate_engine_v7.py:1794`）：

```
[01:18:21] [UltimateWinRateEngineV7.0] [WARNING] 残局管线命中但被_group_consistency_filter拦截: actIndex=1 cards=['H7','C7','D7','C7'] → 回退GUA-075
```

- 4 张 7 炸 (gid=0, is_core=1.0) 是组牌引擎推荐的 core 牌型
- `_group_consistency_filter`（GUA-069）拦截拆 core 的动作 → actIndex=1 Bomb/7 被删
- 残局 fallthrough 到 GUA-075

### 4.3 第三层：`_recommend_bomb_from_mask` 排序过度偏好 SF

代码（`src/v/nn/ultimate_win_rate_engine_v7.py:5310-5320`）：

```python
def priority(candidate):
    size = len(candidate["cards"])
    strength = 9 if candidate["type"] == ACTION_TYPE_STRAIGHT_FLUSH else size
    return (
        -strength,                        # ← **同花顺永远 strength=9，普通 4 炸 strength=4**
        1 if wild_card in candidate["cards"] else 0,
        -self.RANK_ORDER.get(candidate["rank"], -1),
        tuple(candidate["cards"]),
    )
best = min(candidates, key=priority)
```

**`strength = 9 if SF else size`** → 同花顺 `strength=9` **永远** 大于 普通 4 炸 `strength=4`。

候选列表（core-filter 拦截 4 炸后）：
- 4 张 7 炸 → 被拦截（已删）
- 5 张 Bomb/T → strength=5
- 5 张 Bomb/J → strength=5
- 5 张 Bomb/K → strength=5
- 5+ 张 SF → strength=9 **永远最大**
- 5 张 SF/3/4/6/7/8/9/T → 多种 SF

**`min()` 按 -strength 排序 → SF/9 (actIndex=21) 永远靠前 → 选 SF/9**。

## 8. 建议

### 8.1 GUA-181 建议登记

**GUA-181：`_recommend_bomb_from_mask` 排序未考虑「核心 4 炸被 core-filter 拦截」与「平台非标准枚举」组合场景**

- **当前问题**：
  1. 平台 OpenGuanDan 对级牌 Single 走非标准规则（只给 SB/HR），AI 端无法合法出 Single 4/6/7 压级牌
  2. 残局 `_group_consistency_filter` 拦截组牌引擎推荐的 core 4 炸 → 候选只剩 SF
  3. `_recommend_bomb_from_mask` 排序 SF strength=9 永远最大 → 强推 SF
- **修复方向**：
  - **方向 A**：`_recommend_bomb_from_mask` 加 `_has_only_bomb_family_left` 检测：若普通 Bomb 都被 core-filter 拦截、只剩 SF → 退化为 PASS（不出炸，保 SF 资源给关键轮次）
  - **方向 B**：把 GUA-172 `_recommend_cheapest_bomb_from_action_list` 的「最廉价优先」原则补到 `_recommend_bomb_from_mask` 路径（SF 排序 strength 改为 `min(strength, size)`）
  - **方向 C**：在 `_maybe_recommend_sprint_fire_bomb` 中加「actionList 完整性检测」+「手牌是否有 SB/HR」分支：响应级牌 Single 且无 SB/HR → 不出炸，直接 PASS
- **关联**：GUA-170/172/103/141/091/131/180

### 8.2 不在本 GUA 范围

- **平台 OpenGuanDan 对级牌 Single 的非标准枚举**：客户端无法修复（要平台改 `ActionJudgment.getSingle` 的 `rankIdx == greaterPoint` 分支）。但客户端**可以**识别该场景并退化为 PASS / 出最小非炸动作。
- **同花顺"是否炸弹"语义**：代码已明确，无需新增 GUA。
