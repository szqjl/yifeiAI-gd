# M1/V6 分支开发指南

## 📋 分支概述

本项目使用**双分支并行开发**策略，用于独立训练和对比 M1 系列和 V6 系列的 AI 模型效果。

### 分支说明

- **`m1-dev`**: M1 系列硬编码规则引擎分支（本地开发）
  - 基于当前 `main` 分支创建
  - 包含：`yf1_m1.py`, `yf2_m1.py`, `rule_based_decision_engine_m1.py`
  - 特点：全新的硬编码规则引擎，5阶段细分路由
  - **注意**：由于仓库大小限制，完整历史未推送

- **`m1-dev-clean`**: M1 系列干净分支（当前分支，已推送）
  - 基于当前代码状态创建的干净分支（无历史）
  - 包含所有代码和文档，但不包含模型文件和游戏记录
  - 特点：轻量级，适合远程协作和训练
  - **推荐使用**：用于远程训练和协作

- **`v6-dev`**: V6 系列优化分支
  - 基于远程 `origin/main` 创建
  - 包含：`yf1_v6.py`, `yf2_v6.py` 及相关优化
  - 特点：基于现有架构的优化版本

- **`main`**: 主分支
  - 用于最终合并和发布
  - 根据训练效果决定合并哪个分支

## 🔄 分支切换注意事项

### ⚠️ 重要提醒

**测试不同版本时必须切换分支！**

- 测试 M1：必须在 `m1-dev` 分支运行 `yf1_m1.py`
- 测试 V6：必须在 `v6-dev` 分支运行 `yf1_v6.py`

### 原因

- 不同分支包含不同的代码文件
- `m1-dev` 分支没有 `yf1_v6.py`
- `v6-dev` 分支没有 `yf1_m1.py`
- 共享文件（如 `game_recorder.py`）可能有不同版本

### 切换前检查

```bash
# 查看当前分支
git branch

# 查看未提交的更改
git status

# 如果有未提交的更改，先暂存
git stash

# 切换分支
git checkout <分支名>

# 切换后恢复更改（如果需要）
git stash pop
```

## 🎯 训练和评估

### 模型文件隔离

两个分支的模型文件会自动分开：

- **M1 分支**: `models/bc_model_m1_*.pth`
- **V6 分支**: `models/bc_model_v6_*.pth`

### 训练脚本

建议为每个分支创建独立的训练脚本：

- **M1 分支**: `train_m1.py`
- **V6 分支**: `train_v6.py`

### 评估结果

评估结果建议分开存储：

- **M1 分支**: `evaluation_results/m1/`
- **V6 分支**: `evaluation_results/v6/`

## 🔀 分支合并

### 场景1：M1 效果更好

```bash
# 1. 切换到主分支
git checkout main

# 2. 合并 M1 分支
git merge m1-dev

# 3. 解决冲突（如果有）
```

## ⚠️ 常见问题

### Q1: 切换分支时提示有未提交的更改？

**A**: 先暂存更改或提交更改

```bash
# 方法1：暂存更改
git stash
git checkout <分支名>
git stash pop  # 切换回来时恢复

# 方法2：提交更改
git add .
git commit -m "临时提交"
git checkout <分支名>
```

### Q2: 共享文件（如 game_recorder.py）修改冲突？

**A**: 合并时手动解决冲突

```bash
# 合并时如果有冲突
git merge <分支名>
# 手动编辑冲突文件
# 解决后提交
git add .
git commit
```

### Q3: 误删了分支怎么办？

**A**: 可以从提交历史恢复

```bash
# 查看已删除分支的提交
git reflog

# 恢复分支
git checkout -b <分支名> <提交hash>
```

## 📌 最佳实践

1. **定期提交**：每个分支独立提交，保持提交历史清晰
2. **明确命名**：提交信息明确标注是 M1 还是 V6 的改动
3. **及时合并**：确定效果后及时合并到主分支
4. **备份重要代码**：删除分支前确保重要代码已保存
5. **测试隔离**：测试时确保在正确的分支上
