> **源文档**：[`offline_platform/openguandan_latest/README.md`](../../offline_platform/openguandan_latest/README.md)（OpenGuanDan 完整协议，**本方案唯一真源**）

> **分支**：`v8-dev`（从 `v7-dev` commit `2904c08` 复制，代码与 v7 一致）  
> **目标**：将 V7 客户端从旧 `guandan_offline_v1006.exe`（WebSocket `ws://127.0.0.1:23456/game/{user_info}`）迁移到新 `guandan.exe`（WebSocket `ws://127.0.0.1:8181`），AI 决策引擎 `UltimateWinRateEngineV7` **不改动**。

## 1. 新旧平台差异总表

### 1.1 传输层

| 维度 | v1006（旧） | OpenGuanDan（新） |
|------|-----------|-------------------|
| 可执行文件 | `guandan_offline_v1006.exe` | `guandan.exe`（Windows 原生） / `java -jar guandan-java-1.0.0.jar` |
| 端口 | **23456**（WebSocket） | **8181**（WebSocket）+ **3000**（HTTP 管理） |
| 连接 URI | `ws://127.0.0.1:23456/game/{user_info}` | `ws://127.0.0.1:8181`（统一端点） |
| 多线模式 | 无 | 支持 cluster（`-Dguandan.cluster.mode=true` + workers） |
| 启动参数 | `guandan_offline_v1006.exe N`（N=局数） | `guandan.exe`（无命令行参数，局数由客户端 `CREATE_ROOM.round` 指定） |
| 就绪信号 | 控制台输出 `Ready for connect.` | 嵌入式服务无标准就绪信号（需等待端口监听） |

### 1.2 房间与入座

| 维度 | v1006（旧） | OpenGuanDan（新） |
|------|-----------|-------------------|
| 房间模型 | **无房间概念**：4 客户端连入即占 0/1/2/3 座 | **有房间概念**：需显式 `CREATE_ROOM` → 3 个 `JOIN_ROOM` |
| 座位 | 连入顺序决定（不可选） | `CREATE_ROOM` 可指定 `seatNum`，`JOIN_ROOM` 也可指定 |
| 局数设置 | `exe N` 命令行参数 | `CREATE_ROOM` 的 `round` 字段 |
| 游戏开始 | 连满 4 人自动开始 | 房间满 4 人自动开始 |
| roomId 传递 | 无 | `CREATE_ROOM` 返回 `roomId`，后续客户端 `JOIN_ROOM` 需传入 |

### 1.3 上行消息（客户端 → 服务器）— **最大差异**

| 操作 | v1006（旧） | OpenGuanDan（新） |
|------|-----------|-------------------|
| 出牌动作 | `{"actIndex": N}` | `{"type":"PLAY","data":{"roomId":1,"player":0,"act":["Single","5",["D5"]]}}` |
| 进贡 | `{"actIndex": N}` | `{"type":"TRIBUTE","data":{"roomId":1,"player":0,"act":["tribute","tribute",["D2"]]}}` |
| 还贡 | `{"actIndex": N}` | `{"type":"PAYTRIBUTE","data":{"roomId":1,"player":0,"tributePos":3,"tribute":"S2","act":["back","back",["H2"]]}}` |

**核心变化**：
- 旧平台只发 `actIndex`（下标），服务器端有 actionList 上下文
- 新平台须发送**完整 action 三元组**，且外层包装 `type` + `data`
- 还贡还需回传 `tributePos`（进贡位）和 `tribute`（进贡牌），须与收到的 act 消息值**完全一致**

### 1.4 下行消息（服务器 → 客户端）

**好消息：下行消息结构基本不变。**

| 消息类型 | 变化点 | 详情 |
|----------|--------|------|
| `notify` + `stage=beginning` | 可能新增三等级字段 | 新平台 README 的 `beginning` 示例不含三等级，但 `guandan-java/engine/types.py` 的 `Wire.notify_beginning()` 包含 `curRank`/`selfRank`/`oppoRank`。**需要实测确认。** |
| `notify` + `stage=play` | 不变 | `curPos`/`curAction`/`greaterPos`/`greaterAction` 一致 |
| `notify` + `stage=tribute` | 不变 | `result` 格式一致 `[[进贡位,收贡位,牌]]` |
| `notify` + `stage=anti-tribute` | 不变 | `antiNums`/`antiPos` 一致 |
| `notify` + `stage=back` | 不变 | `result` 格式一致 |
| `notify` + `stage=episodeOver` | 不变 | `order`/`curRank`/`restCards` 一致 |
| `notify` + `stage=gameOver` | 不变 | `curTimes`/`settingTimes` 一致 |
| **`notify` + `stage=gameResult`** | **字段变化** | 见 §1.5 |
| `act` + `stage=play` | 不变 | `actionList`/`handCards`/`publicInfo`/三等级/`indexRange` 一致 |
| `act` + `stage=tribute` | 不变 | `handCards`/三等级/`actionList` 一致 |
| `act` + `stage=back` | 新增字段 | 新增 `tributePos`/`tribute`（旧平台也存在于 act 中，但新平台明确文档化） |

### 1.5 `gameResult` 字段差异（影响批跑对账）

| 字段 | v1006（旧） | OpenGuanDan（新） |
|------|-----------|-------------------|
| 结果 | `victoryNum`: `[2,0,2,0]`（四席各赢几局） | `victory`: `0`（0=座位0+2队胜，1=座位1+3队胜） |
| 附带 | `draws`: `[0,0,0,0]` | `victoryRank`: `["A","K"]`（两队最终等级） |

**兼容要求**：旧 `v7_game_recorder.py` 的 `save_victory_num_shared()` 写 `latest_victory_num.json` 时依赖 `victoryNum[0]` 计算局数；批跑 `executor.py` 的 `_session_games_from_victory_file()` 也读 `victoryNum`。需从 `victory` 反推 `victoryNum` 数组。

### 1.6 stage / 牌型名 / 卡牌编码 — **一致**

| 类别 | v1006（旧） | OpenGuanDan（新） |
|------|-----------|-------------------|
| 所有 stage 名称 | `beginning` `tribute` `anti-tribute` `back` `play` `episodeOver` `gameOver` `gameResult` | 完全一致 |
| 牌型名 (Pattern) | `Single` `Pair` `Trips` `ThreePair` `ThreeWithTwo` `TwoTrips` `Straight` `StraightFlush` `Bomb` `FourKings` `tribute` `back` `PASS` | 完全一致 |
| 卡牌编码 | 2 字符 `{Suit}{Rank}`：`S2` `HA` `DT` `SB`(小王) `HR`(大王) | 完全一致 |
| `actionList` 格式 | `[["PASS","PASS","PASS"], ["Single","5",["D5"]], ...]` | 完全一致（通过 `indexRange` 限定可选范围） |
| 座位与队伍 | 0+2 一队，1+3 一队 | 完全一致 |
| 还贡限制 | 还贡牌 ≤ 10 | 完全一致（README §6.4） |
| 无自动重连 | — | 一致（README §6.3） |

## 2. 进贡/还贡完整流程（专题）

进贡/还贡是上行消息格式差异最大的环节（旧 `actIndex` → 新 `TRIBUTE`/`PAYTRIBUTE` 消息），且还贡需额外回传 `tributePos`/`tribute`。本节给出两端（进贡方 yf1、收贡方 yf2）在同一次进贡→还贡交互中的完整消息序列。

### 2.1 进贡流程（tribute 阶段）

**前提**：上一副结束，非双上 → 产生进贡关系。服务器先发 `notify` 广播进贡关系，再发 `act` 要求进贡方选牌。

**消息序列**（假设座位 0 向座位 3 进贡一张 S2）：

| 序号 | 方向 | 消息类型 | 关键字段 | yf1(seat0) 动作 |
|------|------|----------|----------|-----------------|
| 1 | S→All | `notify` `stage=tribute` | `result: [[0, 3, "S2"]]` | 记录：自己是进贡方（0），给 seat 3 进贡 |
| 2 | S→seat0 | `act` `stage=tribute` | `handCards` / `curRank` / `selfRank` / `oppoRank` / `actionList` / `indexRange` | AI 引擎选 `actionList` 下标 N；`send_action(N)` → 构造 `TRIBUTE` 消息 |
| 3 | seat0→S | `TRIBUTE` | `{"type":"TRIBUTE","data":{"roomId":1,"player":0,"act":["tribute","tribute",["S2"]]}}` | — |

**代码路径**（新平台）：

```
handle_action_request(data)                    # data["stage"] == "tribute"
  ├→ self.last_action_list = data["actionList"]
  ├→ self.last_stage = "tribute"
  └→ engine.decide(...) → action_index
     └→ send_action(action_index)
        └→ self.adapter.tribute_action(self.last_action_list[action_index])
           → ws.send({"type":"TRIBUTE","data":{...}})
```

**与旧平台差异**：
- 旧：`{"actIndex": N}`，服务器自行关联到 `actionList[N]`
- 新：`{"type":"TRIBUTE","data":{"roomId":1,"player":0,"act":["tribute","tribute",["S2"]]}}`，**完整 action 三元组**

> **注意**：进贡 `act` 消息**不含** `tributePos`/`tribute` 字段（只有还贡 act 有），所以 `handle_action_request` 中 stage=tribute 分支不需要提取这两个字段。

### 2.2 抗贡流程（anti-tribute 阶段）

**消息**：

| 序号 | 方向 | 消息类型 | 关键字段 |
|------|------|----------|----------|
| 1 | S→All | `notify` `stage=anti-tribute` | `antiNums: 2` / `antiPos: [0, 2]` |

**与旧平台一致**：仅 notify 通知，无需客户端回复。不涉及上行消息改造。

### 2.3 还贡流程（back 阶段）

**前提**：进贡完成，收贡方收到进贡牌后需还一张牌（≤10）。

**消息序列**（假设 seat 3 还 seat 0 一张 H2）：

| 序号 | 方向 | 消息类型 | 关键字段 | yf2(seat3) 动作 |
|------|------|----------|----------|-----------------|
| 1 | S→All | `notify` `stage=back` | `result: [[3, 0, "H2"]]` | 记录：seat 3 还 seat 0 一张 H2 |
| 2 | S→seat3 | `act` `stage=back` | `handCards` / `curRank` / **`tributePos: 0`** / **`tribute: "S2"`** / `actionList` / `indexRange` | **提取 `tributePos` 和 `tribute`**；AI 引擎选 `actionList` 下标；`send_action(N)` → 构造 `PAYTRIBUTE` 消息（回传 tributePos/tribute） |
| 3 | seat3→S | `PAYTRIBUTE` | `{"type":"PAYTRIBUTE","data":{"roomId":1,"player":3,"tributePos":0,"tribute":"S2","act":["back","back",["H2"]]}}` | — |

**代码路径**（新平台，关键新增逻辑标 ★）：

```
handle_action_request(data)                    # data["stage"] == "back"
  ├→ self.last_action_list = data["actionList"]
  ├→ self.last_stage = "back"
★ ├→ self.last_tribute_pos = data["tributePos"]     # ★ 提取进贡位，还贡发送时回传
★ ├→ self.last_tribute_card = data["tribute"]        # ★ 提取进贡牌，还贡发送时回传
  └→ engine.decide(...) → action_index
     └→ send_action(action_index)
        └→ self.adapter.pay_tribute_action(
               self.last_action_list[action_index],
★              self.last_tribute_pos,
★              self.last_tribute_card
           )
           → ws.send({"type":"PAYTRIBUTE","data":{"roomId":1,"player":3,
                           "tributePos":0,"tribute":"S2",
                           "act":["back","back",["H2"]]}})
```

**与旧平台差异**（最大风险点）：
- 旧：`{"actIndex": N}`
- 新：`{"type":"PAYTRIBUTE","data":{"roomId":1,"player":3,"tributePos":0,"tribute":"S2","act":["back","back",["H2"]]}}`
- **`tributePos` 和 `tribute` 必须与第 2 步 act 消息中的值完全一致**（README §3.5 Note）

### 2.4 进贡/还贡阶段 notify 消息处理

两个 notify 消息的下行格式与旧平台一致，**不需要改动解析逻辑**：

| stage | 旧平台字段 | 新平台字段 | 处理 |
|-------|-----------|-----------|------|
| `tribute` | `result: [[0, 3, "S2"]]` | 一致 | 不变 |
| `anti-tribute` | `antiNums` / `antiPos` | 一致 | 不变 |
| `back` | `result: [[3, 0, "H2"]]` | 一致 | 不变 |

### 2.5 进贡/还贡适配器方法对照

```
adapter 方法                stage     作用                          发送消息 type
─────────────────────────────────────────────────────────────────────────────
tribute_action(act)        tribute   进贡方选牌发送                  TRIBUTE
pay_tribute_action(...)    back      收贡方还牌发送（★ 含回传字段）   PAYTRIBUTE
```

> **总结**：进贡只需发送完整 action 即可（同 play）；还贡是唯一需要**从下行 act 提取字段并回传**的环节。方案中 `last_tribute_pos`/`last_tribute_card` 缓存 + `PAYTRIBUTE` 消息构造覆盖了这一路径。

## 3. 迁移步骤

### 阶段 A：新增协议适配层（低风险，不影响旧代码）

**目标**：在不改现有 `yf1_v7.py` 主体逻辑的前提下，新增一个新平台的消息适配模块。进贡/还贡适配方法已在 §2.5 定义，本节聚焦房间管理和连接层。

#### A1. 新增 `src/communication/new_platform_adapter.py`

封装 OpenGuanDan 协议的所有消息构造逻辑：

```python
# 伪代码框架

class OpenGuanDanAdapter:
    """OpenGuanDan 新平台协议适配器"""
    
    def __init__(self, user_id: str, room_id: int = None, seat_num: int = 0):
        self.user_id = user_id
        self.room_id = room_id
        self.seat_num = seat_num  # myPos，初次连接时确定
    
    # --- 房间管理 ---
    def create_room(self, round_count: int) -> dict:
        """构造 CREATE_ROOM 消息"""
        return {
            "type": "CREATE_ROOM",
            "data": {
                "userId": self.user_id,
                "round": round_count,
                "seatNum": self.seat_num
            }
        }
    
    def join_room(self, room_id: int) -> dict:
        """构造 JOIN_ROOM 消息"""
        return {
            "type": "JOIN_ROOM",
            "data": {
                "userId": self.user_id,
                "roomId": room_id,
                "seatNum": self.seat_num
            }
        }
    
    # --- 动作发送 ---
    def play_action(self, act_tuple: list) -> dict:
        """构造 PLAY 消息（从 actionList[selectedIndex] 生成）"""
        return {
            "type": "PLAY",
            "data": {
                "roomId": self.room_id,
                "player": self.seat_num,
                "act": act_tuple
            }
        }
    
    def tribute_action(self, act_tuple: list) -> dict:
        """构造 TRIBUTE 消息"""
        return {
            "type": "TRIBUTE",
            "data": {
                "roomId": self.room_id,
                "player": self.seat_num,
                "act": act_tuple
            }
        }
    
    def pay_tribute_action(self, act_tuple: list,
                           tribute_pos: int, tribute_card: str) -> dict:
        """构造 PAYTRIBUTE 消息"""
        return {
            "type": "PAYTRIBUTE",
            "data": {
                "roomId": self.room_id,
                "player": self.seat_num,
                "tributePos": tribute_pos,
                "tribute": tribute_card,
                "act": act_tuple
            }
        }
```

**关键属性保存**：
- `self.last_tribute_pos`：收到 `act`·`stage=back` 时从消息中提取 `tributePos`，还贡发送时回传
- `self.last_tribute_card`：收到 `act`·`stage=back` 时从消息中提取 `tribute`，还贡发送时回传

#### A2. 更新 `websocket_manager.py` — 连接层

**现有代码**：URI 构建在 `websocket_manager.py` 中硬编码 `ws://127.0.0.1:23456/game/{user_info}`。

**改动**：

| 项 | 旧值 | 新值 |
|----|------|------|


`platform="openguandan"` 时，`connect()` 额外步骤：

4. 将 `room_id` 保存到 context 供后续 `send_action` 使用

#### A3. 房间协调机制

**问题**：新平台需要 roomId 在 4 个客户端间传递。旧平台不关心此值。

**方案（推荐：文件传递）**：

```

```

1. connect WebSocket
2. 发送 `CREATE_ROOM`
3. 收到 `{"type":"CREATE_ROOM","code":200,"data":{"roomId":X,...}}` → 写 `tmp/.v8_room_id`

yf2 / lalala3 / lalala4（seat 1-3）：
1. 轮询 `tmp/.v8_room_id`（超时 30s）
2. 读取 roomId
3. connect WebSocket
4. 发送 `JOIN_ROOM`
5. 进入消息循环

### 阶段 B：修改客户端主体逻辑

#### B1. `yf1_v7.py` / `yf2_v7.py` — `send_action` 改造

**当前**（`yf1_v7.py:454` 附近）：
```python
def send_action(self, action_index: int):
    msg = {"actIndex": action_index}
    ...
```

**改造后**（保留旧路径，新增新平台分支）：
```python
def send_action(self, action_index: int):
    if self.platform == "openguandan":
        act_tuple = self.last_action_list[action_index]  # 需缓存 actionList
        if self.last_stage == "tribute":
            msg = self.adapter.tribute_action(act_tuple)
        elif self.last_stage == "back":
            msg = self.adapter.pay_tribute_action(
                act_tuple,
                self.last_tribute_pos,
                self.last_tribute_card
            )
        else:  # play
            msg = self.adapter.play_action(act_tuple)
    else:
        msg = {"actIndex": action_index}
```

**必要条件**：在 `handle_action_request()` 中缓存当前 actionList：
```python
self.last_action_list = action_data["actionList"]
self.last_stage = action_data.get("stage", "play")
if self.last_stage == "back":
    self.last_tribute_pos = action_data["tributePos"]
    self.last_tribute_card = action_data["tribute"]
```

```python
def wait_for_server_port(port=8181, timeout=60):
    """轮询探测端口是否监听"""
    import socket
    for _ in range(timeout):
        try:
            s = socket.create_connection(('127.0.0.1', port), timeout=1)
            s.close()
            return True
        except:
            time.sleep(1)
    return False
```

#### C2. `batch_executor/restart_manager.py` — 客户端启动协调

新增 roomId 协调：yf1 先启 → 等待 `tmp/.v8_room_id` 写入 → 再启 yf2 + lalala。

## 6. 兼容性设计原则

1. **双平台并存**：通过 `--platform v1006|openguandan` 参数切换，不破坏旧 V7 工作流。`v7-dev` 分支仍可正常跑旧平台。

2. **下行消息解包层不动**：`unwrap_platform_payload()` 当前已支持嵌套结构检测，新平台不需额外改动。

3. **录像格式不变**：`game_records` JSON 格式保持不变（actionList 三元组、stage 名、`gameResult` 兼容后统一为 `victoryNum` 格式）。

4. **日志文件名区分**：v8 批跑日志加 `_v8` 后缀（如 `batch_executor_v8_*.log`），避免与 v7 混淆。

5. **逐阶段开关**：新增 `config.yaml` 的 `platform` 键，全局或按客户端指定。
