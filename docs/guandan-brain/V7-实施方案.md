## 1. 硬约束（升格后）

### 1.1 治理硬约束

- **IDecisionProvider v1.0**（[`src/contracts/decision_provider.py`](../../src/contracts/decision_provider.py)）**不可变更**：`decide(message: ActMessage) -> int` + `player_id: int`
- **M-V 分层**（治理 §2）：V7 = Layer 1 智能体；**不得**修改 M 系列通信/状态/记录契约
- **V 默认冒烟 OFF**（治理 §7.2）：V7 改造**不阻塞** M 日常迭代；改 M 的 PR **不**要求跑 V7 回归
- **模型权重**（治理 §6）：`*.pth` 不进 Git，走 COS `models/v-nn/`；Git 仅保留 manifest 指针（按 `模型文件管理方案.md` 实施）
- **Commit 规范**（治理 §8.1）：V7 提交前缀 `[V-nn-v7]`
- **分支策略**（治理 §4）：V7 开发在 `v7-dev`，评审+测试通过后合并 `m-dev`

### 1.2 升格硬约束（2026-06-04 评审升格）

**不再将 M3 作为 V7 底座。** 边界（白/黑名单）：

| 维度 | 允许 | 禁止 |
|------|------|------|
| **代码 import** | `from src.contracts.decision_provider import IDecisionProvider` | `from src.m.m3 import ...`（任何 M3 内部模块） |
| **数据复用** | M3 批跑产出的 `game_records/*.json`（`my_decisions`）作 BC 训练 teacher 标签（离线、单向） | 实时调用 M3 引擎生成标签；改写 M3 录牌格式以服务 V7 |
| **协议/字段** | 读 v1006 平台 act 消息 | 改 v1006 协议以迁就 M3 |
| **录牌** | V7 自己的 V7-internal 录牌 | 调 M3 录牌链路（`game_recorder`） |
| **架构定性** | M3 = `IDecisionProvider` 契约的**实现方之一** | M3 = V7 底座 |

**子 Agent 评审事实性补充（2026-06-04）**：

| **`src.train.*`（历史 M1/M2 训练代码）** | 临时引用（GUA-037a/b 实施前） | GUA-037a 关单时须替换为 `src/v/nn/training/`，GUA-039 关单时 V7-internal 训练管道全替代 |

## 9. 外部评审意见（OpenCode Agent · 2026-06-04）

### 9.1 关键路径压缩比偏高

串行合计 7.4 迭代压到 4–5 迭代，依赖图假设 GUA-037b（LSTM）与 GUA-038（BC 训练）完全并行。037b 的 actionList 15 维拼接层若不卡 038 入口则可行，但建议在 Phase 1 中期 checkpoint 验证一次并行假设是否成立。

### 9.2 Phase 3 GPU 算力未说明

DMC + PPO 自对弈训练隐含 GPU 需求（特别是 039b PPO 多 Actor 并发），但文中未评估所需显存与训练时长。低端 GPU 上 1.5 迭代可能不足 039a 收敛。建议在 Phase 0 补充 GPU 最低规格与预计训练时长。

### 9.3 风险 #6「M3 数据多样性不足」fallback 未落实

§5 风险 #6 提出「rule-based 自对弈数据扩展训练集」作为 M3 录牌多样性不足的 fallback，但该数据生成器没有对应的 GUA 或责任人。若 M3 仅对 lalala 录牌，分布可能偏窄，影响 BC 训练泛化性。建议在 Phase 0 或划入 GUA-039a 范围落实此 fallback。

### 9.4 测试超时隐患

§2 中各 GUA 验收要求 pytest 40+ case，其中 GUA-038「BC 训练 1 epoch」作为单元测试可能超时（训练循环 + 模型保存约数分钟）。建议标记 `@pytest.mark.slow` 分离慢测试，CI 中默认跳过。

**总体结论**：方案根基扎实，上述 4 条属优化建议而非阻塞项。建议接受，按 handoff「下一步唯一动作」先行登记 ISSUES 后开工 GUA-041。
