## 零、一句话定位

**让 V8 的组牌方案从「开局/手牌变化时跑一次静态最优」升级为「每个决策回合都能按对手出牌模式重新评估与调整」**：当对手连续出某牌型、而当前 plan 把回应牌锁死在其他结构里时，系统能生成「针对性重组」候选、量化重组后的牌力损失，并结合队友获胜收益决定是否执行——掼蛋有时需要牺牲自己成全队友。**动态组牌有牌力门禁：超强牌不启用，仅强牌以下才需要，且强牌细分强牌+ / 强牌 / 强牌-（§二）**；同时须联动领出，感知队友需要什么牌型并重组出对应结构（§3.5）。

## 一、问题本质

### 1.1 静态 plan 不感知局面

当前组牌方案生命周期：

```
decide(521)
 └ _run_grouping_engine(557)
     └ hand_hash 变化才重跑（v7:1466-1468）
     └ enumerate_groupings → best_plan + Top3（grouping_engine.py:2440）
     └ 只保留 best_plan → _card_mask/_group_type_map/_group_members（v7:1480）
     └ Top3 其余候选丢弃
```

**关键事实（全部已核实）**：

| 项 | 现状 | 位置 |
|----|------|------|
| plan 触发 | 仅手牌 hash 变化才重跑；**对手出牌不改我方手牌 → plan 永不因对手模式变化** | `v7:1466-1468` |
| 候选保留 | `enumerate_groupings` 返回 Top3，`_run_grouping_engine` 只用 best_plan | `grouping_engine.py:2440`、`v7:1480` |
| 中局触发 | `_check_midgame_triggers` 只按手牌降量阈值（15/10/5）+ 拆核标记，仍等 hash 自然重跑 | `v7:2847-2882` |
| 拆核成本 | `_group_break_cost` 静态表：SF/Bomb=1000、复合子组=600、straight/trips=500 | `v7:2019-2032` |
| 推荐器压牌 | 只从 plan groups 找同型组（Pair/Trips/Straight），plan 无该型 → None → 改炸/PASS | `v7:5250/5671` |
| 拆对拦单 | 已有零散加分（GUA-157/166：无自然单才拆对、拆 9-J 对优先），但仍是「加分」非「重组」 | `v7:3754-3784` |
| 对手信号 | `memory_tracker.get_inferred_opponent_types` / `rule_card_counter.can_opponent_suppress` 已存在，**未反哺组牌决策** | `memory_tracker.py:630`、`rule_card_counter.py:74` |

**结论**：plan 是「当前手牌」的静态最优划分，不感知「对手正在打什么、队友需要什么」。对手连续出单时，V8 的单张被锁进对子/顺子/三带二里；要回应就只能靠 heuristic 加分「鼓励拆」，但拆哪个、拆完整副牌还顺不顺、值不值得，没有统一框架。

### 1.2 三个子问题

局面感知动态组牌 = 三个子问题的统一回答：

1. **触发（Trigger）**：什么时候该重新评估当前 plan？
2. **候选（Candidate）**：重组该生成哪些「应对性方案」？
3. **决策（Decide）**：重组代价（牌力损失）与收益（压制对手 / 成全队友）如何权衡？

## 二、动态组牌限定条件（牌力分层门禁）【用户 ①】

**超强牌不启用动态组牌；仅强牌以下才需要；强牌细分强牌+ / 强牌 / 强牌-。**

### 2.1 牌力档位定义（复用现有信号，不另造）

V8 已有两套牌力信号，直接作为门禁输入：

| 现有信号 | 输出 | 位置 |
|----------|------|------|
| `_score_power` | `power_score`（牌力分，用于角色定位） | `grouping_engine.py:1379` |
| `_score_plan_v2` → `plan.score` | 四维加权总分 → `score_tier`（天胡/好牌/尚可/偏弱/烂牌） | `grouping_engine.py:1603/1564` |
| `determine_role` | `role`（超强主攻 ≥7 / 主攻 4-6 / 助攻 1-3 / 超弱 <1） | `grouping_engine.py:1544` |

档位映射（评审可调阈）：

| 用户档位 | 映射依据（建议） | 动态组牌策略 |
|----------|------------------|--------------|
| **超强牌** | `score_tier == "天胡"`（score ≥0.50）或 `role == "超强主攻"`（power ≥7） | **不启用**——牌力已碾压，静态 plan 最优，重组是多余损耗 |
| **强牌+** | `score_tier == "好牌"`（0.40-0.50）或 `role == "主攻"` 上沿（power 5-6） | 启用低频触发（仅对手连续同型 ≥3 / 队友 close），可拆仅限低价值结构（对子/顺子/附牌） |
| **强牌** | `score_tier == "尚可"`（0.30-0.40）或 `role == "主攻"`（power 4） | 默认全触发；可拆低价值结构 + 复合子组 |
| **强牌-** | `score_tier == "偏弱"`（0.20-0.30）或 `role == "助攻"`（power 1-3） | 全触发 + 激进：以配合队友/送牌为优先，可容忍拆掉高价值结构（除 SF/Bomb 硬核） |
| **超弱牌** | `score_tier == "烂牌"`（<0.20）或 `role == "超弱"`（power <1） | 触发面最大，但以「尽快送队友 / 消耗炸弹扛线」为目标，不追求保结构 |

### 2.2 门禁规则

1. **门禁判定时点**：每个决策回合 `decide()` 入口，用**当前 plan 的 `score_tier` + `role`**（若尚未组牌则用最新一次 `_score_power`）判定档位，一次判定该回合动态组牌是否开启。
2. **硬边界不随档位放宽**：无论哪档，拆 SF/Bomb core 仍否决（GUA-108 语义保留）；只是「低价值结构 vs 高价值结构」的拆核容忍度随档位放宽。
3. **不启用 ≠ 不压制**：超强牌档关闭的是「重组」，现有拆对拦单等 heuristic 照常工作；只是不因对手模式去改动 plan 本身。
4. 新档位**不新增常量**：复用 `determine_score_tier` / `determine_role` 已有阈值，仅在其上定义组合规则。

## 三、硬边界（评审必认）

1. **禁止**写成「看到单就拆对、看到顺就拆三连对」的牌例特判（`stage_0_1`/`stage_2` 或 heuristic 加分支）；落点必须是「候选生成 + 统一代价评估」框架。
2. **禁止**形成「逢压制必拆结构」退化：拆 SF/Bomb core 仍严格禁止（保留 GUA-108 停手条件 ③ 语义）；拆低价值结构（对子/顺子/三带二附牌）须经代价评估。
3. **复用既有评分**：牌力损失用现有 `_score_power`（`grouping_engine.py:1379`）+ `_score_plan_v2`（`:1603`）重算，不另造评分体系。
4. 新增行为不得降低 83.3% 队胜率 KPI（净盘批跑护栏）+ 针对性 pytest 回归全绿。
5. 队友获胜权衡需显式建模：掼蛋是 2v2，「牺牲自己牌力成全队友头游」是合法且高价值选择，不是「尽量不拆」。
6. **限定门禁先行**：任何动态组牌逻辑必须先过 §二 牌力档位门禁，未过门禁的档位（超强牌）不产生重组候选。

## 四、四要素框架

### 3.1 触发（Trigger）——何时重估 plan

在现有「手牌 hash 变化重跑」之外，新增**局面感知触发**。候选触发条件（须评审裁剪）：

| 触发类型 | 信号来源 | 说明 |
|----------|----------|------|
| **对手出牌模式** | 本回合 `greaterAction` + 历史最近 N 手 `play_history` | 对手连续 ≥2 手同一牌型（Single/Pair/Straight…）→ 该牌型是当前争夺焦点，值得为它重组 |
| **对手压制窗口** | `memory_tracker.get_inferred_opponent_types` / `rule_card_counter.can_opponent_suppress` | 对手当前打 Single 且我方无自然单 → 触发「拆结构出单」候选 |
| **队友 close** | `endgame_preprocessor` 的 `teammate.is_close`（≤5 张） | 队友即将走完 → 触发「送牌型」候选（牺牲自己结构成全队友） |
| **中局阈值** | 现有 `_check_midgame_triggers`（15/10/5 张） | 保留，但让「重跑」真正发生在阈值触发时，而非等 hash |
| **我方 core 已被拆** | `_core_broken_since_regroup` | 已有标记，重跑时按新局面生成候选 |

**设计点**：触发后不是「重新跑一次同样的静态枚举」，而是带着「当前争夺牌型」的上下文重新生成候选（见 3.2）。

### 3.2 候选（Candidate）——重组成什么

两个层面：

**(a) 保留多 plan 不再丢弃**：`enumerate_groupings` 已返回 Top3（`grouping_engine.py:2440`），`_run_grouping_engine` 应缓存全部 Top3，供决策时按局面选用（方案 C 基础，改动最小）。

**(b) 针对性重组候选**：当触发命中（对手连续 Single + 我方无自然单）时，对当前手牌生成「拆出目标牌型」的重组候选。关键思路——**不是全手牌重组，而是「局部重划 + 重新评分」**：

1. 目标牌型 T（如 Single/Pair/Straight）→ 从当前 plan 中找出所有「可贡献给 T 的结构」（含子组）；
2. 对每个候选结构生成「拆它 → 组 T → 剩余牌重划」的重组方案；
3. 每个重组方案用 `_score_plan_v2` 重新评分，得到 `new_score`；
4. 与当前 plan 的 `score` 对比 → **牌力损失 delta**。

示例（用户场景）：手牌 `10,10,J,J,Q,Q,K,K,A`，当前 plan 把 `1010JJQQ` 锁进三连对。
- 候选 A：拆三连对出 `10-J-Q-K-A` 顺子压对手 8-Q → 剩余 `10,J,Q,K,A` 重划 → 重评分；
- 候选 B：拆三连对出对子/单张压对手 → 同样重评分；
- 候选 C：保持 plan 不变（PASS）→ 对比三者 delta。

**注意**：重组候选的生成应复用组牌引擎现有的「结构贡献」逻辑（`_build_consecutive_structure_press` 已会从 `pair_in_three_pair` 重建三连对，`v7:5489`），本质是把它从「从 plan 子结构重建」扩展为「从手牌全局找可拆结构重建」。

### 3.3 代价量化（Cost）——重组后牌力下降多少

**用现有评分函数重算 delta**，不另造体系：

```
delta = plan_score(当前) - plan_score(重组后)   # 四维加权总分差（_score_plan_v2）
power_delta = _score_power(当前) - _score_power(重组后)  # 纯牌力差（可解释性）
```

`_score_plan_v2` 四维：牌力 0.5 + 手数 0.3 + 回收 0.1 + 灵活性 0.1（`grouping_engine.py:1632-1638`）。重组后手数可能下降（拆 3 轮结构组 1 轮压牌）→ rounds_score 上升；但牌力可能下降（拆了对子/顺子）→ bomb_score 下降。**delta 由评分自动综合，不是人拍脑袋**。

额外提供**解释性指标**（供 trace/日志）：
- 拆了哪个 core/子组（复用 `_group_break_cost` 表）
- 手数变化
- 单张残渣数变化

### 3.4 决策权衡（Decide）——值不值得，含为队友牺牲

这是「动态组牌」区别于「鼓励拆牌加分」的核心。统一权衡函数：

```
exec_weight = current_control_gain + teammate_win_gain - plan_loss - core_break_penalty
```

| 项 | 含义 | 信号 |
|----|------|------|
| `current_control_gain` | 压住对手这手牌的即时收益 | 对手是否在冲刺（剩张数）、greaterVal 高度、能否夺回牌权 |
| `teammate_win_gain` | **成全队友获胜的收益** | `teammate.is_close`（≤5 张）+ 队友前序牌型（`_teammate_last_trick_type`）+ 送出的牌型队友能否接 |
| `plan_loss` | 重组牌力损失 | 3.3 的 delta |
| `core_break_penalty` | 拆 SF/Bomb core 的硬罚 | 拆核即否决（保持禁止） |

**关键理念（掼蛋 2v2 牺牲语义）**：
- 如果 `teammate.is_close` 且重组送出的牌型能让队友一手走完 → `teammate_win_gain` 应显著高于 `plan_loss`，允许「牺牲自己结构」；
- 如果对手冲刺、重组能压住 → `current_control_gain` 高，允许拆低价值结构；
- 如果重组纯属拆结构但既压不住对手也帮不了队友 → 否决，保持 plan。

**与 GUA-109（候选并存+统一评分）的关系**：GUA-109 已在组牌层建立「保未来结构 vs 拆结构换当前夺权」并存 + 评分比较（closed_in）。本框架把同一理念**扩展到推荐器/决策层**，并显式加入「队友获胜」这一 2v2 特有的牺牲维度。

### 3.5 领出联动 + 队友需求感知（Lead-Feed）【用户 ②】

动态组牌不只服务「压对手」，还服务「**我方领出时给队友喂什么牌型**」。用户问题：「动态组牌后必须辅助领出后出什么牌型？如何感知队友需要什么牌型？」

#### 3.5.1 队友需求感知：已有真源（**注意残局/中期边界**）

V8 已有「队友需要什么牌型」信号，**但必须区分阶段**——**精确「需求感知」真源只在残局（队友剩 1-5 张）**；中期（剩 ≥6 张）只有「总量引导」，无需求牌型感知（见 3.5.4）。

| 信号 | 适用阶段 | 输出 | 位置 |
|------|----------|------|------|
| `assist_prefer_for(remaining)` | **仅残局**（1-5 张） | 队友剩 N 张 → 允许投喂的牌型列表（1→Single、2→Pair、3→Trips/Pair/Single、4→Pair/Single、5→Straight/TWT/Single）——**单一真源** | `assist_prefer_table.py:11` |
| `assist_is_close(remaining)` | **仅残局** | 队友 1-5 张 → 接近头游 | `assist_prefer_table.py:26` |

#### 3.5.2 领出联动设计

```
我方领出 & 队友需要牌型集 P =
   残局（队友剩 1-5）：assist_prefer_for(teammate.remaining)   [真源]
   中期（队友剩 ≥6）：§3.5.4 中期感知（队友出牌历史牌型统计 + 需求置信）
  → 若 plan 已有 P 中牌型的组 → 走现有领出逻辑（不重组）
  → 若 plan 无 P 中牌型（如队友剩5张需要 Straight/TWT，plan 全是 Pair）：
      → 生成「重组出 P 中某牌型」的候选（复用 §3.2 针对性重组）
      → 用 §3.3 delta 量化损失
      → 过 §3.4 权衡（teammate_win_gain 主导）
      → 选出的重组 plan 交给现有领出消费点（stage_assist_feed / Q2 / GUA-202）
```

- 目标牌型 T 的来源是 **P 集合并集**（`assist_prefer_for` 优先序第 1 位优先，第 2/3 位备选），而非「压对手」场景的对手牌型。
- **队友末手牌型补强**：若 `_teammate_last_trick_type` 非 None（队友刚打过某型），说明队友手里该牌型可能已不多，需结合 `assist_prefer` 综合；以 `assist_prefer` 为主、last_trick 为辅。
- **优先级**：领出场景下重组候选与压对手场景**同池评分**（同一 §3.4 权衡函数），只是 `teammate_win_gain` 在领出送牌时权重更高。

#### 3.5.3 与牌力门禁的关系

- 领出送牌重组同样受 §二 档位门禁约束：**强牌+ / 强牌** 档仅在队友 close（1-5 张）时允许为送牌重组；**强牌- / 超弱** 档领出即以送队友为首要目标，允许更激进拆结构。
- 超强牌档仍不启用（牌力碾压，自己快走更划算，送牌反而拖慢自己）。

#### 3.5.4 中期感知：队友剩 ≥6 张时「需要什么牌型」（用户追问补齐）

**现状缺口（已核实）**：`assist_prefer_for` / `assist_is_close` / `endgame_preprocessor.teammate` **只在队友剩 1-5 张激活**。中期（≥6 张）V8 只有：
- `_feeding_target_types`：按剩张映射**总量引导**（10/9→TWT/Straight、8/7/6→Single/Pair）——只回答「喂大牌还是小牌」，不回答「队友缺哪种牌型」；
- `_teammate_last_trick_type`：仅单手记忆，接风用；
- `teammate_cover_confidence`：承接置信，非需求。

**中期无法精确感知的原因**：残局「剩 5 张→喂 Straight/TWT」能精确，是因为张数=剩余结构约束；中期（剩 6-20 张）队友手牌结构未知，任何「队友需要 X」都是推断。

**中期感知设计（新信号，允许新建）**：用「队友出牌行为」推断需求倾向，产出**需求置信度** `teammate_demand[牌型] → 0..1`：

| 信号 | 来源 | 推断 | 置信 |
|------|------|------|------|
| **队友领出牌型** | `_teammate_last_trick_type` 扩展为**近 N 手牌型历史**（`_teammate_recent_tricks` deque，N=5） | 队友主动领出某型 = 该型是其「想走」牌型 → 我方领出喂该型让队友接 | 领出次数 /N，越高越可信 |
| **队友跟压成功牌型** | 同上历史 + `greaterPos==teammate` 且非领出 | 队友接得住该型 = 手里有该型资源 → 喂该型队友能续 | +0.2/次 |
| **队友连 PASS 牌型** | 对手连续出同一种牌型 T 时，队友对序列内每次应对均 PASS | 队友缺该型/压不过 → **不要喂该型** | 负向，抑制 |
| **剩张总量引导** | 现有 `_feeding_target_types` | 中期大牌型（10/9→TWT/Straight）或小牌型（8/7/6→Single/Pair）倾向 | 基础 0.3-0.5 |
| **队友冲刺窗口** | `_scenario_3_teammate_sprinting`（7-8 张）+ `teammate_cover_confidence` | 队友进入冲刺 → 需求置信整体抬升 | +0.2 |

**判定式（草案）**：

```
demand(T) = 0.5 * 队友领出 T 频率 + 0.3 * 队友接住 T 频率 − 0.4 * 连PASS抑制(T)
          + 0.2 * _feeding_target_types 命中 + 冲刺加成
连PASS抑制(T) = 1 if (对手连续同型 T 序列内队友累计 PASS ≥2) else 0
选 T* = argmax demand(T)，且 demand(T*) ≥ 0.5 才触发「领出送牌重组」
```

（T = 目标牌型 Target type，见下）

**喂牌目标 P 不直接等于 T\***：须再过 **§3.5.4.1 相位门**，再过 **§3.5.4.2–§3.5.4.4 强信号覆盖**（若命中），再进入 §3.5.2。

#### 3.5.4.1 顺/夯/对投喂相位门（用户定稿，对齐 `03_card_interactions` + 传牌「打吐」）

对 **Straight / ThreeWithTwo（TWT）/ Pair** 三类易「打吐」的主路单独计数，决定「同型投喂」还是「换路投喂」：

| 计数 | 定义 |
|------|------|
| `play_count(Straight)` | 本副队友非 PASS 出牌中，牌型为 `Straight` 的累计次数（领出+跟压均计） |
| `play_count(TWT)` | 同上，`ThreeWithTwo` |
| `play_count(Pair)` | 同上，`Pair`（含领出后连续套对） |

**阈值（统一）**：**≤3 同型相位；>3（第 4 次起）换路相位**。  
依据：顺/夯为用户 v6 定稿；对子对齐传牌误传「把队友打吐」——「连续套**三四对**已经把对子轮次打尽」→ 与 3 对齐，**第 4 次起不再喂对**。

**主路判定**：取 `raw_main = argmax demand(T)`（或仅当 Straight/TWT/Pair 领先时进入本门）。

| 相位 | 条件 | 投喂策略 P | 技能依据 |
|------|------|------------|----------|
| **同型相位** | 主路为 Straight/TWT/Pair 且对应 `play_count ≤ 3` | `P = {主路}` | 主路尚未走尽，送桥接风 |
| **相克/换路** | 主路 Straight 且 `play_count > 3` | `P = {Single, Pair}`；**忌** TWT | `03_card_interactions` 队友顺子传牌 |
| **相克/换路** | 主路 TWT 且 `play_count > 3` | `P = {Trips, Single, Pair}`；**忌** Straight | 同上队友三带二传牌 |
| **换路（打吐）** | 主路 Pair 且 `play_count > 3` | `P = {Single}` 优先；次选换路（按 `demand` 次高且非 Pair）；**忌再喂 Pair** | 传牌「把队友打吐」 |

**伪码**：

```
if raw_main == Straight:
    P = {Straight} if play_count(Straight) <= 3 else {Single, Pair}      # >3 禁 TWT
elif raw_main == ThreeWithTwo:
    P = {ThreeWithTwo} if play_count(TWT) <= 3 else {Trips, Single, Pair}  # >3 禁 Straight
elif raw_main == Pair:
    P = {Pair} if play_count(Pair) <= 3 else {Single}  # >3 打吐：改喂单/换路，禁对
else:
    P = {raw_main}  # Single/Trips 不走本门
```

**边界说明**：

- 阈值 **3** 为本副累计次数（非滑动窗口）；新副重置。批跑后可调，改阈须登记 ITERATIONS。
- **≤3 含第 3 次**：第 1～3 次仍可同型投喂；**第 4 次起**切相克/换路。
- 对子「过多」口径：**>3 即过多**（与顺/夯同一数字；技能「三四对」取上沿一致）。
- 相克/换路相位仍受连 PASS 抑制：若 `P` 中某型被压死，取 `P` 内次优，**不**退回已忌讳型。
- 残局（队友剩 1–5）**不走本门**，仍以 `assist_prefer_for` 为准。
- 本门只约束**喂队友**；压对手「同型∪相克反打」另条。
- **例外**：若命中 §3.5.4.2「到顶收回」，即使 `play_count(TWT)≤3` 也**不得**因同型相位继续优先喂 TWT；若命中 §3.5.4.3 / §3.5.4.4「能打不能收」，按相克轮次调整 demand/P（见各节）。

#### 3.5.4.2 「小夯被压 + 顶夯收回」强信号覆盖（用户确认，对齐相生相克）

**场景（用户例）**：队友先发 `333+44` → 敌方压 `888+44` → 队友再用 `AAA+55` 压制收回。

**技能依据**（[`03_card_interactions.md`](../knowledge/skills/04_common_skills/03_card_interactions.md) §三、[`01_passing_skills.md`](../knowledge/skills/03_assist_attack/01_passing_skills.md) 记牌/到顶）：

1. **三带二到顶**：收回手的三头已到 **A（或等价顶三）**，或经典「带 AA 到顶」→ **再有一手 TWT 的概率很低**。
2. **小夯被压 + 顶夯收回**：两手夯之间的点数区（约 **5～K / 7～K**）更可能还有 **Straight 或 ThreePair**，不是「夯还很多、继续喂夯」。

**判定（须同时满足）**：

| # | 条件 | 说明 |
|---|------|------|
| 1 | 队友曾**领出或主动打出**一手较小 TWT（记为 `twt_low`） | 例：`Trips=3` + 小对 |
| 2 | 敌方（或对方）以**同型更大 TWT**压过该手 | 例：`888+44` |
| 3 | 随后队友以 **顶档 TWT** 再压回（记为 `twt_top`） | **顶档定义（v1）**：三头点数为 **A**；或带牌为 **一对 A（AA）**（经典「888AA 到顶」）。级牌作逢人配组成的顶三头视同顶档 |

**命中后推断与喂牌**：

| 项 | 结论 |
|----|------|
| 再有 TWT？ | **判低**（`demand(TWT)` 强抑制，建议 −0.5 或直接剔除出喂牌优先集） |
| 中间区间 | 抬升 `demand(Straight)`（可选 +0.3）；可记 `mid_interval_hint = (twt_low.trips_rank , twt_top.trips_rank)` 供后续记牌 |
| 喂牌 P 覆盖 | **忌再优先喂 TWT**；`P` 改为优先 `{Straight, Single, Pair}`（顺优先；无顺则单/对试探）。**覆盖 §3.5.4.1 同型相位**——即使 `play_count(TWT)≤3` 也适用 |
| 残局 | 队友剩 1–5 仍以 `assist_prefer_for` 为准；若 prefer 含 TWT，到顶覆盖仅作**降权**不硬禁（避免与精确剩张冲突） |

**伪码**：

```
if detect_small_twt_pressed_then_top_reclaim(teammate_history):
    demand(TWT) -= 0.5          # 或置 0
    demand(Straight) += 0.3
    # 覆盖相位门同型喂夯：
    if P == {ThreeWithTwo} or ThreeWithTwo in P:
        P = {Straight, Single, Pair}   # 顺优先
```

**锚点例**：`333+44` → 敌 `888+44` → 队友 `AAA+55` → **不判队友一定还有 TWT**；领出宜喂顺/单/对，不宜再喂夯。

**实现位置**：与 `_teammate_recent_tricks` 同处扫描近手序列（至少保留最近 2～3 手 TWT 事件）；产出标志 `twt_topped_out=True` 供相位门后覆盖。

#### 3.5.4.3 「小顺被压接不回 → 上方三头/夯」强信号（用户确认，对齐算牌）

**技能原文**（[`04_calculation_skills.md`](../knowledge/skills/04_common_skills/04_calculation_skills.md) 注意事项 4；同见 [`03_card_interactions.md`](../knowledge/skills/04_common_skills/03_card_interactions.md) §三.3）：

> **千万不要认为打了顺子就不要三带二**：如果一个人出了 `23456`，被人家 `34567` 压住了接不回去，那他手上剩下的牌 **7 以上的三个头概率很高**。

**与相邻节的关系**：

| 节 | 模式 | 勿误判 | 应推断 |
|----|------|--------|--------|
| 3.5.4.2 | 小夯被压 + **顶夯收回** | 勿以为夯还多 | 再有 TWT 低；中间偏顺 |
| 3.5.4.3 | 小顺被压 + **接不回** | 勿以为打过顺就无夯 | 顺顶之上 **Trips/TWT 概率高**（§3.5.4.4 右支落地） |
| 3.5.4.4 | **能打不能收**总则 | 勿只盯已出同型 | 收不回的那路 → **相克轮次**仍在 |

**判定（须同时满足）**：

| # | 条件 | 说明 |
|---|------|------|
| 1 | 队友曾打出一手 **Straight**（记为 `st_low`） | 例：`23456`（或任意较低行程顺） |
| 2 | 敌方（或对方）以**同型更大 Straight** 压过 | 例：`34567` |
| 3 | 队友**未能**用更大顺（或同型）接回——该圈对压顺选择 **PASS**，或之后直至牌权转移前未再出更大 Straight | 「接不回去」 |

**命中后推断与喂牌**：

| 项 | 结论 |
|----|------|
| 勿抑制 TWT | **禁止**因 `play_count(Straight)≥1` 就认定「无三带二」；取消/回滚「出过顺 → 降 demand(TWT)」类启发式 |
| 上方三头 | 抬升 `demand(Trips)` 与 `demand(TWT)`（建议各 +0.3）；记 `trips_above_hint = st_low.high_rank + 1`（例：顺顶为 6 → **7 以上**三头/夯） |
| 喂牌 P 覆盖 | 若相位门因「打过顺」走向 `{Single, Pair}` 且 **仅因出过顺** 忌夯——**本信号否决该忌讳**：允许/优先将 **TWT / Trips** 纳入 P（尤其队友主攻、剩张仍适合五张型时）。与 §3.5.4.1 相克相位（`play_count(Straight)>3`）并存时：**相克相位仍忌「打无收的小夯」**，但**不**禁止合理 TWT；优先序可为 `{TWT, Trips, Single, Pair}` |
| 残局 | 队友剩 1–5 仍以 `assist_prefer_for` 为准；本信号作加分提示 |

**伪码**：

```
if detect_small_straight_pressed_no_reclaim(teammate_history):
    # 勿：打了顺 → 不要夯
    demand(TWT) += 0.3
    demand(Trips) += 0.3
    straight_no_twt_fallacy = False
    trips_above_hint = rank_after(st_low.high_rank)  # e.g. 6 → 7+
    # 覆盖「因出过顺而忌夯」：
    if Straight in recent and ThreeWithTwo not in P:
        P = P ∪ {ThreeWithTwo, Trips}   # 或重排优先 TWT/Trips
    flag straight_pressed_unreclaimed = True
```

**锚点例**：队友 `23456` → 敌 `34567` → 队友 PASS（接不回）→ **7 以上三头/TWT 概率高**；我方领出**可考虑喂夯/三**，切勿死抱「他出过顺所以只喂顺/单对」。

**实现位置**：同 `_teammate_recent_tricks`；扫描「Straight 出牌 → 被更大 Straight 压 → 队友未接回」；产出 `straight_pressed_unreclaimed=True` + `trips_above_hint`。

#### 3.5.4.4 「能打不能收，必有相克轮次」（用户确认，对齐算牌总则）

**技能原文**（[`04_calculation_skills.md`](../knowledge/skills/04_common_skills/04_calculation_skills.md) 288–289；同见 [`03_card_interactions.md`](../knowledge/skills/04_common_skills/03_card_interactions.md) 「能打不能收」）：

> - 打出小三带二 (`ThreeWithTwo`) 却**收不回来**，手中大概率有顺子 (`Straight`)
> - 打出小顺子 (`Straight`) **收不回来**，手中大概率有三带二 (`ThreeWithTwo`)

**总则**：某路「能打不能收」≠ 该路已打光；更常表示手里留着**相克轮次**（顺↔夯）在守/在等。

**双向落地**：

| 支路 | 触发 | 推断 | 喂牌 P | 落地节 |
|------|------|------|--------|--------|
| **小夯收不回** | 队友出较小 TWT → 被更大 TWT 压 → **未**用更大/顶夯接回（PASS） | `demand(Straight)` ↑；勿继续优先同型喂夯 | `P` 优先 `{Straight, Single, Pair}` | **本节（左支）** |
| **小顺收不回** | 队友出较小 Straight → 被更大 Straight 压 → 接不回 | `demand(TWT/Trips)` ↑；勿因出过顺忌夯 | 见 §3.5.4.3 | **§3.5.4.3（右支）** |

**与 §3.5.4.2 的区分（同为「小夯被压」，结果不同）**：

| | §3.5.4.2 到顶收回 | §3.5.4.4 左支「收不回」 |
|--|-------------------|-------------------------|
| 队友后续 | 用 **顶夯** 压回 | **PASS / 未接回** |
| 含义 | 夯路见顶，再有 TWT 低 | 夯路打不出头，**相克顺**概率高 |
| 标志 | `twt_topped_out` | `twt_pressed_unreclaimed` |

二者互斥：同一序列若最终顶夯收回，只走 4.2；若始终收不回，走 4.4 左支。

**判定（左支，须同时满足）**：

| # | 条件 | 说明 |
|---|------|------|
| 1 | 队友打出一手较小 TWT（`twt_low`） | 例：`333+44`、较小三头 |
| 2 | 敌方以更大 TWT 压过 | 例：`888+44` |
| 3 | 队友**未**接回（该圈 PASS，或直至牌权转移前未出更大 TWT） | 「收不回来」；**且未**命中 §3.5.4.2 顶夯收回 |

**命中后（左支）**：

| 项 | 结论 |
|----|------|
| 相克轮次 | 抬升 `demand(Straight)`（+0.4 建议）；`demand(TWT)` 同型续喂降权（−0.2，弱于到顶 −0.5） |
| 喂牌 P | **忌再优先喂小夯**；`P` 优先 `{Straight, Single, Pair}`（顺优先） |
| 覆盖 | 即使 `play_count(TWT)≤3`，同型相位也不应机械继续喂 TWT |

**伪码（左支）**：

```
if detect_small_twt_pressed_no_reclaim(teammate_history):  # 且非 twt_topped_out
    demand(Straight) += 0.4
    demand(TWT) -= 0.2
    flag twt_pressed_unreclaimed = True
    if P == {ThreeWithTwo} or (ThreeWithTwo in P and play_count(TWT) <= 3):
        P = {Straight, Single, Pair}   # 能打不能收 → 喂相克顺
```

**锚点例**：队友 `333+44` → 敌 `888+44` → 队友 **PASS**（收不回）→ **大概率有顺**；领出宜喂顺/单对，不宜继续喂夯。  
（对照：若队友改为 `AAA+55` 收回 → 走 §3.5.4.2，不是本节。）

**实现位置**：与 4.2/4.3 同处扫描；先判顶夯收回（4.2），否则判夯收不回（4.4 左支）；顺收不回复用 4.3。产出 `can_play_cannot_reclaim_type ∈ {TWT, Straight, None}`。

**「连 PASS」的观测口径与阈值**（用户定稿：全轮观察 + 对手连续同型触发）：

- **T 的定义**：**目标牌型（Target type）**——我方领出时想喂给队友 / 想判断队友需求的那类牌型，取值 `Single / Pair / Trips / Straight / ThreeWithTwo`；`demand(T)` 对每个 T 分别计算，取最高者 T*。
- **观测锚点**：**对手连续出同一种牌型 T**。当对手连续 ≥2 手出同一牌型（如连续 2 手 Single、连续 2 手 Pair、连续 2 手 TWT、连续 2 手 Straight），该牌型即当前场上焦点。
- **触发与阈值**：在「对手连续同型 T」的序列内，队友对该序列**每次应对均 PASS**，**累计到第 2 次 PASS 即触发**判定「队友对 T 无需求/接不住」，`demand(T)` 施加 −0.4 抑制。
  - **≤1 次 PASS 不判**：0~1 次都算噪声——可能是策略性让牌（等队友/敌人继续）、可能是手里有 T 但太小压不过、可能想保存结构，均非「缺 T」。
  - **对手换牌型 → 计数重置**：连续同型序列中断（对手改出其他牌型 / 我方或队友接管）后，该 T 的 PASS 计数归零，需重新累计。
- **与领出/接住信号的互斥**：同一 T 若队友曾领出或接住过（正向信号），则连 PASS 抑制不与正向叠加判死——`demand(T)` 由各项加权综合，正向仍可拉回。
- **强化（可选，草案不做）**：若可判断队友「明明能压却让过」（如队友刚出过 ≥T 的牌型、或剩张多时仍 PASS），则单次即可置信；需手牌/牌力推断支持，超出草案范围。
- **实现**：`_update_teammate_last_trick`（v7:2886）处扩展——维护 `opponent_consecutive[T]`（对手当前连续同型计数，换型即重置）与 `teammate_pass_on_sequence[T]`（该序列内队友 PASS 数）；`teammate_pass_on_sequence[T] ≥ 2` 即触发抑制。全轮观察，无固定窗口过期。

**与残局的关系**：队友剩 5 张及以下切回 `assist_prefer_for` 真源（精确覆盖）；`_teammate_recent_tricks` 历史可作为残局辅助（如队友刚打过 Single 且剩 3，仍优先 Single）。

**实现位置**：在 `_update_teammate_last_trick`（v7:2886）处扩展——同一处已能拿 `greaterPos/greaterAction`，把「单手记忆」升级为「近 N 手 deque + 牌型计数」，不新增决策入口。

#### 3.5.5 中期感知与动态组牌的关系

- 中期领出时：`demand` → `raw_main` → **§3.5.4.1** → **§3.5.4.2–4.4（若命中）** → `P`；若 plan 无 `P` 中牌型 → 重组出 P 内优先型。
- 与压对手场景同一 §3.4 权衡；**喂型取自最终 P**。
- 覆盖示例：
  - 队友前 3 次打顺 → 可同型喂顺；第 4 次起改喂单/对。
  - 队友 `333+44` 被压后 `AAA+55` 收回 → 不再优先喂 TWT，抬顺（§3.5.4.2）。
  - 队友 `333+44` 被压后 **PASS** → **能打不能收**，偏顺，喂顺/单对（§3.5.4.4）。
  - 队友 `23456` 被 `34567` 压住接不回 → 偏夯/三，可喂夯/三（§3.5.4.3 = 4.4 右支）。
