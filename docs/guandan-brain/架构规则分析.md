## 一、调用架构对比

### lalala：单入口 + 按类型分发

```
rule_parse()  ← 唯一入口（L1354）
  ├── stage=="play" + 被动  → passive()
  │     ├── 优先: one_hand()（numofmy≤10，精确残局匹配，L981-986）
  │     └── 按 curAction[0] 分发:
  │           Single() / Pair() / Trips() / ThreeWithTwo() /
  │           ThreePair() / TwoTrips() / Straight() / Bomb()
  └── stage=="play" + 主动  → active()
        └── 第一句/主动情况专用逻辑
```

**调用深度：3层**（rule_parse → passive/active → 具体方法）

---

### M1：多入口 + 分层路由

```
decide()
  → StageRouter（按 rest 阈值路由到 5 阶段之一）
      → Handler（12 个之一，按主动/被动 + 阶段组合）
          → PrioritySystem._calculate_base_scores()
                → priority_map['active'/'passive'] 硬编码字典
          → should_protect()  ← 5 条规则分数累加
          → CardValueSystem
```

**调用深度：6-8层**（decide → Router → Handler → PrioritySystem → should_protect，含 fallback）

## 二、规则嵌入方式对比

### lalala：精确 if-then，无抽象层

**代表例子** — `Single()` 被动处理队友保护（L81-85）：

```python
if numofnext <= 4 or (numofpre <= 3 and numofpre>=1):
    if (myPos+2)%4 == greaterPos and curVal >= max_val:
        return 0    # 队友是对家，当前单张≥最大牌 → PASS
    if (myPos+2)%4 == greaterPos and curVal>=15 and numofnext!=1:
        return 0    # 队友是对家，级牌≥15，下家未剩1张 → PASS
```

**精确在哪里：**
- 边界是整数比较 `numofnext <= 4`（不是"小"、不是阈值、不是分数）
- 队友关系用位置运算 `(myPos+2)%4 == greaterPos`（不是推理、不是查表）
- 牌值用 `curVal >= max_val` 精确比较（不是"大"的概念）

---

### M1：分数积累 + 可配置优先级

**代表例子** — `should_protect()` 队友保护（`strategy_engine.py:196-211`）：

```python
# 用多个规则各自打分，累加超过阈值就算保护
score = 0
if 上家剩牌多: score += 0.3
if 出的牌大: score += 0.5
if 我要剩下对子: score += 0.4
if 队友剩牌少: score += 0.3
...
return score >= 2.25   # 动态阈值，没有精确边界
```

**代表例子** — 两手出完判断（`_calculate_base_scores():503`）：

```python
if card_count >= len(handcards) * 0.7:  # 70% 近似
    scores.append(float(priority_map.get('two_hand_complete', 900)))
```

lalala 对应逻辑（精确匹配）：
```python
# utils.py one_hand() 中
if len(i) + len(j) == len(handcards):   # 精确匹配，不是有牌率
    return ...
```

## 三、M1 与 lalala 的设计模式对比

**核心差异不是优劣之分，而是设计哲学不同：**
- lalala：**精确 if-then**，边界用整数比较控制，无抽象层
- M1：**分数积累 + 软阈值**，用概率近似替代精确匹配，代价是 GUA-022 暴露的问题

| 维度 | lalala | M1 |
|---|---|---|
| 边界控制 | `numofnext <= 4` 精确整数比较 | `score >= 2.25` 浮点阈值 |
| 队友判断 | 位置运算 `(myPos+2)%4`，单向 | 需推理多个规则累加 |
| 调用链深度 | 3层 | 5层+ |
| 可测试性 | if 分支可单独断言 | 分数阈值需集成测试 |
| 语义保留 | 「对家剩4张只出大1」完整保留 | 分数丢失「只出大1」的精确语义 |
| GUA-022 根因 | 无（精确条件无此问题） | `should_protect()` 阈值积累无法精确表达「只出大1」 |

### M1 过度设计的证据

1. `PrioritySystem` 把「打得过对子」映射成 `pair=300`，损失了「对子在这个位置能不能打」的信息
2. `should_protect()` 5条规则累加，8轮调参 GUA-022 仍未解决
3. `one_hand()` 的精确匹配（`len(i)+len(j)==len(handcards)`）被替换成 `card_count >= 70%` 宽松近似
4. **M1 的「共享组件」架构对硬编码规则是过度设计** — 规则越精确，越不应该抽象成组件

### M1 唯一胜过 lalala 的地方

- **阶段划分**：M1 有 5 阶段（opening/mid_early/mid_late/eg_early/eg_late），lalala 只有主动/被动/残局 3 类
- **代码组织**：M1 分散在多个文件便于定位，lalala 1411行单文件难以维护

---

## 四、结论

**M1 的问题不是架构错，而是架构和目标不匹配。**

- `PrioritySystem` + `should_protect()` 这套设计对 **V4/V5/V6（数据驱动/神经网络）** 有意义，因为那些版本的规则边界本来就需要软化
- 但对 **M1（硬编码规则引擎）** 来说，把精确 if-then 规则抽象成优先级分数是反模式 — 在 GUA-022 上直接暴露：调 8 轮参调不出「队友剩4张只出大1」，lalala 一个 `numofnext <= 4` 的整数比较就解决了

## 五、两份评审的核心结论

### opencode（资深架构师视角）

**结论**：lalala 技术路径更优。M1 的 6-8 层调用链、分数积累抽象层、大量 fallback 兜底，使硬编码规则不如 lalala 的纯 if-else 直接可靠。

**6个具体差距（均精确到行号）**：

1. **M1 存在大量无意义降级兜底**：Handler 末尾的 "Final fallback: returning first non-PASS" 证明策略逻辑经常失效（phase_handlers.py 多处）
2. **卡牌一致性检查过度**：stage_router.py:197-245 的 `_validate_action_cards()` 在 Opening 阶段"验证失败也保留"（phase_handlers.py:161-162），徒增复杂度
3. **队友保护评估成本高但收益低**：strategy_engine.py:196-211 遍历 5 个 ProtectionRule 求和，lalala 一行 `if (myPos+2)%4 == greaterPos and curVal>=max_val: return 0`（action.py:83）就解决了
4. **主动出牌逻辑弱**：lalala 有 rankfour/rankthree/ranktwo/rankone 跨牌型动态比较，M1 只有牌型内优先级常量
5. **两手出完判断用 70% 近似**：而非 lalala 的 `len(i)+len(j)==len(handcards)` 精确匹配
6. **炸弹选择无 lalala 式最小代价算法**：utils.py:297-367 的 choose_bomb() 含级牌加成/同花顺特殊处理，M1 没有等价实现

**6条可执行追赶建议**：
- P0：移植 `combine_handcards` + `choose_bomb`
- P0：context 补齐 `pass_num`/`numofnext`/`numofgreaterPos`
- P1：先 Single/Pair 被动移植 + 与 protection 层去重
- P1：active 优先级链替换固定分数
- P2：模板方法整理样板（移植后做）
- P3：验证代码精简（最后做）

---

### cursor（独立 AI 评审视角）

**结论**：方向正确，表述过绝对。M1 是「有框架、缺 lalala 级细规则」，而非「空壳」。

**关键修正**：
- M1 有 `TeammateProtectionStrategy`（strategy_engine.py:213）并行于 Handler 内嵌规则，两套语义未对齐可能互相打架
- M1 `_handle_single_passive` 还有 excess_singles/拆对/级牌压制（L642-729），能力被低估
- `EnhancedPrioritySystem` 对 Bomb 有威胁/风险因子加权（enhanced_priority_system.py:384-441），差距应限定为默认 PrioritySystem
- 建议5"删验证"风险偏高，应改为"验证下沉到 decide() 入口 + warn"

**自评置信度**：🔥🔥🔥🔥（非常认真）
- 对照 8 个源文件抽样验证，rg 验证 M1 缺失维度声明，识别 2 处绝对化表述、3 处 M1 既有能力被低估

## 六、综合结论

**技术路径对比**：

| 维度 | lalala | M1 |
|---|---|---|
| 调用深度 | 3层 | 6-8层（含 fallback） |
| 规则精确度 | 精确 if-then（`numofnext<=4`） | 分数积累（`score>=2.25`） |
| 队友保护 | 内嵌牌型分支，语义对齐 | ProtectionStrategy + Handler 两套可能冲突 |
| 炸弹选择 | choose_bomb() 最小代价 | 仅阶段降权，无牌间择优 |
| 扩充性 | 加规则 O(1) 修改 | 加规则 O(n) 修改 + 多层可能覆盖 |
| 可观测性 | 差（单文件） | 好（结构化日志+验证） |

**M1 真正的问题**：不是架构错，而是架构和目标不匹配。`PrioritySystem` + `should_protect()` 对 V 系列有意义，对硬编码规则的 M1 是过度设计——把精确 if-then 规则抽象成分数，在 GUA-022 上直接暴露。

**追赶优先级**（综合 opencode + cursor 交叉评审，详见 `reviews/架构规则分析_OPENCODE.md` 和 `reviews/架构规则分析_CURSOR.md`）：
1. P0：`combine_handcards` + `choose_bomb`（独立可测，源码：lalala `utils.py:13` / `utils.py:297-367`）
2. P0：context 补齐 `pass_num`/`numofnext` 等维度字段（`stage_router.py:369-423` 缺失 `pass_num`，对照 lalala `action.py` 使用确认）
3. P1：Single/Pair 被动规则移植 + 与 ProtectionStrategy 去重
4. P1：active 优先级链替换（影响大，需 eval 把关）
5. P2：Handler 间重复代码模板化（移植后做）
6. P3：验证代码精简（最后做）
