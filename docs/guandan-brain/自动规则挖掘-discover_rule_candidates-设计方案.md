## 零、一句话定位

**从批跑牌谱（botzone 为主）的败招集合自动归纳「情形 → 动作」候选规则**：标记败招 → 决策点特征化 → 简化枚举挖掘 → 输出候选清单，供人裁决 + 三闸验证（静态三指标 / 自对弈出现率 / 回归护栏）。

**解决的问题**：规则补丁迭代（缝合怪）三宗罪——① 加规则效率低（每 GUA 手写 if-else 特例）；② 收益递减（近期都是边界 case）；③ 规则冲突（6086 行引擎几十个 gate 布尔串接，改一条赌不破坏前 120 条）。本脚本把「人看牌谱总结规则」的归纳步骤自动化，产出的候选规则与现有 Guard/Heuristic 体系同构，可直接进同一套可测试、可回滚、可解释的框架。

## 一、背景与核心认知

### 1.1 规则缝合怪的本质问题

- **决策 = 几十个硬 gate 的布尔串接**（`_group_consistency_filter`、`_group_break_cost`、`_action_breaks_core`…）。新规则在手工裁定「我优先还是你优先」，冲突靠人工仲裁。
- **端到端 BC/RL 已证伪**（V5 匹配率 0%、V7 argmax collapse）——掼蛋是不完全信息 + 队友 + 组牌，纯 NN 走不通。
- **规则本身是两年积累的资产**（V7Dan 90.5%、V8 83.3% 队胜率），不是包袱——本方案不替代规则，只自动化「新规则的发现」。

### 1.2 核心认知一：规则是「归纳」出来的，不是「发明」出来的

当前「看到败招 → 找出共性 → 手写成 if-else」= 人在做**错误驱动规则归纳**（error-driven rule induction）。这个归纳步骤可自动化：

```
① 自动标记败招（check_endgame_solver 已能做确定性检测）
② 败招归纳（机器取代"人看牌谱"）→ 频繁模式挖掘共同前提 → 候选规则
③ 回归验证（决定要不要保留）
```

**为什么 NN 学不到新规则**：候选集评分 NN 只能学「已表达成特征的偏好」。但「对手剩 1 张、且我拆对子能送队友」这种全新情形，特征空间里根本没有——**真正的新规则必须先被「发现」，才能被「学习」**。发现靠挖掘，不靠梯度。

### 1.3 核心认知二：候选质量验证不依赖「复现情形」

**致命约束**：掼蛋 108 张随机分发，某情形在单副出现的概率极小；Botzone 每 match = 1 副（`scores=[0,3,0,3]` 即副结果），lalala 批跑每批几十副。**「开规则 vs 关规则」的 A/B 根本碰不到几次情形X，统计上无意义。**

**因此删掉「回 lalala 批跑验证候选规则」环节**，改用三闸模型：

| 闸 | 验证对象 | 方式 | 依赖复现？ |
|----|---------|------|-----------|
| **① 静态离线三指标** | 规则是否正确 | support / conflict / coverage（全部历史牌谱静态可算） | **否** |
| **② 自对弈池出现率** | 规则是否值得留 | 自对弈几百副，统计情形X出现率 | **否**（用池子替代碰运气） |
| **③ 回归护栏** | 规则是否闯祸 | 净盘批跑，确认 KPI（83.3%）不降 | 否（护栏不要求复现） |

**关键洞察**：check_endgame_solver 的 R1/R3/R4 已经是「确定性败招检测」——验证的是单步逻辑错误存在与否，与整副牌分布无关，**零复现即可跑**。候选规则的验证同理：先静态判正确性，再统计价值，最后护栏防破坏。

## 二、数据流设计（双数据源）

```
Botzone 发现败招（WF-13）──→ ① 候选发现（本脚本, botzone.log 为主源）
game_records_v8（V8 自对弈池）──→ ② 候选验证（静态三指标 + 回归护栏）
                                    └── 自对弈池本身 ──→ ③ 出现率 + 事后统计挖掘（b 路线）
```

### 2.1 为什么发现和验证分开

| 数据源 | 有副收尾？ | 可重建副胜率/名次？ | 决策链信息密度 | 角色 |
|--------|-----------|--------------|---------------|------|
| `logs/v8_vs_botzone_*.log` | ❌ 无 `restCards`/`episodeOver`，仅 match 级 `scores` | ❌ | ✅ 完整 `history`/`greater`/`hand_self`/`actionList`，单文件 471 play request / 666 回复 | **① 候选发现**（高信息密度对局，挖「新情形→动作」） |
| `game_records_v8/*.json` | ✅ `game_info`/`actions`/`my_decisions` 全字段 | ✅ `result.order`（出完顺序）→ 名次；`victoryNum` → 得分 | ✅ **148 文件 = 37 副 V8 vs V8 自对弈 × 4 视角**（20260729 批次），`actions` 可重建四家手牌 | **② 候选验证 + b 路线事后统计**（回归 A/B、名次归因必须用它） |

> **WF-13 强约束**：Botzone 只写 `logs/v8_vs_botzone_*.log`（无 game_records），结论只追加 `ITERATIONS.md`。本脚本对 botzone 数据只做**只读解析**，不新增落盘要求。
> **v4 数据源事实修正**：此前误标 `game_records_v8` 为「lalala 148 副」。实测该目录 148 个 JSON 为 **37 副 V8 vs V8 自对弈 × 4 视角**（`seat_players` 全为 `yf1/yf3/yf2/yf4_v8`，对手标识 `opponent_1_3`=队B / `opponent_0_2`=队A，`game_id` 时间戳 20260729）。每副 `victoryNum` 组合 3 种、`order` 组合 16 种——名次与得分分布健康，非恒定空跑。

### 2.3 解析可行性实测（2026-08-10 已通过）

用真实日志 `logs/v8_vs_botzone_20260809_152013.log`（572KB）验证「botzone 日志 → 决策点 → 败招检测」全链路：

| 验证项 | 结果 |
|--------|------|
| 副（match）数 | 22 个，全部有完整 27 张手牌 |
| 决策点 | 471 play request，其中我方回复 328 条（含 129 PASS）|
| 编码解码 | 复用 `botzone_adapter.bz_to_v8_card`（0-107 整数 → V8 字符串牌），`history` 解码成功 |
| greater 提取 | 每 request 最后一个非空 response 可作待压牌（已见 Single/ThreePair/Bomb 等） |
| curRank | 每副可提取（已见 2/J/9，非恒 "2"） |
| 手牌重建 | 按我方回复扣减，27→0 正确 |
| 败招检测 | R1/R4 在 72 个残局决策点（手≤10）完整跑通，0 命中（与 lalala 148 副方向一致） |

**解析陷阱清单**（正式脚本必须处理）：
1. `hand=[...]` 与 `cards=[...]` 是 **Python repr（单引号）**，须用 `ast.literal_eval`，不是 `json.loads`
2. `play request raw` 里是真 JSON（双引号），用 `json.loads`；且 history 元素可能是 dict（`{"player","response"}`）或纯 list
3. PASS 回复格式为 `cards=PASS`（无列表），须单独处理
4. req(471) vs rep(328) 缺口是**对手行动的 request**（轮不到我方回复），属正常结构，非解析缺陷
5. 我方回复在 `决策:` 行（`GUA-075 推荐`行含 actIndex 但非执行流，须过滤）

**对设计的两个影响**：
- **Q1（解析器缺口）已解决**：`botzone_adapter.py` 的 `bz_to_v8_card` 是现成资产，在其上加一层日志解析即可，无需新写编码表。
- **Q2（败招正样本趋近于零）确认存在**：botzone 72 个残局决策点 **0 个败招命中**。三指标挖掘的统计基础仍薄弱，须在 §九 风险应对中处理（扩样本 / 降阈值 / 改挖掘目标）。

### 2.4 b+A 路线可行性实测（2026-08-10 已通过）

选定 b 路线（事后统计败招）+ A 定义（状态级「同情形」= 我方手牌规模 + greater 牌型 + 点数）。用 37 副自对弈池（yf1 视角，918 决策点）验证「同状态键 → 不同动作」的反事实对照是否存在：

| 验证项 | 结果 |
|--------|------|
| 决策点总数 | 918（37 副 yf1 视角） |
| 状态键总数 | 523（hs + greater 牌型 + greater 点数） |
| **动作分歧桶** | **94 个（45% 决策点），含 >1 种动作**——反事实对照真实存在 |
| 分歧桶样例 | `hs=4 LEAD` 9 副 9 种动作（Bomb/Single/...）；`hs=26 greater=Single[B]` 11 副 PASS vs 1 副 Single[R]（该压不压型） |
| 四家手牌重建 | `actions` 出牌 + `restCards` = 108 张精确还原（seat1/3 restCards 与出牌零误差对上） |
| 名次 ground truth | `result.order` 出完顺序 → 名次；我方队名次 9 种组合，分布健康 |

**结论**：b+A 路线成立——A 状态键下确有跨副「同键不同动作」对照，可做「同状态 → 名次/得分差异」事后统计。

**管线污染点（正式脚本须处理）**：
1. `hs=None`/`hs=27` 桶混入 `tribute`/`back` 动作（非 play 阶段）→ **① 切片时按 `stage=='play'` 过滤**，只留我方出牌决策
2. `my_decisions` 含四视角重复（每副 4 份）→ 默认只取 `yf1_v8` 视角（或 `--player` 指定），避免同副重复计数
3. A 状态键的「手牌规模」取 `context.handCards_size`（实时值），不用 `numofplayers`（静态整副）

## 三、特征字典（③ 核心，全部对齐已有字段，零新增采集）

每个决策点提取（可空则置 `null`）：

| 特征 | 来源 | 说明 |
|------|------|------|
| `my_hand_size` | 重建手牌 | 我剩几张 |
| `teammate_rest` | `context.numofplayers[(my+2)%4]` / botzone history 推算 | 队友剩几张 |
| `opp_rest_min` / `opp_rest_max` | 同上另两家 | 对手张数极值 |
| `greater_type` | `greater_action[0]` | 待压牌型（Single/Pair/Bomb/PASS…） |
| `greater_power` | `trick_state.rank_value` | 待压牌力（级牌 15.5 语义） |
| `greater_pos` | `actions[i].greater_pos` | 牌权归属（me/teammate/opp） |
| `lead_side` | `greater_pos==-1 → 自由领出` | me/teammate/opp/free |
| `cur_rank` | `context.curRank`（副内恒定） | 级牌 |
| `role` | `context.role` | 主攻/助攻（botzone 从引擎日志提取） |
| `breaks_core` | `context.grouping_plan` 比对 | 该动作是否拆 core 组 |
| `my_bomb_avail` | 重建手牌含 ≥4 同点/王炸 | 我可压炸数量 |
| `sprint_signal` | 队剩≤4 | 冲刺信号 |
| `stage_label` | `context.stage` + 手牌数 | open/mid/endgame |

> 全部字段已存在于 `my_decisions.context` 或可由 `actions` 重建——**不引入新采集**。

## 五、挖掘算法（④ 选型）

- **首选简化 Apriori 式项集挖掘**（纯 Python，无 sklearn，CPU 轻量）：特征离散化（`my_hand_size`→`≤3/4-7/≥8` 分桶）→ 枚举组合 → 统计
- **三指标定义**：
  - **support** = 覆盖败招数 / 败招总数（要求 ≥ `--min-support`）
  - **lift** = 该前提在败招集中的比例 / 在对照集中的比例（要求 > 1）
  - **conflict** = 同前提但做了「动作偏好相反」的**非败招**决策点数量（要求 = 0）
- 输出前按 `lift × log(support) ` 排序，取 top-K
- **v1 简化**：组合枚举限制单条 ≤3 个特征条件（防组合爆炸），先看一轮候选质量，再决定是否升级完整 Apriori

## 九、风险与限制

1. **机器归纳的自由规则质量低于人总结的**（欠采样过拟合、缺语义）→ 第一版做**半自动**：机器产候选 + 静态三指标 → 人最终裁决。
2. **botzone 无副收尾** → 候选发现可用，验证必须回 lalala/自对弈；发现与验证分离是本方案纪律。
3. **特征空间依赖已有字段** → 若未来需新特征，须先在 recorder 侧落地，本脚本不自造。
4. **v1 简化枚举可能漏挖长条件规则** → 先看候选质量，质量低再升级完整 Apriori。
5. **【实测确认】败招正样本趋近于零**（2026-08-10 验证）：lalala 148 副残局仅 2 个败招（R4）；botzone 单日志 22 副 / 72 残局决策点 **0 命中**。三指标挖掘的分母（败招总数）≈0，`support/lift` 统计无意义，且 R1/R3/R4 是**残局检测器**，覆盖不到中局战术新情形。
6. **【判定标准三层】「败招」的判定标准本身决定正样本质量与数量**（2026-08-10 补充）。按严格度从高到低：

   | 层级 | 标准 | 误报 | 召回 | 能挖新情形？ | 现状 |
   |------|------|------|------|------------|------|
   | **① 确定性** | 仅凭「掼蛋规则 + 自己手牌 + greater」即可证明动作错误（R1 报单不压 / R3 一手清拆牌 / R4 临门不炸） | 0 | 趋近 0 | 否（只挖已知铁错） | ✅ 已有 `check_endgame_solver` |
   | **② 事后统计** | 无法确定性证明，但「同情形这样做 → 副结果明显更差」；需 ground truth（副胜/名次）+ 大批同情形样本做反事实统计 | 中 | 中 | ✅ 能 | ❌ 无（需大样本 + 反事实归因） |
   | **③ 启发式标记** | 决策点触发引擎内部低分/警告信号（GUA-075 推荐无法匹配、启发式选候选集最低分、guard 拦一半放行） | 高 | 高 | 可能 | ❌ 无（**实测 `score` 字段全为 `None`**，recorder 未存分数，此路当前无信号） |

   **核心矛盾**：想要的「新情形败招」（botzone 上发现的战术失误）属**层级 ②**，而 ② 需要大样本 + 反事实归因——正是「复现概率低」死穴的所在。**确定性标准（层级 ①）是唯一零复现可跑的，但挖不出新情形**。故「自动挖掘新规则」与「零复现验证」本质冲突：要发现新败招须用统计标准（需大样本），要用确定性标准须接受挖不出新东西。
   **应对（已定案 v4：走 b + a 组合）**：
   - **b. 换挖掘目标到层级 ②（核心路线）**：以「事后统计败招」为目标——用副内名次/得分（`result.order`/`victoryNum`）作 ground truth，统计「同情形不同动作 → 名次/得分差异」。
   - **a. 扩样本（同池扩展，随 b 走）**：自对弈池现有 37 副，扩到数百副提高统计基础；`game_records_v8` 目录即池，`run_v8_vs_v8_games.py` 已存在。
   - **c. 补 recorder 信号（后续改进，非 v1）**：让 recorder 落盘 `score` 等决策质量信号，为层级 ③ 弱正样本铺路（当前 `score=None`）。
   **v1 范围**：b + a。第一步先用现有 37 副跑通「决策点 → 名次归因 → 同情形统计」管线一轮验证，可行再扩池。c 记为后续。
