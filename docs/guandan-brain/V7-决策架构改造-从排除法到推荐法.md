# V7 决策架构改造：从排除法到推荐法

> 创建时间：2026-06-20
> 状态：**已实施**（初版 2026-06-20）
> 关联：GUA-063（组牌→出牌衔接）· GUA-075（ISSUES 登记号）· 组牌-NN衔接设计-软引导vs硬约束.md §零
> 前提：本章基础发现须先被团队理解——服务器 actionList 是规则警察，不是策略约束器

---

## 一、改造缘由

### 1.1 核心发现（2026-06-20）

南邮 v1006 服务器的 `actionList` 本质是**规则警察，不是策略约束器**。它基于你手中 27 张牌，枚举所有不违反掼蛋规则的合法出牌方式——从 `PASS` 到 `八星炸`，全都塞进 actionList 发给你。它没在帮你选策略，它只是在说"圈里的随你挑，别出圈外的犯规"。

实测：27 张手牌 + 2 个逢人配 → actionList 最高可达 **2812 个候选**。

### 1.2 V7 当前的根本缺陷

V7 的 NN 是固定 512 维位置的 softmax——**它不是在评估 2812 个候选的内容，而是 BC 训练让它记住了"slot 0（PASS）和 slot 1（首候选）历史上概率最高"。**

| 问题 | 表现 |
|------|------|
| 位置背答案 | 不看候选内容，只看 slot 编号。slot 1 大概率 PASS，slot 37 太靠后永远不出顺子 |
| 排除法管线 | Guard、组牌引擎、角色过滤都在做排除法——删掉不该选的——但**没有一条管线干"从合法候选中主动选出最好的那一个"** |
| 组牌决策割裂 | 组牌引擎知道最优方案（哪组是炸、哪组是顺子），但 NN 不鸟它 |

### 1.3 正确架构方向

```
组牌引擎 → 最优组局方案（card_mask: 炸弹组0、顺子组1、对子组2…）
                │
                │  + 当前局面上下文（curPos是谁 / greaterAction / 队友剩牌）
                │  + 上家/下家/对家策略
                ↓
        出牌推荐 → 扫描原始actionList → 找到匹配候选 → {"actIndex": 157}
```

**不需要 NN 做选择题。** 2812 选 1 从"背答案"变成了"按方案点菜"。

### 1.4 上家/下家/对家策略必须纳入推荐

掼蛋四项基本原则之一是「打上家、卡下家、让对家」。服务器通过 `myPos` 和 `curPos` 提供了足够信息：

```python
上家 = (myPos + 3) % 4    # 逆时针上一个，应压制
下家 = (myPos + 1) % 4    # 顺时针下一个，应卡住
对家 = (myPos + 2) % 4    # 队友，应让道/喂牌
curPos == -1              # 领出，应遵守首出高压线
```

没有这个判断，出牌推荐就是盲打——不知道自己在压制谁、在配合谁。

## 二、现有管线分析（改造前）

### 2.1 当前管道全貌

```
game_state (含 actionList)
    │
    ▼
① _run_grouping_engine(game_state)     → card_mask + role
② _inject_numofplayers(game_state)     → 各家剩牌数
③ _update_teammate_last_trick(gs)      → 接风记忆
④ Guard filter: filter_action_list(gs) → R01-R15 硬排除，返回 filtered_actions + action_map
⑤ _group_consistency_filter(...)       → 角色驱动排除拆core动作，返回 group_actions + group_filter_map
⑥ _apply_wind_catch_anchor(...)        → 接风跟线重排
⑦ _try_teammate_feeding(...)           → 投喂策略重排
⑧ _model_decision(game_state, group_actions) → NN forward → argmax → best_idx
⑨ validate_decision(...)               → Guard 二次校验
⑩ GUA-071 后置覆盖                     → 拆局/joker滥用/炸弹滥用 → _heuristic_select
⑪ 两级索引映射                          → group_actions[idx] → group_filter_map → action_map → original_idx
    │
    ▼
actIndex (原始 actionList 下标)
```

### 2.2 问题本质

| 环节 | 做什么 | 问题 |
|------|--------|------|
| ④ Guard filter | 从 actionList 中**砍掉**错误候选 | 排除法，只告诉你不能选什么 |
| ⑤ group_consistency | 从剩余候选中**砍掉**拆局候选 | 排除法，保护组局不被破坏 |
| ⑥⑦ wind/feeding | 在剩余候选中**重排**优先级 | 调整顺序，但不创造新候选 |
| ⑧ NN model_decision | 从剩余候选中 argmax | **不看内容看位置**，背答案 |
| ⑨⑩ validate/覆盖 | 兜底纠错 | 善后，不是主动选优 |

**没有一步在做"从合法候选中主动选出最优的那一个"。**

## 三、改造方案

### 3.1 新架构总览

```
game_state (含 actionList)
    │
    ▼
① _run_grouping_engine(game_state)     → card_mask + role（不变）
② _inject_numofplayers(game_state)     → 各家剩牌数（不变）
    │
    ▼  ═══════════ 【NEW】主路径 ═══════════
    │
③ 【NEW】_recommend_play(game_state)
   内部整合:
   ├─ curPos 场景判断    （上家/下家/对家/领出）
   ├─ 组局方案选择        （从 card_mask 中选本步该出的组）
   ├─ Guard 规则前置      （领出不炸、压单不用炸等作为推荐约束）
   ├─ 接风/投喂判断       （是否该接风/喂队友）
   └─ 首出高压线          （进贡慎出单/顺子慎始发）
   ── 注：火不打四（P-H02）属于残局管线，后续单独设计 ──
   → recommendation: {type, rank, cards}
    │
    ▼
④ 【NEW】_match_actionList(recommendation, actionList)
   → 三要素精确匹配（牌型/点数/牌张） → actIndex 或 -1
    │
    ├── 命中（actIndex >= 0）
    │     │
    │     ▼
    │   ⑤ Guard 硬规则快速校验（R01/R05/R10等不可逾越的底线）
    │     │
    │     ├── 通过 → return actIndex  ✅ 主路径完成
    │     │
    │     └── 不通过 → 走回退路径
    │
    └── 未命中（actIndex == -1）
          │
          ▼  ═══════════ 回退路径（现有管线）═══════════
          │
          Guard filter → group_consistency_filter →
          wind_catch + feeding 重排 →
          NN model_decision → validate →
          GUA-071 后置覆盖 → 两级映射 → actIndex
```

### 3.2 两个路径的职责

| | 主路径（推荐法） | 回退路径（排除法） |
|---|---|---|
| 何时走 | 组牌方案 + 局面上下文能产出明确推荐，且 actionList 中精确命中 | 推荐失败（无匹配/Guard否决/残局应变/对手急眼） |
| 谁做决策 | 出牌推荐器（规则驱动，基于组牌+局面） | 现有管线（Guard → NN → Heuristic） |
| 预期占比 | 目标 80%+ 的决策步 | 20%- 的决策步 |
| 优点 | 可解释、可控、不背答案 | 兜底安全网 |

### 3.3 管道时序变化

| 阶段 | 旧位置 | 新位置 | 变化 |
|------|--------|--------|------|
| 组牌引擎 | ① | ① | 不变 |
| 人数注入 | ② | ② | 不变 |
| Guard filter | ④（在 actionList 上排除） | **前移到③**（作为推荐约束）+ 保留在⑤（硬规则校验）+ 保留在回退路径 | 逻辑前移 |
| group_consistency | ⑤（在过滤后列表上排除） | **前移到③**（决定选哪个组出） + 保留在回退路径 | 逻辑前移 |
| wind_catch | ⑥（重排） | **前移到③**（影响推荐决策） + 保留在回退路径 | 逻辑前移 |
| teammate_feeding | ⑦（重排） | **前移到③**（影响推荐决策） + 保留在回退路径 | 逻辑前移 |
| NN model_decision | ⑧（主路径 argmax） | **降级为回退路径** | 角色降级 |
| validate_decision | ⑨ | 保留在回退路径 + ⑤快速校验 | 双路径 |
| GUA-071 覆盖 | ⑩ | 保留在回退路径 | 不变 |

**关键原则：推荐器必须在 Guard filter 之前运行。** 推荐器需要原始 actionList（完整菜单）来匹配推荐方案，不能先用 Guard 砍掉候选再匹配。

## 四、出牌推荐器设计（_recommend_play）

### 4.1 输入

| 输入 | 来源 | 说明 |
|------|------|------|
| `card_mask` | 组牌引擎 | Dict[card_str, (group_id, is_core, group_size)] |
| `myPos` | game_state | 我方座位号 0-3 |
| `curPos` | game_state | 当前出牌人 0-3 或 -1（领出） |
| `greaterAction` | game_state | 当前圈最大牌 [type, rank, cards] |
| `publicInfo` | game_state | 各玩家剩余牌数 |
| `curRank` | game_state | 本副级牌 |
| `handCards` | game_state | 我方手牌 |

### 4.2 推荐逻辑流程

```
① 判断场景
   curPos == -1          → 领出场景
   curPos == 上家         → 打上家（压制）
   curPos == 下家         → 卡下家（阻止跑牌）
   curPos == 对家         → 让道/喂队友

② 领出场景
   ├─ 进贡后领出 → 慎出单张（P-H01）
   ├─ 顺子慎始发（P-H05）
   ├─ 通常：出小单试探 或 出小对子开路
   └─ 从 card_mask 中选一个非core、低耗损的组 → 生成推荐
   ── 注：火不打四（P-H02）误放在此，正确归属是残局管线（对手剩牌 ≤ 4 不炸），后续单独建管道 ──

③ 跟牌场景（上家在出牌 → 打上家）
   ├─ greaterAction 是 PASS → curPos 变为领出身份，走②
   ├─ 有同型可压 → 选节牌力最优的同型 → 生成推荐
   ├─ 无可压同型、有炸弹 → 评估是否值得炸（上家剩牌少？上家快跑了？）
   └─ 无解 → 推荐 PASS

④ 跟牌场景（下家在出牌 → 卡下家）
   ├─ 下家剩牌少（≤5张）→ 有炸弹直接用炸锁住
   ├─ 有同型可压 → 用最大可压的同型（不留余地）
   └─ 无解 → 考虑炸或 PASS

⑤ 跟牌场景（对家在出牌 → 让道）
   ├─ 默认 PASS
   ├─ 队友可能跑不掉（对手有大牌在压队友）→ 考虑接牌喂队友
   └─ 队友快跑了（剩牌≤2）→ 绝对 PASS

⑥ 生成推荐
   → {type: str, rank: str, cards: [str, ...]}
```

### 4.3 Guard 规则前置映射

部分 Guard 规则不是"排除"，而应作为"推荐约束"前置：

| Guard 规则 | 旧方式（排除法） | 新方式（推荐约束） |
|------------|-----------------|-------------------|
| R10 领出不炸 | 从 actionList 中删掉炸弹 | 领出场景下，推荐器**不推荐炸弹** |
| R01 压单不用炸 | 删掉用炸压单的候选 | 有同型单张可压时，**不推荐炸压单** |
| R05 队友不炸 | 删掉炸队友的候选 | 对家场景下，**不推荐炸弹** |
| R07 队友让道 | 删掉压队友的候选 | 对家场景下，**优先推荐 PASS** |

### 4.4 多匹配/无匹配处理

**多匹配**（同一推荐对应 actionList 中多个候选，如同一顺子可用 S2+C3 或 H2+C3 实现）：
- 推荐器应输出**精确牌张**，尽可能唯一确定候选
- 若仍有多个，优先选**节牌力最优**（消耗最小点数）的变体

**无匹配**：
- 走回退路径（现有 Guard + NN + Heuristic）
- 常见原因：残局手牌不足无法形成推荐方案、对手急眼超出了组牌方案的预期范围

## 五、actionList 匹配器设计（_match_actionList）

### 5.1 接口

```python
def _match_actionList(
    self,
    recommendation: Dict[str, Any],  # {type, rank, cards}
    action_list: List[List]           # 原始 actionList
) -> int:
    """
    在 actionList 中精确查找匹配推荐方案的候选。
    
    Returns:
        actIndex (0-based) 或 -1（未找到）
    """
```

### 5.2 匹配逻辑

三要素匹配（缺一不可）：

```python
for i, candidate in enumerate(action_list):
    # [type, rank, cards] 三字段精确比对
    if (candidate[0] == recommendation["type"] and
        candidate[1] == recommendation["rank"] and
        sorted(candidate[2]) == sorted(recommendation["cards"])):
        return i
return -1
```

注意：牌张列表需要排序后比对，因为 actionList 和推荐中的牌张顺序可能不同。

## 六、回退路径（不变，结构保留）

当主路径（推荐匹配）失败时，完整走回退路径：

```
Guard filter (R01-R15 硬排除)
  → group_consistency_filter (角色前置过滤)
    → wind_catch_anchor (接风重排)
      → teammate_feeding (投喂重排)
        → NN model_decision (argmax)
          → validate_decision (Guard 二次校验)
            → GUA-071 后置覆盖 (拆局/joker滥用/炸弹滥用)
              → 两级索引映射 → actIndex
```

回退路径代码**不删**，保持完整可用。这是安全底线。

## 八、验收标准

1. **新管道能跑通**：组牌推荐 → 匹配 actionList → 返回 actIndex，无异常
2. **至少 80% 决策步走主路径**：统计 `_recommend_play()` 命中率
3. **回退管道可用**：推荐失败时能正常 fallback 到现有管线
4. **牌型选择不再受 slot 位置影响**：顺子、三带二、钢板等 slot 靠后的牌型能在合适时机正常打出
5. **不拆最优组局**：NN 背答案导致的拆炸弹/拆顺子问题消失
6. **上家/下家/对家场景区分**：压制、卡位、让道行为可验证
7. **批跑胜率不低于现有基线**：作为安全底线

## 十、NN 自学习道路的架构隐患

> **上下文**：V7 当前架构下，推荐器命中后**直接跳过 NN 返回 actIndex**。NN 只在推荐器失败时作为回退路径执行。这意味着：推荐器命中率越高 → NN 参与决策越少 → NN 得到的训练信号越弱。如果 V7 未来要走 NN 自学习（如 RL 自对弈），以下 5 个隐患必须正视。

### 10.1 训练信号截断（Selection Bias）

```
推荐器命中 → 直接 return actIndex  (NN 永远碰不到这些场景)
NN 只处理: 推荐器覆盖不了的边缘局面
```

推荐器拦截了"有同型可压"和"改炸"等核心决策。NN 在自对弈中只看到：
- 领出自己的牌（⑤ 场景）
- 接风/喂队友
- 推荐器判定 PASS 后的被动形势
- 残局边缘炸决策

NN **学不到**「跟上家用最小牌压」「卡下家用最大牌压」「上家第二圈改炸」——这些恰恰是掼蛋战术密度最高的决策。训练数据出现严重的 **selection bias**。

### 10.2 Credit Assignment 断裂

自对弈胜负是 NN 的 loss signal。但关键决策来自推荐器：

| 场景 | 实际决策者 | NN 的后果 |
|------|-----------|----------|
| 推荐器压牌压小了，对手跑掉 | 推荐器 | NN 背锅（loss 上升），但无法改进推荐器 |
| 推荐器及时改炸获胜 | 推荐器 | NN 白拿 credit，学不到为什么赢 |
| 推荐器 PASS 让道被队友接住 | 推荐器 | NN 既无 credit 也无 blame |

Win/loss 梯度通过整个对局反向传播，但推荐器的规则决策是**离散的、无梯度的**。NN 接收到的 gradient 实际上是不可归因的噪音。

### 10.3 NN 退化风险

```
推荐器命中率 70%+ → NN 只参与 30% 决策
长时间自对弈后:
  - NN 在推荐器覆盖的决策空间里完全没经验
  - 一旦推荐器规则失效（新牌型、新对手策略），NN 是空白
  - NN 退化成只能处理"残局边角料"的策略
```

### 10.4 迭代死锁

```
推荐器越强 → NN 训练场景越少 → NN 越弱 → 越依赖推荐器
推荐器越弱 → NN 被迫上场 → NN 越强 → 推荐器被冷落

这是一个此消彼长的零和关系，而非协同进化。
推到最后：推荐器天花板 → 项目天花板；NN 永远长不大。
```

### 10.5 推荐器天花板

推荐器的上限由人工规则决定。R11 改炸虽然用了全局牌记忆，但仍然是 if-else：
- 上家出 Single，我无同型 → 第一圈 PASS，第二圈炸
- 下家出 Single，抑制牌 0 张 → 炸

真正「这手该不该炸」需要考虑的因子远超人工能枚举：
- 对手剩余牌力分布
- 队友手牌推断（队友还剩什么？能接吗？）
- 全局节奏感（现在是控场还是冲刺阶段？）
- 炸弹收益 vs 消耗的牌力比

NN 有能力从海量对局数据中学习这些隐性信号，但推荐器不让它上场。

### 10.6 如果坚持 NN 自学习，四种架构修正

| 方案 | 思路 | 训练/部署分离 | 风险 |
|------|------|-------------|------|
| **A. Bias over Replace** | 不用推荐器替换 NN，而是给 NN logits 加 bias（推荐牌 +2.0，不该出 -5.0） | 一致 | NN 仍有探索空间，收敛变慢 |
| **B. Train without Recommender** | 训练时关闭推荐器，NN 从零积累经验；部署时推荐器兜底 | 分离 | 部署与训练数据分布不同，需大量算力 |
| **C. Gradual Phase-out** | 先以推荐器为主，逐步降低命中率（随机 X% 让 NN 决策），观察 NN 能否接管 | 一致 | 需要长期监控 win rate 波动，可能长期停在中间态 |
| **D. Dual-track** | 推荐器和 NN 独立出决策，选胜率预估更高的那个 | 一致 | 实现复杂度高，需要 NN 有置信度输出 |

> 最简单可执行的起步方案是 **B**：训练时跑 `--no-recommender` 模式，NN 从头积累战术经验；部署时合并推荐器作为安全网。

## 十一、V7 与 M3：复杂度的意义到底是什么

> **背景数据**（截至 2026-06-20）：
> - M3：~1000 行 guard 规则 + 简单 heuristics → 队胜率 **34/42（81.0%）** vs lalala
> - V7：组牌引擎 ~1461 行 + Guard ~810 行 + 推荐器 ~500 行 + NN 训练管线 + MemoryTracker + 角色过滤 + 接风投喂… → 队胜率 **1/111（0.9%）** vs lalala
>
> M3 代码量是 V7 的 **1/3**，胜率是 V7 的 **90 倍**。

### 11.1 这是失败吗？

**从胜率看，是的。从架构演化看，不是。**

V7 不是在 M3 上堆复杂度——V7 是在解决 M3 没有解决的问题：

| M3 的债 | V7 的答案 | 当前状态 |
|---------|----------|---------|
| NN 位置背答案，不看牌型内容 | 推荐器从组牌方案出发，看内容出牌 | ✅ 已工作，但胜率更低 |
| 组牌方案与出牌决策割裂 | card_mask → _recommend_play → 精确出牌 | ✅ 架构打通 |
| 全局牌记忆缺失（M3 R11 不知道外面还有王） | MemoryTracker 贯穿全管线 | ✅ 已接入 R11 预检 |
| Guard 规则是手工 if-else，不可能枚举所有局面 | 设计上为 NN 留位置 | ❌ NN 从未真正参与 |
| 不可解释的黑盒决策 | 推荐器每步日志可追溯到组牌方案 | ✅ 可追溯 |

V7 付出了巨大的架构复杂度，牺牲了短期胜率，换来了一个**正确的骨架**——组牌 → 场面 → 推荐 → 匹配，每个环节都可独立测试、可独立迭代、可日志追溯。

### 11.2 M3 为什么能赢？

M3 的成功有结构性原因：

1. **问题域窄**：M3 打 lalala——lalala 是规则 AI，有固定出牌模式的弱点。M3 的 1000 行 guard 本质是「反 lalala 的针对性规则」。
2. **规则密集问题更适合手写**：掼蛋的硬约束（领出不炸、队友不压）天然适合 guard。M3 把有限的规则枚举做到了极致。
3. **没有 NN 拖后腿**：M3 不走 NN 主路径。BC argmax collapse、位置背答案这些 V7 的坑，M3 根本不存在。
4. **简单就是快**：M3 迭代周期是 10 分钟改 guard → 批跑 → 看回放。V7 迭代是 改引擎 → 重训 → 批跑 → 对账，动辄 4 小时。

### 11.3 V7 的复杂度花在了哪里

```
V7 代码量级（估算）:
  grouping_engine.py       1461 行  ← 组牌引擎，做 M3 完全不做的事
  v7_guards.py             810 行   ← Guard 规则（M3 也有约 300 行版本）
  engine_v7.py             2600 行+ ← 主引擎（推荐器、匹配器、记忆、管线）
  memory_tracker.py        300 行   ← 全局牌记忆（M3 没有）
  train_bc_v7.py           500 行+  ← NN 训练管线（M3 完全不需要）
  -------------------------------
  合计                     5700 行+   vs M3 ~1000 行
```

但本质不是"5700 行 vs 1000 行"的问题——是**问题定义不同**：

| | M3 | V7 |
|---|---|---|
| 目标 | 打赢 lalala | 打赢任意对手（含人类） |
| 组牌 | 不做（交给发牌） | 全面自组牌方案 |
| 牌记忆 | 不看全局 | 跟踪每张牌的出牌历史 |
| 策略 | 反 lalala 硬规则 | 通用出牌知识 |
| NN | 不走（或浅度参与） | 核心理念是 NN 自学习 |
| 解释性 | 不可解释 | 每步可追溯 |

V7 的复杂度分布在「通用性基础设施」上——组牌、记忆、推荐框架。这些东西 M3 不需要，因为 M3 的目标只是打赢一个已知弱点的固定 AI。

### 11.4 危险信号与冷静反思

以下信号说明当前架构有**方向性问题**：

| 信号 | 说明 |
|------|------|
| 🔴 推荐器 vs NN 零和 | 推荐器越强，NN 越弱——设计上完全背离"NN 自学习"目标 |
| 🔴 复杂度全在手工规则 | 5700 行里 4000+ 是手工规则，只有 ~500 行是模型 → V7 本质还是专家系统 |
| 🔴 没有从 M3 继承战斗力 | M3 的 81% 胜率经验完全没有迁移到 V7——两个系统几乎没有共享逻辑 |
| 🟡 迭代周期过长 | 改一组牌 → 跑 9 局 → 1.5 小时，远慢于 M3 的 10 分钟验证循环 |
| 🟡 赔率不对 | V7 投入了 M3 3 倍的代码量，胜率是 M3 的 1/90——投入产出完全倒挂 |

### 11.5 三条可能的前路

| 路 | 做法 | 代价 | 预期 |
|----|------|------|------|
| **路A：做减法** | 砍掉推荐器，恢复 M3 风格 guard→NN→heuristic 管道；保留组牌引擎和 MemoryTracker 作为 features 喂 NN | 推翻 GUA-075 全部工作 | 短期胜率可能回升，长期仍受 BC argmax 限制 |
| **路B：坚持推荐法** | 继续迭代推荐器覆盖更多场景 + 保留回退 NN；接受"推荐器为主、NN 为辅"的专家系统定位 | 放弃 NN 自学习愿景 | 可能追平 M3 胜率，但无法超越手工天花板 |
| **路C：双引擎融合** | 推荐器输出 logit bias（不替换 NN），NN 仍是最上层 argmax；训练时关闭推荐器 bias，部署时打开 | 训练/部署分离，架构改动中等 | 理论上唯一能同时收获"可解释"和"可自学习"的路线 |

### 11.6 底线结论

**V7 写了一堆管线，做了 M3 没做的事（组牌、全局记忆、可解释出牌），但忘了回答最基本的问题：这套管线比 M3 多打出的 1 张好牌，能不能覆盖它引入的 10 个新 bug 和 3 倍延迟？**

V7 的架构方向——组牌→推荐→出牌——在概念上是正确的。但**当前实现踩了推荐器与 NN 互斥的坑**，导致推荐器虽然逻辑正确、却没能把正确性转化为胜率。

如果你决定继续在 V7 上迭代，**必须在下个工作周期内做出路线选择**（A/B/C），否则会陷入「在错的架构上加对的规则」的死循环。
