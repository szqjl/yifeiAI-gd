## 1. 问题摘要

| 项 | 说明 |
|----|------|
| **现状** | `UltimateWinRateEngineV7`（[`src/v/nn/ultimate_win_rate_engine_v7.py`](../../src/v/nn/ultimate_win_rate_engine_v7.py)）已满足 `IDecisionProvider` v1.0 契约（`player_id:int` + `decide(message)->int`），但 **内部实现极简** |
| **特征工程** | 512 维零填充——有效维度仅 ~23 维（位置 one-hot 12 + 手牌数 1 + rest 4 + rank 3 + actionList 长度 1 + curAction/greaterAction 长度 2），**489 维为零**；无牌态编码、无出牌历史、无动作结构 |
| **模型** | 依赖 `bc_model_ultimate_win_rate.pth`（**不在** `models/` 中），加载失败时直接 fallback |
| **Fallback** | 仅遍历 actionList 选第一个非 PASS 动作，无任何策略深度 |
| **训练** | 无可用训练数据管道、无自对弈框架、无 BC 数据生成器 |
| **结论** | V7 当前 **仅具备接口骨架**，决策能力远低于 M3（队胜率 75%+ / 36 个 GUA 迭代） |

## 3. 现状代码审计

### 3.1 特征工程缺陷清单

| 缺陷 | 当前实现 | 影响 |
|------|---------|------|
| 手牌未编码 | 仅 `len(handCards)` | 模型无法感知具体牌面 |
| 出牌历史未使用 | `history` 字段存在但未提取 | 无法学习对手/队友策略 |
| 动作结构未编码 | 仅 `len(actionList)` | 无法区分炸弹/顺子/单张等 |
| 级牌信息极简 | 仅 3 个数值（curRank/selfRank/oppoRank） | 红心配、级牌炸弹等未体现 |
| 大量零填充 | 489/512 维为零 | 模型训练信号稀疏 |

### 3.2 与 Danzero+ / ABL-GD 对比

| 维度 | V7 现状 | Danzero+ | ABL-GD |
|------|---------|----------|--------|
| 牌态编码 | 23 维有效 | ~108×N + LSTM 历史 | 168 伪动作 |
| 动作压缩 | 无 | top-K=2（验证最优） | 168 伪动作 |
| 训练方法 | 无 | DMC + PPO 两阶段 | BC + PPO |
| 框架 | PyTorch（本地模型缺失） | TF1.x + PyTorch 1.9 | 未开源 |
| 胜率（论文） | — | 55%（vs rule-based） | 60.9%（500 局） |

## 4. 候选方向

### 方向 A：借鉴 Danzero+ 架构重写 V7 — **文档推荐**

| 项 | 内容 |
|----|------|
| **做法** | 分三阶段：① **特征工程重写**（108 维牌态 + 出牌类型 + 级牌/红心配编码）；② **BC 预训练**（M3 净盘批跑数据做 teacher 标签）；③ **DMC 自对弈 + PPO 增强**（Danzero+ 两阶段路线） |
| **Phase 1** | 重写 `_extract_features`：手牌 one-hot（54 类 × 2 副 = 108 维）、各玩家 rest/played、级牌/红心配、出牌历史 LSTM 编码、动作结构（牌型 one-hot + 点位） |
| **Phase 2** | M3 净盘批跑（`game_records` + `my_decisions`）提取 (state, action) 对 → BC 训练 → 初始策略权重 |
| **Phase 3** | 分布式自对弈（Actor × N + Learner）；DMC value net → top-K 过滤 → PPO policy net |
| **优点** | 掼蛋专用架构（论文已验证）；特征工程与学术界对齐；长期上限高 |
| **风险** | 工作量大（Phase 1-3 预计 3-4 迭代）；TF1.x→PyTorch 需移植；训练算力需求 |
| **工作量** | 大（Phase 1 ~1 迭代；Phase 2 ~1 迭代；Phase 3 ~2 迭代） |

### 方向 B：M3 知识蒸馏 → V7 BC（可独立执行）

| 项 | 内容 |
|----|------|
| **做法** | 用 M3 净盘批跑数据（`game_records/*.json` 中 `my_decisions` 字段）提取 (state, M3_action) 标签对 → 训练 V7 BC 模型 → V7 初始策略 = M3 行为克隆 |
| **前置** | Phase 1 特征工程须先完成（否则 BC 标签无对应特征） |
| **优点** | 利用 M3 已有的 75%+ 胜率决策质量；无需自对弈基础设施；快速验证特征工程 |
| **风险** | BC 上限 = M3（不会超越 teacher）；M3 决策数据仅覆盖 v1006 lalala 对手 |
| **工作量** | 中（~1 迭代） |

### 方向 C：SDMC 软启动方案

| 项 | 内容 |
|----|------|
| **做法** | 借鉴南京大学 SDMC：用 M3 rule-based 策略初始化 agent（软启动），训练中以概率混合 rule-based 和模型探索动作（软采样） |
| **优点** | 收敛快、策略稳定；SDMC 胜率 ~57%（高于 DMC ~54%） |
| **风险** | 论文未开源；软启动/软采样参数需调优；与 Danzero+ top-K 路线不完全兼容 |
| **工作量** | 中偏大 |

### 方向 D：仅修特征工程 + 接入现有训练脚本

| 项 | 内容 |
|----|------|
| **做法** | 仅重写 `_extract_features`（对齐 Danzero+ 特征维度），不引入新训练框架；复用 `src/train/` 已有 stage0-8 训练脚本 |
| **优点** | 工作量最小；可快速验证特征有效性 |
| **风险** | 现有训练脚本可能不匹配新特征；无自对弈能力；上限受限于离线训练数据质量 |
| **工作量** | 小（~0.5 迭代） |

### 方向 E：Fork Danzero+ 源码直用

| 项 | 内容 |
|----|------|
| **做法** | 克隆 `submit-paper/Danzero_plus`，适配 v1006 平台协议，直用其 Actor-Learner-ZMQ 训练框架 |
| **优点** | 省去重新实现 DMC+PPO 的工作；论文已验证效果 |
| **风险** | TF1.x deprecated → 迁移成本高；与现有代码风格/PyTorch 栈冲突；v1006 平台适配工作量大 |
| **工作量** | 大（平台适配 + TF 迁移 + 特征对齐） |

## 6. 文档推荐结论（待评审确认）

1. **主线**：**方向 A**（借鉴 Danzero+ 架构重写 V7），分三阶段推进。
2. **Phase 2 可与方向 B 合并**：M3 知识蒸馏作为 BC 预训练热启动，**A+B 并行**。
3. **Phase 1 先行**：特征工程重写是 A/B/C/D 所有方向的公共前置，应作为 **V7-01** 首先立项。
4. **本轮不做**：方向 E（Fork 源码）——TF1.x 迁移成本与项目 PyTorch 栈冲突。
5. **SDMC**（方向 C）作为 Phase 3 备选：若 Danzero+ PPO 效果不理想，可叠加软启动/软采样。
6. **验收**：
   - Phase 1：特征向量维度合理 + pytest 可构造 + `is_decision_provider` 仍通过
   - Phase 2：BC 模型加载成功 + 对 M3 决策数据准确率 >60%（非队胜率关单）
   - Phase 3：自对弈框架可跑 + 对 lalala 队胜率 >40%（治理方案 §7.2 V 冒烟门槛 A）
