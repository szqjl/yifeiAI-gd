# 组牌方案与 NN 决策衔接设计：前置过滤 + 角色驱动

> 创建时间：2026-06-18
> 状态：方案确定 — 第三阶段「角色驱动前置过滤」为 GUA-063 核心设计方向
> 关联：GUA-063（组牌→出牌衔接三缺口）
> 前提：组牌引擎 v2（GUA-062）已 closed，能产出合格的多方案；`determine_role()` / `_score_power()` 已实现

---

## 零、重大发现：组牌方案可以直接映射到 actionList 实现「按方案点菜」（2026-06-20）

### 问题根因

服务器 actionList 的本质是**规则警察，不是策略约束器**。它是基于你手中 27 张牌，枚举所有不违反掼蛋规则的合法出牌方式，全部塞进 actionList 发给你。它没在帮你选策略——它只是在说"圈里的随你挑，别出圈外的犯规"。

实测数据：27 张手牌 + 2 个逢人配 → actionList 最高可达 **2812 个候选**。

但 V7 当前的 NN 是固定 512 维位置 softmax——它不是在评估 2812 个候选的内容，而是 BC 训练让它记住了"slot 0（PASS）和 slot 1（首候选）历史上概率最高"。这是一个**位置背答案**的模型，不是**内容做决策**的模型。

**所有管线（Guard、组牌引擎、角色过滤）都在做排除法——删掉不该选的——但没有一条管线干「从合法候选中主动选出最好的那一个」这个活。** NN 负责的应该是这个活，但它的 512 维 fixed-slot softmax 架构根本消化不了候选内容的语义。

### 正确架构方向

```
组牌引擎 → 最优组局方案（出顺子2-6，用 S2 C3 D4 C5 H6）
                │
                ↓
       扫描 actionList → 找到 ['Straight', '2', ['S2','C3','D4','C5','H6']]
                │
                ↓
        返回 {"actIndex": 157}
```

**不需要 NN 做选择题。** 组牌引擎定了方案 → 去服务器枚举的菜单里找到对应菜 → 点单。2812 选 1 从"背答案"变成了"按方案点菜"。

### 与现有架构的关系

| 现有做法 | 应该是 |
|---------|--------|
| NN 背 slot 1 的答案（与手牌内容无关） | 组牌引擎生成方案 → 精确匹配 actionList |
| 管线做排除法，排除完剩下的凑合选 | 管线保底：组牌匹配失败时走现有 Guard+Heuristic 回退 |
| card_mask 保护炸弹不被拆 | card_mask 升级为精确匹配候选的索引 |

### 技术关卡

actionList 里同一牌型可能有多个变体（如顺子 2-6 有 S2+S3 vs C2+S3 两种选法）。组牌引擎需要精确到**具体用哪几张牌**，才能唯一匹配 actionList 中的某个候选。当前 `card_mask` 已有这个精度（标记了每张牌属于哪个组），理论上可以做精确映射。

### 对现有方案的影响

- 本文档的二~十一章（角色驱动前置过滤、Guard 管道、Heuristic 选择）仍然有效，作为**回退路径**
- 理想路径：组牌引擎直接选 → 无需 NN 也无须 Heuristic
- 回退路径：组牌匹配失败 / 残局应变 / 对手急眼 → 走现有 Guard+Heuristic
- 长期：这为 GUA-055（动作空间剪枝）和 DanZero+ 的 Top-K 候选范式提供了更简洁的落地方式——不是用 NN 选候选，而是用组牌引擎选候选

## 一、核心矛盾

组牌引擎跑出了合格的 best_plan（如「9999 是炸、10-A 同花顺、444→555 钢板」），但下游 NN 出牌时可能随手拆掉 ♦9 打顺子，炸弹就没了。

**两极困境**：

```
硬约束（组牌方案不可破）
    → "电烙铁焊住"，新手死守不变
    → 被高手嘲笑，中局无法应变

零约束（组牌方案不可见）
    → 90%+ 概率拆核心牌型
    → 组牌引擎白跑了
```

两个极端都不对。真正的答案在中间地带。

## 二、人类学习路径的三个阶段

### 第一阶段：电烙铁焊住

```
组好牌 → 死守不变 → "像被电烙铁焊住了一样"
```

新手的特点：牌怎么组就怎么打，方案不可变。被高手嘲笑，中局无法应变。

### 第二阶段：以组牌为框架，适当灵活

```
有方案 → 但"适当"灵活 → 问题是：什么时候适当？谁说了算？
```

进阶选手有了方案意识，知道该灵活。但没有判断标准，"适当"就是一句
空话——要么永远不会灵活，要么随便灵活。**它丢掉了掼蛋的本质：角色
决定策略**。

### 第三阶段：角色驱动的偏置策略 ✅

```
牌力强（主攻） → 90% 按组牌进攻，最快跑光
牌力弱（助攻） → 40% 按组牌，重心在压制对手+喂队友
```

高手不问"该不该灵活"，而是问"我的角色是什么"。主攻时守方案是
因为牌力强、按方案打效率最高；助攻时松方案是因为自己跑不掉，影响
战局的是帮对家。

---

### 为什么选第三阶段而非第二阶段

第二阶段的「适当灵活」没有判断依据，会退化：
- 偏置总生效 → V7 永远不灵活（退回第一阶段）
- 偏置太弱 → V7 随便灵活（退回零约束）

第三阶段**不需要 NN 重新训练，也不需要判断"何时灵活"**。角色已有的
（`determine_role()` / `_score_power()` 已实现），只需在 `decide()` 里根
据角色动态调偏置强度：

```
角色 → 偏置权重
主攻 → group_bias_weight = 0.9
助攻 → group_bias_weight = 0.4
```

**第二阶段的上限是「打好自己的牌」，第三阶段的上限是「理解团队博弈」。**

## 三、建议的三层架构

### 第一层：card-level grouping mask（解决 GUA-063 的 A）

核心问题：组牌方案是树结构（哪些牌在哪些组），NN 输入是固定长度浮点
数向量，**不能直接传**。

两条路线：

| | 路线 1：方案入 NN | 路线 2：外挂（前置过滤）✅ |
|---|---|---|
| 怎么做 | mask 编码 → 拼入 state_vector → NN 学习 | mask 在 `_model_decision` 之前过滤候选动作 |
| 需重训 | 要 | **不要** |
| 立即可用 | ❌ | ✅ |
| 插入点 | state_vector 维度扩展 | Guard filter 之后、NN forward 之前 |
| 留到什么时候 | GUA-039b 自对弈时训 | **现在就做** |

**当前选路线 2**：不碰 NN 输入、不改训练。mask 在 `decide()` 中 Guard
filter 之后立即过滤候选动作，NN 看到的动作空间已经按角色清洗过。

mask 编码格式：

```
每张牌 → [group_id, is_core, group_size] → 27×3 = 81 维

group_id:   0~N，同组牌共享同一 ID，散牌/单张 = -1
is_core:    1.0 = 核心不可轻拆（炸弹/同花顺/火箭），0.0 = 普通牌型
group_size: 该组共有几张牌（用于判断动作是否完整打出该组）

示例：
♦9  group_id=1, is_core=1.0, group_size=4  ← 属于炸弹组 1（9999），核心，共4张
♣9  group_id=1, is_core=1.0, group_size=4  ← 同上
♠8  group_id=2, is_core=1.0, group_size=5  ← 属于同花顺组 2，核心，共5张
♠Q  group_id=3, is_core=0.0, group_size=2  ← 普通对子，非核心，共2张
```

group_id 用绝对值（不用归一化）。

**这个 mask 不进 NN 输入**，只给 `decide()` 里的前置过滤器用。
Phase 1 完成 `GroupingPlan.to_card_mask()` 方法即可。

### 第二层：角色驱动的前置过滤（替代后置偏置）

做完 mask，接下来用 mask 按角色过滤动作候选集，**让 NN 看不到拆核心
牌型的动作**。

#### 为什么前置过滤而非后置偏置

`decide()` 当前流程：

```
actionList → filter_action_list (Guard) → _model_decision(NN → argmax) → validate_decision → 返回
```

`_model_decision` 就是 `extract_features → model forward → softmax → argmax`，
返回后直接走 validate 就结束了，**没有后置偏置的插入点**。

前置过滤插入在 Guard filter 之后、`_model_decision` 之前：

```
actionList → filter_action_list (Guard) → group_filter (NEW) → _model_decision → validate → 返回
                                              ↑
                                  主攻：剔拆核心动作
                                  助攻：全部放行
```

NN 看到的候选动作是已经按角色清洗过的——主攻的 NN 面前没有"拆炸"
选项，不需要偏置博弈。

#### 过滤规则

```
对于每个候选动作：
  统计该动作使用各 core 组的牌数

  如果 ∃ 组 G 满足：
      is_core[G] == 1
      AND 动作使用的 G 牌数 < group_size[G]     ← 部分使用 = 拆核心
    → 标记为「拆核心」
    → 主攻角色：从候选池移除
    → 助攻角色：保留（自由发挥）

  如果动作使用了某个 core 组的全部牌（count == group_size）
    → 这是完整打出该组（如 9999 炸弹）
    → 不视为拆，保留
```

安全阀：如果过滤后候选池为空（罕见，所有合法动作都拆核心）→ 全部放行。

#### 角色驱动

| 角色 | 过滤行为 | NN 看到的候选 | 效果 |
|------|------|------|------|
| **主攻** | 移除非完整打出的 core 组动作 | 无拆核心选项 | NN 被迫在安全候选里选最优 |
| **助攻** | 不放过滤 | 全部动作 | NN 自由选压制/喂牌动作 |

硬例外覆盖（三种场景无论角色都放行全部动作）：
- 自己剩 ≤5 张：加速出逃，放行全部
- 对手剩 1-2 张：保命，放行全部
- **R16**（2026-06-20）：队友剩 1 张 + 下家非 1 张 → 放行全部（送单不卡 role filter）
  - 下家也是 1 张时不放行：我出单→下家跟→下家头游 ❌
  - 下家 ≥2 张 + 队友 1 张 → 放行：我出单→下家跟或不跟→队友轮到→队友头游 ✅

**效果**：主攻时 NN 根本看不到拆炸选项，天然不拆。助攻时 NN 看到全部
动作自由发挥。不是偏置博弈，而是直接收窄候选空间。

### 第三层：中局重分组（解决 GUA-063 的 C）

不是每手都重新组（太费），而是**触发式**：

| 触发条件 | 原因 |
|----------|------|
| 核心牌型被破坏 | NN 决定拆 9999 出 ♦9，方案结构变了 |
| 手牌降到 15 张 | 超过一半已出，结构显著变化 |
| 手牌降到 10 张 | 进入残局前最后一次重分组 |
| 手牌降到 5 张 | 微调，简化方案 |
| 炸弹已全部消耗 | 方案不再需要防炸 |

重分组后更新 mask，NN 看到的新方案基于当前手牌，不是开局旧方案。

## 四、组牌引擎复用架构：一次跑，双产出

三层的 mask、role、features 都来自同一个组牌引擎 `enumerate_groupings()`，
但当前一次 `decide()` 调引擎两次：

```
Path 1（已有）：MemoryTracker.get_state_vector(game_state)
  └─ extract_grouping_engine_features(hand_cards, cur_rank)
      └─ enumerate_groupings() → _extract_features() → 24维 float
         ↑ 跑一次

Path 2（GUA-063 新加）：GroupingPlan.to_card_mask()
  └─ 也要 enumerate_groupings() → best_plan → 27×3 mask
      ↑ 再跑一次
```

**解决方案**：引擎提前到 `_extract_features()` 入口跑一次，同时产出三样东西。

### 改后数据流

```
decide()
  ├─ _run_grouping_engine()          ← 只跑一次，产出 card_mask + role + features
  │
  ├─ filter_action_list (Guard)      ← Layer 1: 硬排除 Guard 规则（R01-R15）
  │
  ├─ _group_consistency_filter()     ← Layer 1.5: 角色驱动前置过滤（按 card_mask 剔拆 core 动作）
  │    ├─ 硬例外：自己≤5 / 对手≤2 / 队友1张且下家非1张 → 全部放行
  │    ├─ 主攻/超强主攻：移除拆核心牌型动作
  │    └─ 助攻/超弱：走投喂规则条件放行
  │
  ├─ 接风跟线 + 投喂策略 (重排)
  │
  ├─ _model_decision() / _heuristic_select()
  │    └─ _extract_features(game_state, action_list)
  │         ├─ 复用已缓存的 card_mask / role / grouping_features
  │         │
  │         ├─ static_features     (124维)
  │         ├─ dynamic_features    (64维)
  │         ├─ state_belief        (8维)
  │         ├─ tracking_vector     (24维，MemoryTracker 只出追踪部分)
  │         └─ grouping_features   (24维，外部传入，不再从 MemoryTracker 内部算)
  │              ↓
  │         state_vector → NN forward / heuristic → 最终动作
  │
  └─ validate_decision → 返回 action
```

> **管线顺序定音（2026-06-20）**：Guard → _group_consistency_filter → NN/heuristic。此顺序由 R08/R09 需求驱动——Guard 先按队友剩牌过滤（如队友剩1张→只留最小Single+PASS），_group_consistency_filter 随后按角色/投喂规则保护 core 牌型。若反转（group_filter→Guard），R08 看候选池中可能已经无 Single（被 group_filter 删了），队友送单逻辑完全架空。

### 关键变化

| 组件 | 当前 | 改后 |
|------|------|------|
| `_extract_features()` | 间接通过 MemoryTracker 调分组引擎 | 直接调 `enumerate_groupings()`，一次性产出 features + mask + role |
| `MemoryTracker.get_state_vector()` | 返回 33/48 维（追踪 + 组牌） | 拆为 `get_tracking_vector()` (24维) + 外部拼接组牌特征 |
| `GroupingPlan` | 无 `to_card_mask()` | 新增 `to_card_mask()` → `[group_id, is_core, group_size]` × 27 |
| `decide()` | Guard → NN → validate | Guard → **group_filter**(mask + role) → NN → validate |
| grouping engine 调用次数 | 每轮 2 次 | **每轮 1 次** |

### 两条管道互不干扰

```
enumerate_groupings()
  │
  ├─ best_plan ──┬──→ role（主攻/助攻）→ decide() 角色判断
  │              │
  │              └──→ to_card_mask() → [group_id, is_core, group_size] × 27
  │                       ↓
  │                   group_filter（前置过滤，主攻剔拆核心动作）
  │
  └─ all_plans ──→ _extract_features(all_plans, ...) → 24维 float
                        ↓
                   MemoryTracker 拼接 → state_vector → NN forward
                   （NN 感知"牌力弹性"）
```

#### 为什么 features 用全部方案、mask 只用最优方案

**features（进 NN）用 `all_plans`**：

`enumerate_groupings()` 枚举 6 种策略（BOMB_FIRST / BALANCED / ROUND_OPTIMAL / NO_STRAIGHTS / ALL_COMBOS / SF_FIRST），
每种策略给同一手牌不同的组牌视角。`_extract_features(all_plans, ...)` 把这 6 套方案汇总为 24 维 float，捕捉的是手牌的**弹性空间**：

- 最优方案得分 0.85，次优 0.82 → NN 知道"手牌结构灵活，有多种合理组法"
- 最优方案得分 0.90，次优 0.40 → NN 知道"手牌结构刚性，只有一种组法最优"
- 所有方案都含 2 炸 → NN 知道"这手牌炸弹充沛"
- 3/6 方案含同花顺 → NN 知道"同花顺存在但不稳定"

NN 不需要知道"♦9 属于炸组 1"，但需要知道"我的手牌是有弹性的还是刚性的"——这直接影响决策：弹性手牌可以冒险拆一张，刚性手牌必须死守方案。

**mask（进前置过滤）用 `best_plan`**：

前置过滤的职责是"主攻时，哪些牌不能拆"。这个判断需要一个**明确的、无歧义的标准**。

- 方案 A 说 ♦9 是 Core（炸组成员），方案 B 说 ♦9 不是（走散了）
- 如果同时用两套方案，♦9 算不算 Core？没法决定
- 只有一个 best_plan，说一不二：「♦9 是 Core，主攻不能拆」

用最佳方案作为 mask 来源，相当于告诉前置过滤：「最优视角下，这些牌是核心——别动它们。」

#### 总结

| | 来源 | 内容 | 去向 | 作用 |
|------|------|------|------|------|
| features | `all_plans`（6 方案汇总） | 24 维 float（方案多样性、牌力弹性） | state_vector → NN | 软引导：NN 感知手牌结构特征 |
| mask | `best_plan`（最优方案） | 27×3（group_id, is_core, group_size） | group_filter | 硬约束：主攻禁止拆核心牌型 |
| role | `best_plan`（最优方案） | "主攻"/"助攻" 字符串 | decide() | 决定前置过滤开关 |

三者同源（一次 `enumerate_groupings()`），分流不同下游。features 和 mask 互不干扰——NN 继续通过软引导学习，前置过滤按角色硬收窄候选空间。

## 五、模式对比：从「焊住」到「团队博弈」

| 模式 | 对应阶段 | 组牌角色 | NN 感知 | 机制 | 上限 |
|------|:--:|------|------|------|------|
| **硬约束** | 第一 | 代替 NN 决策 | 看不见方案 | 硬过滤全部拆 core 动作 | 零 —— "电烙铁焊住" |
| **零约束** | V7 当前 | 仅 24 个抽象数字 | 不知牌型边界 | 无过滤 | 无序 —— 90%+ 拆核心牌型 |
| ~~后置偏置~~ | ~~第二~~ | ~~统一 soft bonus~~ | ~~方案不可见~~ | ~~argmax 前加偏置~~ | ~~"打好自己的牌"~~ |
| **前置过滤（选）** | **第三** | 角色驱动候选过滤 | 主攻看不到拆 core 动作 | 主攻: 移除非完整 core 组动作 | "理解团队博弈" |

第二阶段的场景衰减和后置偏置都被舍弃。前置过滤将判断权交给
掼蛋的本质——**你在团队里是什么位置，你面前的候选池就长什么样**。

## 六、实施路线

### Phase 1：card-level grouping mask（不进 NN）

- `GroupingPlan` 新增 `to_card_mask()` 方法，为 27 张手牌每张输出
  `(group_id, is_core, group_size)` 元组 → 27×3 维数组
- **不进 NN 输入、不进 state_vector、不重训**
- mask 传给 `decide()`，用于 Phase 2 前置过滤
- 后续 GUA-039b 自对弈时考虑将 mask 编码接入 NN 输入（路线 1）

### Phase 2：角色驱动前置过滤（插入 _model_decision 之前）

- `decide()` 中：Guard filter 之后、`_model_decision` 之前插入
  `_group_consistency_filter(action_list, card_mask, role)`
- 过滤规则：
  - 主攻：移除「拆核心牌型」的动作（部分使用 core 组牌且未完整打出）
  - 助攻：全部放行
- 安全阀：过滤后候选为空 → 全部放行
- 硬例外（放行全部）：
  - 自己剩 ≤5 张
  - 对手剩 1-2 张

## 七、核心原则

1. **组牌不替 NN 决策** — NN-first 架构下，组牌是信息提供者，不是决策者
2. **角色决定 NN 看到的候选空间** — 主攻看不到拆核心动作（前置过滤），助攻看到全部动作（自由发挥）
3. **前置过滤而非后置偏置** — 插入点在 Guard filter 之后、NN forward 之前，不改 NN 输入/训练
4. **极端局面放行全部** — 对手快赢了 / 自己快跑光了 / 队友剩1张要送单（下家非1），过滤关闭，全部候选进池
5. **安全阀避免死路** — 过滤后候选为空时全部放行，不造出无牌可出的局面

## 八、超弱角色投喂规则：从"一律过滤"到"条件放行"

> 背景：GUA-069 修复后，所有角色统一保护 core 牌型（炸弹/同花顺/顺子/三张），超弱角色不再全放行。但超弱角色需要**有条件地**放行某些拆牌动作以投喂队友。
> 关联：队友保护策略（待讨论）会影响投喂场景的前置条件。

### 8.1 牌张大小顺序（基础定义）

掼蛋牌张从大到小的严格顺序：

```
HR(大王) > SB(小王) > curRank(级牌) > A > K > Q > J > T(10) > 9 > 8 > 7 > 6 > 5 > 4 > 3 > 2
```

**"级牌以下"的定义**：在以上排序中，所有排在 curRank 之后的牌张。即从 A 开始往下全部属于"级牌以下"。

> ⚠️ **常见混淆澄清**：curRank 的牌张大于 A。例如 curRank=8 时，8 > A > K。因此 A、K、Q、J、T、9、……、2 全部属于"级牌以下"。K 单张**也是**级牌以下单张，不是"级牌以上"的单张。

**级牌以上**：只有 HR(大王) 和 SB(小王)。

### 8.2 超弱角色的放行规则总览

| 牌型 | 超弱是否放行 | 说明 |
|------|:---:|------|
| 炸弹（含同花顺） | ❌ 永不放行 | 炸弹/同花顺是战略资源，超弱也不得拆 |
| 顺子 | ❌ 默认不放行 | 仅场景三可放行（见下） |
| 其他 core 牌型（三张/对子/三带二等） | 🔀 条件放行 | 见场景一、二、三 |

### 8.3 铁律：有现成先出现成

投喂队友的最高原则：

> **如果手里有级牌以下的现成单张或对子，必须先出现成的，不得拆任何结构性牌型。**

这条铁律用前置过滤自动保证：当存在自然废单/废对时，场景一/二的放行条件不满足（`_has_natural_*_below_cur_rank()` 返回 true），拆牌动作被过滤，NN 面前只有现成废单/废对可选。

只有当级牌以下确实没有任何现成废牌时，放行条件才满足，才允许拆结构性牌型投喂。

### 8.4 三种投喂场景

#### 场景一：队友出单 → 拆对子送单

**前置条件**（全部满足才放行）：
1. 队友获得出牌权：`greaterPos == (myPos+2)%4`
2. 队友出的牌型是单张：`get_action_type(greaterAction) == "Single"`
3. **手中不存在级牌以下的自然单张**：遍历手牌，不存在 rank < curRank 且 count==1 的牌

**放行动作**：拆对子出单（broken core group 类型为 "pair"）

**逻辑**：优先出级牌以下的废单张。只有当废单清空后，才允许拆对子去投喂。

**示例**（curRank=8）：
| 手中牌 | 投喂单张时 | 原因 |
|--------|-----------|------|
| 5 单张 + 4-4 对子 | 出 5 单 → **不拆** 4-4 | 5 是级牌以下自然单张，先出 |
| 只有 A 单张（无更低单张） | 出 A 单 → **不拆** 4-4 | A 也是级牌以下自然单张 |
| 只有 SB(小王) 单张 | 可拆 4-4 出单 | 小王是级牌以上，不属于"级牌以下废单" |

#### 场景二：队友出对 → 拆三张/三带二送对

**前置条件**（全部满足才放行）：
1. 队友获得出牌权：`greaterPos == (myPos+2)%4`
2. 队友出的牌型是对子：`get_action_type(greaterAction) == "Pair"`
3. **手中不存在级牌以下的自然对子**：遍历手牌，不存在 rank < curRank 且 count>=2 的牌

**放行优先级**（铁律自动保证）：

```
有现成级牌以下对子 → 出现成的（不拆）
      ↓ 无
有三带二附牌对子（如 8-8-8+5-5 中的 5-5）→ 拆出 5-5（优先拆附牌，保留三张完整性）
      ↓ 无
拆三张出对子（如 8-8-8 → 8-8 + 单 8）→ 最后手段
```

**示例**（curRank=8）：
| 手中牌 | 投喂对子时 | 原因 |
|--------|-----------|------|
| 4-4 对子 + 8-8-8 三张 | 送 4-4 → **不拆** 8-8 | 4-4 是级牌以下自然对子，铁律先出现成 |
| 8-8-8 + 5-5 三带二（无其他级牌以下对子） | 出 5-5 → 保留 8-8-8 | 5-5 是三带二附牌，优先拆附牌 |
| 8-8-8 裸三张（无附牌对子、无级牌以下自然对子） | 拆 8-8-8 出 8-8 | 别无选择，拆三张出对子 |

> **铁律自动执行**：前置过滤只需检查条件 3（是否存在级牌以下自然对子）。有自然对子 → 过滤条件不满足，不拆。无自然对子 → 放行，NN 在三带二附牌 vs 拆三张之间由 NN 自由选（附牌 5-5 通常牌力更低，NN 自然倾向选它）。

#### 场景三：队友剩 7-8 张冲刺 → 拆顺子送单/对

**前置条件**（全部满足才放行）：
1. 队友剩余手牌数：`publicInfo[teammate].rest in (7, 8)`
2. 自己已无获胜可能：`role == "超弱"` 或 power_score 极低（组牌引擎已给出）
3. 队友需要冲刺配合

**放行动作**：拆顺子出单张或对子（broken core group 类型为 "straight"）

**顺子拆牌规则**：
- 顺子必须且只能由 5 张连续单张组成。拆掉任意一张后，剩余的 4 张无法再组成有效顺子，整组废掉。
- 拆顺子是除炸弹外最后的选择——只有在没有其他牌型可拆时才考虑拆顺子。
- 拆法：可从任意位置拆（端牌或中间均可），但人类惯例是拆倒数第二张（从小端数起）。例如 `3-4-5-6-7`，先出 `4`，留 `3` 和 `5-6-7` 散件。
- 代码不强制端牌限制：由 NN 在放行的拆顺子候选动作中自由选择拆哪张。NN 的牌力评估自然会倾向拆低点牌。

> 此场景覆盖了场景一/二中顺子不放行的例外：队友即将冲刺时，顺子也可以拆。

### 8.5 实现结构

修改 `_group_consistency_filter` 的过滤循环，对每条候选动作执行：

```python
for idx, action in enumerate(action_list):
    core_type = _get_broken_core_type(action, card_mask)

    if core_type is None:
        keep                          # 不拆任何 core → 保留
    elif core_type in ("bomb", "straight_flush"):
        remove                        # 炸弹/同花顺 → 永不放行（全角色）
    elif core_type == "straight":
        if _scenario_3_teammate_sprinting(state):
            keep                      # 场景三：队友冲刺可拆顺子
        else:
            remove                    # 顺子 → 其余不放行
    elif core_type in ("trips", "three_with_two", "pair"):
        if _scenario_1_feed_single(state) or _scenario_2_feed_pair(state):
            keep                      # 场景一/二：投喂单或对
        elif _scenario_3_teammate_sprinting(state):
            keep                      # 场景三：队友冲刺放行所有（除炸弹）
        else:
            remove
```

**过滤只放行不选择**：放行后 NN 仍在所有放行的候选动作中使用 softmax → argmax 选择最优动作。场景一/二中有自然废单/废对时，拆牌动作被过滤，NN 自然选到废单/废对。铁律「有现成先出现成」自动生效。

### 8.6 所需新增函数

| 函数 | 职责 |
|------|------|
| `_get_broken_core_type()` | 判断动作破坏了哪种类型的 core group，返回类型字符串；未破坏任何 core 则返回 None |
| `_scenario_1_feed_single()` | 检查场景一：队友出单 + 自己无级牌以下自然单张 |
| `_scenario_2_feed_pair()` | 检查场景二：队友出对 + 自己无级牌以下自然对子 |
| `_scenario_3_teammate_sprinting()` | 检查场景三：队友 7-8 张 + 自己无赢面 |
| `_has_natural_singles_below_cur_rank()` | 手牌中是否存在 rank < curRank 且 count==1 的牌 |
| `_has_natural_pairs_below_cur_rank()` | 手牌中是否存在 rank < curRank 且 count>=2 的牌 |

需要增强 `to_card_mask()` 输出 `group_id → 牌型字符串` 的映射。

### 8.8 已决议

#### 决议 1（Q1）：拆三带二时优先拆附牌对子

**铁律「有现成先出现成」**：前置过滤自动保证——当存在级牌以下自然对子时，场景二放行条件不满足，拆牌动作被过滤。NN 只会看到现成对子。

当无自然对子时，NN 在三带二附牌对子（5-5）和拆三张出对子（8-8）之间自由选，附牌通常牌力更低，NN 自然倾向选它。**不需要额外编码区分**。

#### 决议 2（Q2）：顺子拆牌不强制端牌限制

顺子必须且只能由 5 张连续单张组成，拆任意一张整组报废。代码不强制拆哪张，由 NN 在放行的拆顺子候选动作中自由选择。NN 的牌力评估自然倾向拆低点牌，大概率符合人类惯例（倒数第二张）。

#### 决议 3（Q3）：场景一/二仅在队友"刚获得出牌权"的第一手触发

**实现**：新增布尔状态 `teammate_just_gained_lead`：
- 每轮开始时检查：`prev_greaterPos != teammate AND cur_greaterPos == teammate` → `True`

**现状**：`_run_grouping_engine()` 已通过手牌 hash 缓存（L311-313）自动检测手牌变化。每次 `decide()` 手牌必然和上一轮不同，引擎自动重跑，`card_mask` 始终是最新的。

**结论**：无需新增任何投喂拆牌重分组触发。现有 hash 缓存已覆盖。

```
新签名：(action_list, greater_pos, my_pos, numofplayers, greater_action, cur_rank)

1. 队友控牌 + 自己 >10 张 → 仍为前置条件
2. 读 greater_action → action_type, curVal
3. 按牌型阈值：
   - single:          curVal >= 15 → 让道
   - pair:            curVal >= 12 → 让道
   - three:           curVal >= 11 → 让道
   - three_with_two:  curVal >= 12 → 让道
   - straight:        curVal >= 10 → 让道
   - straight_flush:  curVal >= 10 → 让道
   - bomb/unknown:    保持原行为（curVal 无关，只留 PASS）
4. 队友近尾例外：numoffri <= 4 → 不让道，返回全部（帮队友冲线）
5. curVal 低于阈值 → 不让道（对手可能压队友，自己应参与）
```

**不做 max_val 检查的原因**：guard 层没有 `publicInfo`/`rest_cards_list`，无法精确计算全局最大牌值。M3 的 `curVal >= max_val` 条件（绝对安全→让道）暂不导入，后续迭代可考虑将 `publicInfo` 传入 guard 层。

> 🔮 **后续迭代**：M3 的精细度本身也不高（仅 6 类阈值 + 队友近尾例外），V7 可在此基础上进一步提升——比如结合全局牌记忆（大王/小王/级牌出了几张）动态调整阈值，或者按"自己能否压队友"做二次判断防"让道后被对手反压"。

**改动量**：`v7_guards.py` 约 30 行（改函数签名 + 新增阈值表 + 队友近尾例外）。

#### 决议 10（Q11）：方案 C — 基于队友余牌数的投喂策略

**核心原则**：自己是弱牌（超弱/助攻）才有投喂，强牌（主攻/超强主攻）不存在投喂。不硬拆牌组去送。

**投喂的两阶段流程**：

```
对手出牌 → 队友被压（无力或不愿拆牌型） → 队友PASS
    → 我（弱牌）压制对手获得 greaterPos（出牌权）
        → 按队友余牌数送对应现成牌型
```

**阶段 1（被动侧解围获权）**：对手控牌时，检测队友是否被压：
- 对手出牌 + 队友 PASS（greaterPos 不是 teammate）
- 且我是超弱或助攻角色
- 且队友余牌数暗示某种牌型（见下表）
- → 我应压制对手获取出牌权（用更大牌或炸弹），而不是 PASS
- **特别强制**：队友余牌 ≤5 + 对手出 A 级以上的 5 张类牌型（三带二/顺子）→ 队友明显无力压制 → 我必须用炸弹或相同牌型压制，不能 PASS

**阶段 2（主动侧按余牌数投喂）**：我获得 greaterPos 后：

| 队友余牌 | 投喂牌型 | 说明 |
|:---:|------|------|
| 10-9 张 | 三带二 / 顺子（现成） | 用手中已有的 5 张组，不拆 |
| 8-6 张 | 单张 / 对子（现成） | 不拆 |
| **5 张** | ①先三带二/顺子 → ②对手不接再送单 | 唯一有反馈路径：先送 5 张类，若对手不压（greaterPos 非对手）说明队友不是这个牌型，改送单张 |
| 4 张 | 对子（现成） | 不拆 |
| 3 张 | 三张（现成） | 不拆 |
| 2 张 | 对子（现成） | 不拆 |
| 1 张 | 最小单张（现成） | 不拆 |

**设计逻辑**（为什么这样设计）：

1. **不硬拆是第一条底线** — 拆炸弹/顺子/三带去送，送完自己全废
2. **余牌数映射牌型** — 掼蛋常见规律：剩 5 大概率三带二/顺子、剩 4 大概率两对、剩 3 大概率三张、剩 2 大概率对子、剩 1 大概率单张
3. **5 张有反馈** — 最关键的残局关口：先试探 5 张类牌型，如果对手不接说明队友大概率不是该牌型，降档为单张
4. **只触发于弱牌角色** — 强牌自己打自己的，不需要投喂
5. **没有"队友牌力判断"** — 不需要评估队友强不强，只看余牌数。避免了 M1 的过严条件导致 0 触发

**与 R07（让道 PASS）的关系**：
- R07 触发条件是"队友控牌"（greaterPos == teammate）→ 让道 PASS
- 方案 C 触发条件是"对手控牌"（greaterPos == opponent）→ 压制对手 → 投喂
- **两者不冲突**：R07 管队友控牌时让道，方案 C 管对手压队友时帮队友解围

**需澄清的术语**：

> "投喂"不是"我出牌直接送给队友"。在掼蛋中，只有获得 greaterPos（出牌权）的人才能主导下一轮牌型。投喂路径是：队友被对手的牌型压制（如队友剩 5 张三带二但对手出对子，队友拆了三带二打对子后剩单+三+单就废了），队友 PASS，我（弱牌）用更大的相同牌型或炸弹压制对手，获得出牌权后再出与队友余牌数匹配的牌型，队友就能舒服地过牌或回收。

**代码位置**：`ultimate_win_rate_engine_v7.py` `_group_consistency_filter` 之后新增 `_try_teammate_feeding()`，约 50 行。分两段：`_should_rescue_teammate()`（被动侧判断是否压制） + `_pick_feeding_action()`（主动侧选投喂牌型）。

**实现细节（Q7 讨论产出）**：

##### D1：代码插入层

```
Guard 层（_filter_action_list_impl）
  → R05/R07(决议9)/R08/R09 等硬约束
    → _group_consistency_filter（拆 core 过滤 + 角色分流）
      → 【新增】_try_teammate_feeding()（方案 C 两阶段）
          阶段 1 硬约束：_should_rescue_teammate() → 删 PASS，强制压制
          阶段 2 软引导：_pick_feeding_action()     → 按余牌数选最小现成牌型
        → NN 排名 → top-1
```

- 阶段 1 放 `_group_consistency_filter` 之后（有 role 信息）而非 Guard 层（无 role）
- 阶段 2 紧跟阶段 1，同位置做软引导

##### D2：阶段 1 硬约束 — 删 PASS，强制压制

| 场景 | 行为 |
|------|------|
| 有能压制的牌（更大相同牌型或炸弹） | 硬删 PASS，保留压制动作 |
| 没有能压制的牌（无更大牌型也无炸弹） | PASS 自然保留（唯一退路） |

**不凭空变牌**：删 PASS 只是在有多于 PASS 的动作时才生效。只剩 PASS → 照常 PASS。

##### D3：多候选选最小牌

投喂时如有多个匹配牌型的候选（如队友剩 2 张，手里有 3-3 也有 8-8），**选最小对子**（3-3）。原则：能送就行，不浪费大牌。

##### D4：5 张反馈路径的状态记忆

复用决议 8 的 `self._teammate_last_trick_type`：
- 第一次送三带二/顺子后，记录 `_teammate_last_trick_type = "five_card"`
- 下一轮如 greaterPos 非对手（对手没压），说明队友不是 5 张类牌型 → 降档送单张
- 状态保留直到队友牌张数量变更（出牌后 re-count），变更后重置
- 中间如果有炸弹或其他干扰（对手炸了），状态仍保留——只要队友牌没少、对手没压，说明试探结果有效

##### D5：投喂退出条件（优先级排序）

投喂前检查，以下任一条件满足 → **放弃投喂**，走正常 NN 决策：

| 优先级 | 退出条件 | 原因 |
|:---:|------|------|
| 1 | 对手剩余 ≤ 2 张 | 先防对手跑，堵对手比喂队友更紧急 |
| 2 | 自己剩余 ≤ 5 张 | 先自己冲线，残局自保优先于助攻 |

**优先级顺序**：先防对手跑 > 先自己冲线 > 投喂队友。

## 九、战略转向：从 NN argmax 到启发式选择（2026-06-19 定音）

> **背景**：GUA-064 日志确证 BC argmax collapse——2048 维输出空间仅用 2 维（PASS 50.1% + 首候选 48.9%，actIndex≥2 仅 0.9%）。多轮批跑累计队胜 1/93（1.1%），NN 实质上是"在 Guard 过滤后的合理动作中随机选一个"。同时 Guard 体系已证明有效：GUA-065 三规则独立带来副胜率 +18.5pp（7.0%→25.5%），R01-R14 每条规则都有秒级单元测试。

### 9.1 核心洞察：组牌引擎的成功范式可以复制

组牌引擎的迭代模式——观察问题→修改算法→单元测试→批跑验证——经过数轮迭代达到了人类中等水平：

```
组牌引擎：输入手牌 → 确定性规则 → 输出牌型分组 → 人类评判"分组合理吗？"→ 秒级测试
```

行牌 Guard 本质相同：

```
行牌 Guard：输入游戏状态 → 确定性规则 → 输出可行动作子集 → 人类评判"出牌蠢不蠢？"→ 秒级测试
```

**两者都不依赖"学习"，都是人类掼蛋经验翻译成 Python 代码。** 组牌能到中等水平，行牌为什么不能？

### 9.2 当前决策管线的结构性问题

```
actionList → Guard filter → 组牌引擎 → 角色过滤 → 接风/投喂 → NN argmax → validate → 最终动作
                                                              ↑
                                                    这里选 PASS 或首候选
                                                    基本等于随机选择
```

Guard 已经筛掉了明显错误的动作，但最后一步 NN argmax 在保留下来的合理动作中做随机选择。这既浪费了 Guard 的劳动，又无法利用任何出牌策略。

### 9.3 新架构：Guard 驱动 + 启发式选择

```
actionList → Guard filter → 组牌引擎 → 角色过滤 → 接风/投喂 → _heuristic_select → validate → 最终动作
                                                              ↑
                                                   按优先级选择：
                                                   ① 优先非 PASS（出牌 > 让道）
                                                   ② 同优先级取最小（节约牌力）
                                                   ③ 角色/场景感知
```

**决策权完全移交给规则体系**，NN 权重文件（bc_model_v3.pth）保留不动，未来自对弈 RL（GUA-039b）就绪时重新接入。

### 9.4 迭代循环

```
观察批跑中 V7 的错误出牌
    → 分析根因：Guard 缺失？还是 heuristic 不够聪明？
    → 加 Guard 规则（如 R14 领出不拆对子）或改进 heuristic 选择逻辑
    → pytest 单元测试（秒级）
    → 批跑验证（5-10 分钟）
    → 胜率爬升
```

这和组牌引擎的迭代模式**完全一致**。每一次改动都有独立测试，每一次批跑都是累积验证。

### 9.5 与 M3 的区别

| | M3 规则引擎 | V7 Guard + Heuristic |
|---|---|---|
| 结构 | 千行 if-else，规则交织 | Guard 正交叠加 + 选择函数独立 |
| 可测试 | ❌ 改一行崩全局 | ✅ 每条规则 pytest 独立测试 |
| 可观测 | ❌ 不知哪条触发 | ✅ 每规则 debug log |
| 可迭代 | ❌ 牵一发动全身 | ✅ 加 R15 不影响 R01-R14 |
| 角色感知 | ❌ 无角色概念 | ✅ 主攻/助攻/超弱 角色驱动 |

这不是回到 M3 老路，而是用测试驱动开发的工程手段，重走一遍"从人类经验到代码规则"的路径，但每次迭代有明确的秒级反馈。

### 9.6 NN 的未来

NN 不是永远放弃，而是暂存。当以下条件满足时重新接入：

1. 自对弈 RL 管线（GUA-039b）就绪
2. policy gradient 训练出 >50% 副胜率的 policy net
3. Guard + Heuristic 的 baseline 稳定在合理水平

届时 NN 替代 heuristic 作为最终选择器，Guard 体系作为安全网不变。

> 关联决策：GUA-071（新建）— 行牌启发式选择替代 NN argmax；参见 [[ISSUES]]、[[ITERATIONS]] 最新行。

### 9.7 四个深层矛盾：转向方案的自我审视（2026-06-19）

> 以下质疑由架构师/掼蛋专家/AI 训练专家三角视角联合产出，目标不是否定转向，而是防止转向从一个坑跳进另一个坑。

#### 矛盾一：组牌引擎与行牌决策的问题数量级完全不同

| | 组牌引擎 | 行牌决策 |
|---|---|---|
| 输入空间 | 27 张手牌（固定） | 手牌 + 出牌历史 + 各家残牌 + 级牌 + 进贡状态 |
| 决策粒度 | 一局一次 | 每轮一次，一局数十轮 |
| 正确性反馈 | 即时：人类看一眼就知道分组合不合理 | 延迟：这一手 PASS 可能是 3 轮后才输的根因 |
| 测试可行 | ✅ 静态评判 | ⚠️ 需要整副牌因果链 |

组牌引擎的「秒级单元测试」能做是因为输入固定、输出可静态评判。行牌中一手牌的对错取决于对手接下来出什么、队友能否接住、炸弹是否浪费在错误时机。这种**延迟因果**是规则引擎最难处理的——Guard TDD 能覆盖「出牌蠢不蠢」，但能覆盖「策略对不对」吗？

#### 矛盾二：heuristic_select 退回了零信念决策

[[掼蛋AI自我进化-随机应变套路]] 核心诊断：

> 掼蛋的决策依赖动态贝叶斯局面判断，标准 RL 学到的是没有条件依赖的条件概率。

Document 1 的解法是局面信念作为中间变量（记牌→策略→动作）。但 `_heuristic_select` 的三条优先级规则中，**没有一条涉及信念建模**——不推断对手手里有什么牌，不考虑「PASS 后队友能不能接过」。它本质上和崩溃的 NN 一样是「没有条件依赖的条件概率」，只是从 softmax 变成了 if-else。

#### 矛盾三：两个核心文档在互相否定

Document 1 §套路七 的路线：模块化训练 NN（Week 1 组牌 → Week 2 记牌 → Week 3 策略 → Week 4 动作）。这个模块化架构（`CardGroupingNetwork` + `CardCountingNetwork` + `StrategyNetwork` + `ActionNetwork`）**从来没有被训练过**。argmax collapse 是针对端到端 BC 的单一 policy net 的诊断——它在模块化架构上是否会发生？不知道。

用一个没有训练过的架构来论证「NN 这条路走不通」，是用端到端 BC 的失败否定了模块化 NN 的可能性。这是稻草人论证。

#### 矛盾四：WBridge5 和 M3 的成功条件在掼蛋中不成立

Document 1 引证 WBridge5 支持规则引擎。但：
- 桥牌叫牌有标准化体系（精确制/自然制），打牌有跟色约束
- 掼蛋的逢人配（百搭）+ 自由出牌权 → 状态空间组合爆炸远高于桥牌
- WBridge5 是「足以参赛」，不是「超越最强人类」

掼蛋的规则化程度远低于桥牌，规则引擎更容易碰到天花板，不是因为规则写得不够多，而是因为策略场景的组合爆炸超出了可手动编码的极限。

### 9.8 残酷现实 + 务实修正：Lalala 水平定位与方案重新定级

> ⚠️ **关键事实（2026-06-19 确认）**：Lalala 是弱对手——在人类标准下属于不会打掼蛋的，连初级水平都达不到。

这个事实从根本上重校了所有胜率数据的意义：

| 数据 | 原解读 | 修正后解读 |
|------|--------|-----------|
| M3 队胜 70% vs Lalala | M3 规则引擎很强大 | M3 只是一个**勉强能赢不会打牌的人**的 AI |
| V7 队胜 1.1% vs Lalala | NN 崩溃导致失败 | V7 在**不会打牌的人面前**也几乎赢不了任何一局 |
| V7 副胜 25.5%（GUA-065 后） | Guard 规则卓有成效 | Guard 规则让 V7 从「完全不会打」变成了「偶尔能赢几副」 |

**这意味着当前赛道不是「从 25% 到 50%」，而是「从不会打到会打」。** 在这个阶段，Guard 规则的秒级反馈优势是真实的——在对手也是弱 AI 的前提下，消除明显错误就是最大杠杆。

#### 修正后的方案定位

**不改变 GUA-071 的实施方向**，但诚实修正其定位：

```
原定位：heuristic_select 是 NN 的替代方案，战略终点
修正后：heuristic_select 是 NN 崩溃期间的过渡基线，上界待探索
```

具体修正：

1. **GUA-071 实施照旧**：用 `_heuristic_select` 替代 NN argmax。这比让崩溃的 NN 随机选动作好。

2. **上界诚实声明**：不预设 heuristic 能到多高。目前唯一的硬数据是 Guard 规则独立带来 +18.5pp 副胜率（7.0%→25.5%）。heuristic 的选择逻辑（非 PASS 优先 / 取最小 / 角色感知）能在此基础上挤出多少 pp，需要批跑数据说话，不做预测。

3. **并行保留模块化 NN 路线**：Document 1 §套路七 的模块化 NN 路线不因本次转向而废弃。特别是 **记牌模块（CardCountingNetwork）**——从出牌历史推断各家剩余牌分布——这恰恰是规则引擎最难做、NN 最容易做的。当前因 NN 崩溃而放弃所有 NN 模块，是用一个可解决的问题（端到端 BC 崩溃）来论证一个不可逆的方向（永远不用 NN）。正确的做法是：heuristic 做基线保障不退化，记牌 NN 并行开发提供信念建模能力。

4. **Lalala 弱的事实是双刃剑**：
   - 正面：在弱对手面前，消除明显错误（Guard）就有显著收益，heuristic 方向短期内有效
   - 反面：M3 70% vs 弱对手意味着 M3 本身也不强。如果目标是「能赢人类」，Lalala 不是合格的参照系。长期需要一个更强的测试对手

5. **不回到 M3 老路的保证**：Guard 的正交架构、pytest 独立测试、debug log 可观测性，这些工程改进是真实的。它们不保证 V7 比 M3 更强，但保证 V7 比 M3 **更容易变强**——迭代成本低一个数量级。

> **总结**：GUA-071 是有意义的过渡方案，但不是最终答案。真正的答案可能在「Guard 规则引擎 + 记牌 NN（信念建模）+ heuristic 选择」的混合架构中——让规则覆盖确定性的错误，让 NN 覆盖概率性的推断，让 heuristic 在两者基础上做最终选择。这个方向 V7 当前走了一半（Guard 有了，heuristic 在建），还缺最关键的一块：信念建模。

### 9.9 Guard-Heuristic 管道架构全览（GUA-073 · 2026-06-19）

> **背景**：15 条 Guard + 1 个 Heuristic 8 条优先级——规则越堆越多，需要一张完整地图标注"什么规则在哪层、为什么"。

#### 9.9.1 三层职责边界

```
actionList (from platform)
  │
  ├─ _group_consistency_filter (组局一致性前置过滤)
  │   └─ 主攻：剔拆 core 动作 / 助攻+超弱：走投喂条件放行
  │   └─ 输出：缩小后的候选池
  │
  ├─ Layer 1: Guard 管道 (v7_guards.py filter_action_list)
  │   └─ 硬排除：只删不改、UNION 叠加
  │   └─ 输出：合法动作子集 + 动作索引映射
  │
  ├─ Layer 2: Heuristic 选择 (engine._heuristic_select)
  │   └─ 软排序：在 Guard 保留的动作中按优先级打分选最优
  │   └─ 输出：1 个最优动作索引
  │
  └─ Layer 3: validate_decision (v7_guards.py)
      └─ 安全网：覆盖 PASS/炸队友/卡牌校验
      └─ 输出：最终安全动作索引
```

#### 9.9.3 新增规则 checklist

```
问自己这两个问题：

① "这个动作应该被排除吗？"
   → 是 → 加进 Guard (v7_guards.py)，return 保留子集

② "这两个合法动作哪个更好？"
   → 是 → 加进 Heuristic (_heuristic_select)，加减分

不要同时在两层写相同逻辑！
Guard 删了炸弹 → Heuristic 不需要再扣炸弹分
Guard 限定了某场景只能 PASS → Heuristic 不需要再给 PASS 加分
```

|------|-----------|---------------|:--:|------|

| R01 删炸弹 → heuristic ⑧ 也扣炸弹分 | R01 删 Single 炸弹 | ⑧ 扣所有同型炸弹 | **互补** | R01 仅覆盖 Single，⑧ 覆盖 Pair/Trips/Straight 等 |
| R15 炸后相克 → 领出禁同型 | R15 删同型动作 | — | **无冲突** | 动作级别过滤，heuristic 根本看不到被删动作 |

#### 9.9.5 踩过的坑

1. **R11 记忆泄漏**（已修复 2026-06-19）：`_UPPER_SKIP_MEMORY`/`_POST_BOMB_BLOCK_TYPE` 是模块级全局 dict，定义但从未清理 → `UltimateWinRateEngineV7.on_game_start()` 每局开始时调用 `_clear_r11_memory_for_game()`
2. **Heuristic 重复判断**（已知，暂不修复）：⑧ "有同型不炸" 与 R01 "压单不用炸" 部分重叠（R01 仅 Single，⑧ 全牌型）→ 属互补而非重复，保持现状
3. **隐式条件耦合**：R11 放行炸弹的前提是"无同型非炸弹可压"，恰好与 R01 的过滤前提互斥 → 暂时安全，但改 R11 条件时需警惕

> **原则**：Guard 正交互不打架（UNION 叠加），Heuristic 只看 Guard 剩余的，validate 只看最终输出。三层各司其职，加新规则时先按 checklist 确定该放哪层。

## 十、清晰路线图：从现在到混合架构（2026-06-19）

> 背景：M3 底座方案被评审否决（千行规则→BC→RL 不可行）、V5 + 1312 人类数据 BC 失败（完全匹配率 0%）、V7 NN argmax collapse（2048 维只用 2 维）——三个否定性结论共同指向**同一个方向**：让 NN 做它最擅长的小而精的事，而不是强迫它做端到端的复杂映射。

### 10.1 三层走法

| 时间 | 做什么 | 为什么 |
|------|--------|--------|
| **现在** | GUA-071 heuristic 替代 NN argmax | 停止流血。NN 在 Guard 过滤后的合理动作中随机二选一，等于 Guard 白干。heuristic 是当前唯一可迭代的方向。 |
| **现在并行** | 规则记牌 ~50 行 | 给 heuristic 喂信念输入。当前 heuristic 是零信念决策——没有一条优先级涉及"对手手里还有什么牌"。改动量最小、收益最大。 |
| **2-4 周** | NN 记牌模块 | Document 1 核心组件。输入完整出牌历史 → 输出剩余牌分布，独立可训可测，不依赖端到端 BC。这是从未被训练过的、真正可能撬动质变的模块。 |
| **长期** | 三层混合架构 | Guard 规则引擎 + 记牌 NN（信念建模）+ 策略选择，各司其职：规则覆盖确定性错误，NN 覆盖概率性推断，heuristic 在两者基础上做最终选择。 |

### 10.2 转向不是放弃 NN，是给 NN 换一个正确的入口

```
端到端 BC 的失败否定了"手牌→动作"的一步映射
    ≠
模块化 NN 的失败

记牌 NN 的输入（四条出牌序列）完整、
输出（剩余牌概率分布）低维、
有明确 ground truth（restCards）
    →
和端到端 BC 是完全不同的问题
```

三个教训合在一起指向同一个地方：

1. **M3 底座方案的失败** → 教会我们不要用烂数据（弱对手胜局）训 NN
2. **V5 + 1312 人类数据 BC 的失败** → 教会我们端到端 BC 对大动作空间走不通
3. **V7 NN argmax collapse** → 教会我们 BC 训出的 policy net 作为最终选择器不可靠

**结论**：让 NN 做它最擅长的小而精的事（从完整出牌历史推断剩余牌分布），而不是强迫它做端到端的复杂映射。

### 11.2 Candidate-Action Scoring：不是固定 softmax

welkin03 的核心设计决策与 V7 的 argmax collapse 直接相关：

```
V7 的做法（失败）：
state → fixed 2048-dim softmax → 在全部可能动作中选 argmax
    → 只用 2 维，其余 2046 维浪费

welkin03 的做法：
state → MLP trunk → 对每个合法候选动作单独评分
    → 动作空间可变，只对当前合法动作打分
```

这正是 V7 路线图的"Guard 过滤 + 候选动作评分"模式——不是让 NN 在 2048 维里盲选，而是在 Guard 生成的合理候选集合上打分。

### 11.3 教师-学生蒸馏路线（与 V7 三层路线高度一致）

welkin03 的 NN 训练经历了完整的演进路径：

| 阶段 | 做法 | 结果 |
|---|---|---|
| V45 全信息教师 | 看四家牌 + 有界搜索 + paired gate 验证 | 166/192 胜率 86.46%（vs old-pool） |

| V46 公共信度蒸馏 | 隐牌采样 + V45 教师打分 + v18 anchor 防漂移 | 可行但不稳定，未发布 |

**关键教训**：
- 学生蒸馏不能只看 label fit → 必须上实战 paired gate
- 纯教师 label 会漂移 → 需要旧策略 anchor 标签做正则化

这与 V7 的"Guard + 记牌 NN + 策略选择"三层路线互补：welkin03 验证了教师→学生蒸馏的可行性，V7 可以跳过教师阶段直接用 Guard 规则引擎做候选生成。

### 11.5 Guard 设计模式：干净的函数拆分

welkin03 的每个 Guard 都是 `should_guard_*`（判断条件）+ `guard_*`（执行改写）一对函数：

| Guard | 触发条件 | 改写行为 |
|---|---|---|
| `active_bomb_lead` | 主动出炸开门，且手牌非全炸，且有非炸可选 | 改出最小代价非炸动作 |
| `single_card_opponent_lead` | 对手剩 1 张时主动出单 | 改出非单动作 |
| `single_card_opponent_response` | 对手剩 1 张且跟单，但自己有更大的单 | 改用最大非王牌单压死 |
| `partner_bomb_overplay` | 队友赢墩时出炸，对手未靠近走完 | 改 pass |
| `pre_first_pressure_response` | 无人走完前，对手出牌后可跟"改善组牌回合数"的动作 | 改出效率动作 |
| `dangerous_opponent_pass` | 关键对手状态（已走完/≤3 张/靠近走完）时不 pass | 改出非炸最小代价动作 |
| `partner_pass` | 队友赢墩时 pass | 有走完/单张锁/接牌则出，否则维持 pass |

**对 V7 的启示**：welkin03 的 Guard 更少（6-7 个）但更聚焦，每个都有独立的启用/关闭开关。V7 的 Guard 数量远超此数，但设计模式类似。可以考虑：
1. 为每个 V7 Guard 补充 `should_guard_*` / `guard_*` 的干净拆分
2. 增加 per-Guard 启用/禁用配置（便于 gate 实验）
3. 对比 welkin03 的 Guard 覆盖率找 V7 的盲区

| V7 路线图 | welkin03 的印证 |
|---|---|
| **现在**：heuristic 替代 NN argmax | ✅ `policy.py` 的 `heuristic_policy` 就是纯规则选择器，与 NN 无关 |
| **现在并行**：规则记牌 ~50 行 | ⚠️ welkin03 没有规则记牌——它依赖 hand_eval 的 `min_play_count` 做规划，但不追踪对手牌分布 |

## 十二、外部验证：DanZero+ 源码分析（2026-06-19）

> 来源：https://github.com/submit-paper/Danzero_plus ，中国科学技术大学（USTC），论文 [arXiv:2312.02561](https://arxiv.org/abs/2312.02561)。本地克隆到 `d:\guandanscore\danzero_plus\`。依赖环境 `guandan_mcc`（AltmanD）暂未克隆成功。

### 12.1 核心架构：DMC 预训练 → PPO 精调

DanZero+ 是目前已知最强的开源掼蛋 AI（vs 规则型 80%+，vs 人类 71/100 胜）。其架构分两阶段：

```
阶段 1：DMC (Deep Monte Carlo) 预训练
  ├── MLPQNetwork：512×5 MLP，输入 567 维 state → 输出标量 Q(s,a)
  ├── 训练方式：蒙特卡洛整局回报（非单步 TD）
  └── 产出：已训好的 Q 网络（代码中直接加载 q_network.ckpt，不需要在线训练）

阶段 2：PPO 精调
  ├── MLPActorCritic：共享 MLP trunk(512×4+256) → policy head(128→2) + value head(128→1)
  ├── DMC Q-net 将合法动作数压缩到 Top-2 → PPO 只在 2 个候选里选
  └── 分布式：ZeroMQ Actor-Learner 分离，pyarrow 序列化
```

### 12.2 动作空间压缩：Top-2（最关键的设计）

这是 DanZero+ 对 V7 最直接、最可操作的参考：

```python
# actor_torch/actor.py: sample() 方法
ActionNumber = 2  # 核心常量：始终只选 Top-2

def sample(self, state):
    legal_action = ActionNumber  # 默认 2
    if len(states) >= ActionNumber:
        indexs = self.model_q.get_max_n_index(states, ActionNumber)  # DMC 取 Top-2
        # ... 拼接 state + top_actions → 输入 PPO
    elif len(states) < ActionNumber:
        # 合法动作不足 2 个时补齐
        legal_action = len(states)
        legal_index[legal_action:] = 0  # mask 掉无效动作
    action, value, neglogp = self.model.step(states, legal_index)
    return indexs[action]  # 映射回真实动作索引
```

**与 V7 的对照**：

| | V7 当前 | DanZero+ |
|---|---|---|
| 候选动作生成 | Guard 规则过滤 | DMC Q 网络评分取 Top-2 |
| 候选动作数 | 不固定（Guard 过滤后） | **固定 2** |
| 最终选择 | NN argmax（2048 维） | PPO policy net（2 选 1） |
| 问题 | NN 只用 2 维，其余 2046 维浪费 | NN 输入维度正好是 2，无浪费 |

**关键启示**：DanZero+ 证明了**动作空间压缩到 2 个候选 + NN 做二选一是可行且强大的**。V7 的 Guard 过滤后也只剩少量合理动作，完全可以用同样的范式：Guard 生成候选 → 启发式/tiny-NN 在候选集上做选择。

### 12.3 状态表示（567 维特征向量）

DanZero+ 的 state 设计（`game.py:prepare()`）值得参考：

| 特征 | 维度 | 说明 |
|---|---|---|
| `my_handcards` | 54 | 自己手牌（0-1 编码） |
| `universal_card_flag` | 12 | 万能牌相关标志（顺子/连对/钢板/炸等可能性） |
| `other_handcards` | 54 | **除自己外所有剩余牌**（追踪对手可能持有的牌） |
| `last_action` | 54 | 最近一次出牌 |
| `last_teammate_action` | 54 | 队友最近一次出牌 |
| `down_played_cards` | 54 | 下家所有已出牌（累计） |
| `teammate_played_cards` | 54 | 队友所有已出牌（累计） |
| `up_played_cards` | 54 | 上家所有已出牌（累计） |
| `down/teammate/up_num_cards_left` | 28×3 | 三家剩余牌数（one-hot） |
| `self_rank` | 13 | 己方当前级牌（one-hot） |
| `oppo_rank` | 13 | 对手当前级牌（one-hot） |
| `cur_rank` | 13 | 当前局级牌（one-hot） |
| `my_action` | 54 | 当前考虑的合法动作 |

加上 `count_a`（3 维，记录 A 级牌出现次数），总计 567 维。

**关键发现**：DanZero+ 的 `other_handcards` 字段（除自己外所有剩余牌 + 已出牌的补集）是一种**隐式记牌**——它不是推断对手具体有什么牌，而是把"还可能存在于其他玩家手中的牌"作为原始特征输入 NN。V7 也可以先做一个简化的版本：用已出牌信息更新 `other_left_hands` 数组即可。

### 12.4 分布式训练架构

```
┌─────────────────┐     ZeroMQ     ┌─────────────────┐
│   4× Actor       │ ──── data ──→ │    Learner       │
│ (CPU, 推理+游戏)  │ ←── weight ── │  (GPU, 训练)     │
│                  │               │                  │
│ game.py:         │               │ learner.py:      │
│  WS 连接服务器    │               │  MemPool 2048    │
│  每局发 trajectory│               │  Batch 2048      │
│  actor.py:       │               │  PPO update      │
│  更新权重、采样   │               │  save ckpt       │
└─────────────────┘               └─────────────────┘
```

PPO 超参：`clip_ratio=0.2, lr=1e-4, train_iters=20, target_kl=0.01, γ=0.99, λ=0.95`

### 12.5 网络结构细节

```
DMC Q-Network:
  obs(567) → Linear+Tanh(512) ×5 → Linear(1)
  参数量：~1.3M

PPO ActorCritic:
  obs(2, 516+2×54) = (2, 624)
    → shared_mlp: Linear+Tanh(512) ×4 + Linear+Tanh(256)
    → policy_head: Linear+Tanh(128) → Linear(2) → Categorical
    → value_head:  Linear+Tanh(128) → Linear(1)
  参数量：~1.8M
```

注意 PPO 输入形状 `(2, 516+ActionNumber*54)`——状态不含动作部分的 516 维 + Top-2 动作各 54 维 = 624 维。也就是说，每个候选动作的 54 维编码和公共状态拼接后一起输入共享网络。

### 12.8 结论：两个项目指向同一个答案

welkin03 和 DanZero+ 各自独立验证了**同一个架构范式**：

```
候选动作生成（规则/DMC/Q-net） → 小候选集（2-10 个） → 策略选择（heuristic/NN）
```

区别只在于中间环节的复杂度：
- welkin03：规则引擎 → **不压缩**（所有合法动作）→ heuristic cost 排序
- DanZero+：DMC Q-net → **压缩到 2** → PPO policy net 二选一
- **V7 最优路径**：Guard 规则 → **压缩到 3-5** → heuristic/NN 选择

两个项目都没有试图做"端到端 BC 直接从 2048 维 softmax 选动作"——这本身就是一个强烈的信号。
