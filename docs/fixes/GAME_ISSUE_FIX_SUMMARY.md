# 游戏记录问题分析与修复总结

## 问题分析

### 问题1：yf2_v5将两个红桃A（百搭、逢人配）轻易去组了一把小顺子

**问题描述**：
- 第1步：yf2_v5打出了 `['Straight', 'A', ['HA', 'S2', 'HA', 'S4', 'D5']]`
- 使用了两个HA（红桃A，百搭牌）组了一个A-2-3-4-5的小顺子
- 这是极大的浪费，因为红心配应该保留用于炸弹或关键组合

**根本原因**：
1. 代码中硬编码了`H2`作为百搭牌，但实际上应该根据`cur_rank`（当前级牌）动态判断
2. 如果级牌是2，红心配是H2；如果级牌是A，红心配是HA
3. 用红心配组小顺子的惩罚力度不够（只有-20分）

**修复方案**：
1. ✅ 修复红心配识别：根据`cur_rank`动态判断红心配（`H{cur_rank}`）
2. ✅ 增加用红心配组小顺子的惩罚：从-20分提升到-80分
3. ✅ 增加用红心配组长顺子的惩罚：-50分
4. ✅ 初期使用红心配组其他牌型的惩罚：从-20分提升到-40分

**修复文件**：
- `src/decision/card_grouping_strategy.py` (第194-221行)

### 问题2：天然单张留着不出，反而去拆三张打单张

**问题描述**：
- yf1_v5和yf2_v5都有天然单张（整副手牌只有唯一的一张）
- 但AI选择拆三张打单张，而不是优先使用天然单张

**根本原因**：
- 代码中有天然单张的识别逻辑，但优先级不够高
- 没有明确禁止拆三张打单张的规则

**修复方案**：
1. ✅ 增加优先使用天然单张的逻辑：+50分
2. ✅ 增加禁止拆三张打单张的规则：-60分
3. ✅ 在yf1_v5.py和yf2_v5.py中都添加了这些规则

**修复文件**：
- `src/communication/yf1_v5.py` (第828-850行)
- `src/communication/yf2_v5.py` (第906-928行)

### 问题3：D9重复出牌（手牌跟踪问题）

**问题描述**：
- 第13步：yf2_v5打出了 `['Pair', '9', ['H9', 'D9']]`（对子9）
- 第21步：yf2_v5又打出了 `['Single', '9', ['D9']]`（单张D9）
- 这说明D9被重复使用了

**可能原因**：
1. 游戏引擎的手牌跟踪问题（不在我们的代码范围内）
2. 决策引擎在计算时使用了错误的手牌状态
3. 游戏记录文件本身的问题

**建议**：
- 这个问题需要检查游戏引擎的代码（`guandan_offline_v1006`项目）
- 可能是游戏服务器在更新手牌状态时出现了bug
- 建议在游戏引擎中添加手牌验证逻辑

**需要检查的文件**（不在当前项目）：
- 游戏引擎的手牌管理模块
- 游戏服务器的状态更新逻辑

## 修复总结

### 已修复的问题

1. ✅ **红心配识别问题**：根据`cur_rank`动态判断红心配
2. ✅ **红心配使用策略**：禁止用红心配组小顺子（-80分惩罚）
3. ✅ **天然单张策略**：优先使用天然单张（+50分），禁止拆三张打单张（-60分）

### 修复效果预期

1. **红心配使用**：
   - AI将不再轻易用红心配组小顺子
   - 红心配将优先保留用于炸弹或关键组合
